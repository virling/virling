Next.js Paddle UTM tracking: pass the visitor ID to Paddle.js checkout

By Devendra Variya, co-founder of Virling. Published 2026-11-23, updated 2026-11-25.

To tie a Paddle Billing checkout opened from a Next.js app to the visit that brought it, load the Virling script in your root layout, then open checkout from a client component with customData: { virling_vid: window.virling?.vid?.() } in Paddle.Checkout.open. Paddle stores it in the transaction's custom_data, and Virling joins the payment to every visit behind that visitor ID, with the UTM tags of each. Two files change, and the rest of your checkout stays as it is.

This post covers the App Router. For hosted checkout and where the values show up in Paddle, see the general guide to Paddle checkout UTM parameters. Using Stripe instead? See Next.js Stripe UTM tracking. On a Laravel backend? See Paddle UTM tracking with Laravel.

Why Paddle checkout loses your UTM tags

UTM tags live on the landing URL. Paddle only stores what you pass when checkout opens, and by then the visitor is usually a few pages past the landing page. Passing one visitor ID instead of the tags keeps earlier visits and untagged ones, such as search and referrals, too.

Step 1: add the script to the root layout

Use next/script with strategy="afterInteractive" in app/layout.tsx, so it loads once and runs on every route. Client-side navigation is counted too. If you self-host, replace app.virling.com with your Virling server.

import Script from "next/script";

export default function RootLayout({ children }) {
  return (
    <html lang="en">
      <body>
        {children}
        <Script src="https://app.virling.com/v.js"
          data-site="yourdomain.com" strategy="afterInteractive" />
      </body>
    </html>
  );
}

The script sets the first-party virling_vid cookie on your domain, records the UTM tags of each visit against it, and window.virling?.vid?.() returns the same ID in the browser.

Step 2: open Paddle.js checkout from a client component

Paddle.js and window.virling only exist in the browser, so open checkout from a client component. Load Paddle.js and initialize it with your client-side token as Paddle describes, then pass the visitor ID as customData:

// app/buy-button.jsx
"use client";
import Script from "next/script";

export default function BuyButton() {
  function buy() {
    Paddle.Checkout.open({
      items: [{ priceId: "pri_...", quantity: 1 }],
      customData: { virling_vid: window.virling?.vid?.() },
    });
  }
  return (
    <>
      <Script src="https://cdn.paddle.com/paddle/v2/paddle.js"
        onLoad={() => Paddle.Initialize({ token: process.env.NEXT_PUBLIC_PADDLE_CLIENT_TOKEN })} />
      <button onClick={buy}>Buy</button>
    </>
  );
}

Render <BuyButton /> on your pricing page. The ID is read on click, after both scripts have loaded. Paddle's reference for the options is Paddle.Checkout.open.

Or create the transaction in a route handler

If your server creates the transaction through the Paddle API, read the cookie from the request and set custom_data:

// app/api/checkout/route.ts
import { NextRequest, NextResponse } from "next/server";

export async function POST(req: NextRequest) {
  const res = await fetch("https://api.paddle.com/transactions", {
    method: "POST",
    headers: { authorization: `Bearer ${process.env.PADDLE_API_KEY}`, "content-type": "application/json" },
    body: JSON.stringify({
      items: [{ price_id: "pri_...", quantity: 1 }],
      custom_data: { virling_vid: req.cookies.get("virling_vid")?.value },
    }),
  });
  const { data } = await res.json();
  return NextResponse.json({ transactionId: data.id });
}

The browser then opens checkout with Paddle.Checkout.open({ transactionId }). Renewals carry no custom data of their own; Virling credits them to the channel of the subscription's first payment. The full setup is in the Paddle docs, on the Paddle integration page and on the Paddle for SaaS page.

Check that it works

  1. Connect a sandbox key that starts with pdl_sdbx_.
  2. In app/buy-button.jsx, call Paddle.Environment.set("sandbox") before Paddle.Initialize, put a sandbox client-side token in NEXT_PUBLIC_PADDLE_CLIENT_TOKEN and use a sandbox price ID. Then build again. If you use the route handler, also send it to https://sandbox-api.paddle.com/transactions, with a sandbox API key in PADDLE_API_KEY.
  3. Open a private window and visit a page that runs the script through a tagged link, such as https://yourdomain.com/?utm_source=test&utm_medium=email.
  4. In the same window, go to the page with <BuyButton />, click Buy and pay with one of Paddle's test cards.
  5. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed.

Use a new email address for each test, because a later payment by the same customer is a renewal and keeps the first payment's channel. A site has one Paddle connection, and sandbox payments stay in your reports after you replace the key with a live one. If a step fails, see test your setup.

Open the payment to see its journey. If it lists no visitor ID, checkout did not carry virling_vid: check that the page with the button loads the Virling script.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment, with a made-up channel table under step 5, is in how to track Paddle revenue by traffic source.

Frequently asked questions

How do I pass UTM parameters to Paddle checkout in Next.js?

Pass the Virling visitor ID instead. In a client component, call Paddle.Checkout.open with customData: { virling_vid: window.virling?.vid?.() }. The Virling script records the UTM tags of every visit against that ID, so the transaction is joined to all of them.

Where does Virling read the visitor ID on a Paddle transaction?

From virling_vid in the transaction's custom_data. Paddle.js sets custom_data from the customData you pass when you open checkout.

Why does the checkout code need a client component?

Paddle.js and window.virling only exist in the browser, so the code that opens checkout has to run there. Mark the file with "use client" and open checkout from a click handler.

What about transactions I create on my server?

Read the virling_vid cookie in the route handler and set custom_data: { virling_vid: ... } when you create the transaction through the Paddle API.

Which channel do Paddle renewals get?

Renewals carry no custom data of their own. Virling credits them to the channel of the subscription's first payment.
