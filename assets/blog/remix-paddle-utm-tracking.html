Remix Paddle checkout UTM tracking: pass the visitor ID

By Devendra Variya, co-founder of Virling. Published 2026-11-26.

Remix Paddle checkout UTM tracking takes one value: the visitor ID. Add the Virling script to app/root.tsx, read the virling_vid cookie in the pricing route’s loader, and pass it to Paddle.js as customData: { virling_vid } when checkout opens. Paddle keeps it on the transaction, and Virling joins the payment to every visit behind that ID, with the UTM tags of each. Two files change, and the rest of your checkout stays as it is.

The code is for Remix v2 on Paddle Billing, and works in React Router v7 framework mode with other imports. For a Vite single-page app, see React Paddle UTM tracking. On Stripe, see Remix Stripe UTM tracking. For where the values show up in Paddle, see Paddle checkout UTM parameters.

Why the tags are gone at checkout

A visitor lands on /?utm_source=newsletter&utm_campaign=launch and follows a <Link> to /pricing. The query string stays behind, so the URL has no tags when they click Buy, and Paddle stores only what you pass when checkout opens.

Step 1: add the script to the root route

Put the tag in the <head> in app/root.tsx, next to <Meta /> and <Links />. It is rendered into every page, and client-side navigation is counted on its own, so load it once here. If you self-host, replace app.virling.com with your Virling server.

// app/root.tsx
<head>
  <Meta />
  <Links />
  <script defer src="https://app.virling.com/v.js"
    data-site="yourdomain.com"></script>
</head>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it. The cookie is created in the browser, so the server sees it from the second request on.

Step 2: read the cookie in a loader and open checkout

Install the wrapper with npm install @paddle/paddle-js. It downloads Paddle.js from Paddle’s CDN and initializes it (source: Paddle, paddle-js-wrapper). The loader reads the cookie from the request’s Cookie header and hands it to the page, with the client-side token:

// app/routes/pricing.tsx
import { useEffect, useState } from "react";
import type { LoaderFunctionArgs } from "@remix-run/node";
import { useLoaderData } from "@remix-run/react";
import { initializePaddle, type Paddle } from "@paddle/paddle-js";

declare global {
  interface Window { virling?: { vid?: () => string | null } }
}

export async function loader({ request }: LoaderFunctionArgs) {
  const vid = request.headers.get("Cookie")
    ?.match(/(?:^|;\s*)virling_vid=([^;]+)/)?.[1] ?? null;
  return {
    vid,
    token: process.env.PADDLE_CLIENT_TOKEN!,
    sandbox: process.env.PADDLE_ENV === "sandbox",
  };
}

export default function Pricing() {
  const { vid, token, sandbox } = useLoaderData<typeof loader>();
  const [paddle, setPaddle] = useState<Paddle>();

  useEffect(() => {
    initializePaddle({ environment: sandbox ? "sandbox" : "production", token })
      .then(setPaddle)
      .catch(console.error);
  }, [token, sandbox]);

  function buy() {
    // The loader has no cookie when this page is the landing page.
    const id = vid ?? window.virling?.vid?.();
    paddle?.Checkout.open({
      items: [{ priceId: "pri_...", quantity: 1 }],
      ...(id ? { customData: { virling_vid: id } } : {}),
    });
  }

  return <button onClick={buy} disabled={!paddle}>Buy</button>;
}

initializePaddle touches window, so it runs in an effect, never in the loader or during server rendering. The client-side token is meant for the browser; never return an API key from a loader, because loader data is sent to the page. Paddle says Paddle.Initialize() can be called only once on a page (source: Paddle, Paddle.Initialize), and the wrapper switches to Paddle.Update() when Paddle.js is already initialized, so moving between routes is safe.

When the cookie is missing. If /pricing is the first page of the visit, its loader ran before the script set the cookie, so the click falls back to window.virling.vid(). vid() returns null in cookieless mode and before a visitor accepts under Until consent, and an ad blocker can stop the script. The spread leaves customData out then, because Paddle asks for valid JSON with at least one key (source: Paddle, Paddle.Checkout.open). The sale goes through either way, as Unattributed.

The loader’s data now differs per visitor. If a CDN caches /pricing, send Cache-Control: private for it from a headers export, or one visitor’s ID can reach another.

In React Router v7

In framework mode, import Route from ./+types/pricing, type the loader’s argument as Route.LoaderArgs and read the data from the component’s loaderData prop instead of useLoaderData:

import type { Route } from "./+types/pricing";

export async function loader({ request }: Route.LoaderArgs) { /* same */ }

export default function Pricing({ loaderData }: Route.ComponentProps) {
  const { vid, token, sandbox } = loaderData;
  // same as above
}

Hosted checkout links and server-created transactions

Hosted checkout links send the buyer to a page on Paddle’s domain. Paddle documents query parameters such as price_id and transaction_id for them, but not custom_data (source: Paddle, hosted checkout), and the Virling script does not add the visitor ID to Paddle checkouts by itself. A plain hosted link therefore gives an Unattributed payment. To keep the ID, create the transaction on your server first.

Server-created transactions are made in a Remix action, which receives the cookie with the form post. Set custom_data on the transaction:

// app/routes/pricing.tsx
import type { ActionFunctionArgs } from "@remix-run/node";

export async function action({ request }: ActionFunctionArgs) {
  const vid = request.headers.get("Cookie")
    ?.match(/(?:^|;\s*)virling_vid=([^;]+)/)?.[1];
  const res = await fetch(`${process.env.PADDLE_API_URL}/transactions`, {
    method: "POST",
    headers: {
      authorization: `Bearer ${process.env.PADDLE_API_KEY}`,
      "content-type": "application/json",
    },
    body: JSON.stringify({
      items: [{ price_id: "pri_...", quantity: 1 }],
      ...(vid ? { custom_data: { virling_vid: vid } } : {}),
    }),
  });
  const { data } = await res.json();
  return { transactionId: data.id as string };
}

PADDLE_API_URL is https://api.paddle.com, or https://sandbox-api.paddle.com with a sandbox key. Post to it with useFetcher, then open the result in Paddle.js with Paddle.Checkout.open({ transactionId }), or send the buyer to your hosted checkout link with ?transaction_id= and the ID. Create it in the action, not a loader, so a <Link prefetch> or a crawler does not make transactions nobody asked for.

What a renewal is credited to

A renewal never opens your app. Paddle says a transaction’s custom data is copied to the subscription, and from there to the transactions it creates (source: Paddle, custom data). Virling does not need that copy. A transaction with origin subscription_recurring, subscription_update or subscription_charge is a renewal and keeps the channel of the customer’s first payment, matched by Paddle customer ID. Only when that first payment was not credited does a renewal’s own ID count.

For example, with made-up numbers: a buyer lands from a newsletter link tagged utm_medium=email, pays $30 in May and renews at $30 in June and July. All $90 is credited to Email, even if they came back from a search in June. See renewals in the docs.

Test it in the Paddle sandbox

  1. In Virling, connect a sandbox API key that starts with pdl_sdbx_, with transaction.read and adjustment.read (Paddle docs).
  2. Set PADDLE_ENV=sandbox, a client-side token that starts with test_ in PADDLE_CLIENT_TOKEN, and a sandbox price ID (source: Paddle, client-side tokens). Run the app on your domain or a subdomain of it, such as staging.yourdomain.com.
  3. Open a private window on a tagged link, such as https://staging.yourdomain.com/?utm_source=test&utm_medium=email, then follow a link to /pricing.
  4. Click Buy and pay once with the test card 4242 4242 4242 4242, any name and a future expiry date (source: Paddle, test cards).
  5. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel instead of Unattributed.

The script is silent on localhost, and visits are kept only from the site’s domain and its subdomains. Use a new email address for each test, because a later payment by the same customer is a renewal. A site has one Paddle connection, and sandbox payments stay in your reports after you switch to a live key. If a step fails, see test your setup.

Frequently asked questions

How do I pass UTM parameters to Paddle checkout in Remix?

Pass the Virling visitor ID instead. Read the virling_vid cookie in the route loader, return it to the page, and call Paddle.Checkout.open with customData: { virling_vid: vid }. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

Why is the cookie missing in my loader?

The script creates the cookie in the browser, so the server sees it from the second request on. If the pricing page is the first page of the visit, its loader runs before the cookie exists. Fall back to window.virling?.vid?.() when the buyer clicks.

Can I add custom data to a Paddle hosted checkout link?

Paddle documents no custom_data parameter for hosted checkout links. Create the transaction in a Remix action with custom_data: { virling_vid }, then pass its ID as transaction_id in the hosted checkout URL.

Does it work in React Router v7?

Yes. The loader and checkout code are the same in framework mode. Type the loader with Route.LoaderArgs and read the data from the loaderData prop instead of useLoaderData.

Which channel does a Paddle renewal get?

The channel of the customer's first payment, when that payment was credited. It does not matter whether the renewal carries a visitor ID of its own in that case.
