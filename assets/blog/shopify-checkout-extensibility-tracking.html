Shopify checkout extensibility tracking: what still works

By Devendra Variya, co-founder of Virling. Published 2026-11-25.

Shopify checkout extensibility tracking runs through pixels, not pasted scripts. Code in checkout.liquid, in Additional scripts, or in an app's script tag no longer runs on the thank you and order status pages. App pixels and custom pixels still report purchases, from inside a sandbox. Attribution that never needed a checkout script is unaffected: if your store writes a visitor ID to the cart, Shopify copies it onto the order, and your analytics reads it from the order. So move each ad pixel to its app or a custom pixel, and check that new orders carry the ID.

What Shopify changed, and when

Everything in this table is from Shopify's own developer pages, read on 2026-11-25. Shopify can change these dates, so follow the link before you plan around one.

A script tag here is a record that an app creates through Shopify's API to load JavaScript on your store. A tag you paste into theme.liquid yourself is theme code, not one of those records. For tracking, Shopify's replacement is a web pixel; for content on the order status page, it is a customer account UI extension.

What a pixel can and cannot do

Shopify says pixels load on the storefront, checkout, thank you page and order status page, and that they run in a sandbox (how pixels work, read on 2026-11-25). There are two kinds. An app pixel comes with an app, and a custom pixel is code you add under Settings, Customer events. Four limits matter for tracking:

  • No page to read. A pixel sandbox cannot detect events, emails or phone numbers by scraping the page, and cannot show buttons, forms or banners.
  • JavaScript only, in a frame. A custom pixel runs in an iframe that cannot access the top frame. Reading the page address there returns the sandbox's URL, unless you take it from the event (about web pixels).
  • One purchase event, if the page loads. checkout_completed fires once for each checkout, usually on the thank you page. With upsells it fires on the first upsell offer page instead. If that page fails to load, Shopify says the event is not triggered at all (checkout_completed).
  • Consent decides. In markets set to require consent, web pixels run only when the visitor has given the permissions the pixel asks for. New pixels ask for Marketing and Analytics by default.

All of these pages were read on 2026-11-25. Shopify also says it does not support adding and using custom pixels, and recommends looking for an app first (creating custom pixel code).

The pattern is simple. Tracking that started on the last page of checkout has to become a pixel. Tracking that starts on your store pages and ends on the order has nothing to move.

Why an ID on the cart does not depend on a checkout script

A cart is made on your storefront, before checkout. Shopify's developer docs say that attributes set on a cart carry over to the resulting order after checkout (Attribute, read on 2026-11-25). So the steps are:

  1. A visitor lands on your store from a tagged link. Your analytics script records the visit and its source, and gives the visitor an ID.
  2. A snippet on your store pages writes that ID to the cart as an attribute.
  3. The buyer goes through checkout. No code of yours runs there, and none needs to.
  4. The order has the ID in its note attributes. Your analytics reads the order from Shopify and joins it to that visitor's earlier visits.

If the buyer closes the tab before the thank you page loads, the order is still in Shopify, ID included. Refunds work the same way: they are on the order, and no page has to open for them to count. That is the main idea of server-side revenue tracking. For Virling, the attribute is virling_vid, and this snippet goes in theme.liquid, after the Virling script:

<script>
addEventListener("load", function () {
  var vid = window.virling && virling.vid && virling.vid();
  if (vid) fetch("/cart/update.js", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ attributes: { virling_vid: vid } })
  });
});
</script>

The full method is in how to track Shopify revenue by traffic source. A headless store has no theme.liquid, so it sets the same attribute from its own cart code, as in the Shopify docs.

What the cart ID does not cover

  • Ad platforms. It tells you which visit led to an order. It does not send a purchase to an ad account, so an ad platform still needs its own pixel or server connection.
  • Blocked scripts. If an ad blocker, a consent choice or cookieless mode stops the script or its cookie, there is no ID to store.
  • Carts made elsewhere. Cart permalinks, Buy Button embeds, draft orders and other sales channels do not use your storefront's cart, so they have no ID.
  • Buttons that skip the cart. An express or Buy it now button may leave the ID out. Place a test order with each one you use.

In Virling, an order with no ID can still match by email, if its email is the same as one your site sent as an identify event. Otherwise it counts as revenue and shows as Unattributed. Other ways an order loses its source are in why Shopify orders show up as Direct.

Check list for a store that has moved

  1. List what you had. Find any saved copy of the old additional scripts and checkout.liquid, and write down each tag and what it reported.
  2. Find its new home. Give every tag on the list an app pixel, a custom pixel, or a decision to drop it.
  3. Open Customer events. In Settings, Customer events, check that each custom pixel shows as connected. A saved pixel that is not connected tracks nothing.
  4. Remove duplicates. Shopify says to remove old pixel code, such as in theme.liquid, so customer events are not counted twice (managing custom pixels).
  5. Check permissions. Look at what each pixel asks for, and test with consent given and refused in a market that requires it.
  6. Check the live theme. Theme code belongs to one theme. If you changed themes along with checkout, the analytics script and the cart snippet have to be in the new one.
  7. Ask about storefront script tags. For each app that loads a script on your store, ask its developer what happens on March 1, 2027.
  8. Place a test order. Open a tagged link in a private window, add a product, go to checkout from the cart and pay in test mode. In the order, check that the additional details include your visitor ID.
  9. Try each way to buy. Repeat with every express button, and with an upsell if you use one.
  10. Compare a week. Count orders in Shopify, purchases in each pixel, and orders that carry the ID, for the same seven days.

Frequently asked questions

Does Shopify checkout extensibility break conversion tracking?

It ends tracking that relied on checkout.liquid, additional scripts or an app's script tag on the thank you and order status pages. Tracking that runs as an app pixel or custom pixel works there, and so does reading orders from the Admin API.

What replaces additional scripts in Shopify?

For tracking, Shopify points to app pixels and custom pixels, which are managed under Settings, Customer events. For content shown on the thank you and order status pages, it points to apps and UI extensions.

When did Shopify script tags stop working on the order status page?

Shopify's dates are August 28, 2025 for Plus stores and August 26, 2026 for all other stores. Storefront script tags have a separate date, March 1, 2027. These are from Shopify's developer pages, read on 2026-11-25.

Can a custom pixel read the thank you page?

Not the page itself. A custom pixel runs in a sandboxed iframe that cannot access the top frame. It receives events instead, such as checkout_completed, which carry the checkout data.

Do cart attributes still reach the order?

Yes. Shopify's developer docs say attributes set on a cart carry over to the resulting order after checkout. The store's cart sets the attribute before checkout, so no script on the checkout or thank you page is involved.

Does Virling need a checkout script or a Shopify pixel?

No. Virling uses its script and a short cart snippet in theme.liquid, then reads paid orders and refunds with a custom app token that has only the read_orders scope.
