Cal.com UTM tracking: which channel books calls that pay

By Devendra Variya, co-founder of Virling. Published 2026-11-25.

For Cal.com UTM tracking, Cal.com does most of the work itself: it saves five standard tags from the booking address, fills booking questions from matching query parameters, and accepts hidden metadata from an embed. What it cannot tell you is which booked call ended in a paid invoice. This guide uses those Cal.com hooks to carry a Virling visitor ID into the booking, and covers self-hosted Cal.com, the webhook payload and routing forms.

Every Cal.com detail links to its source; the webhook, self-hosting and routing form pages were read on 2026-11-27 and the rest on 2026-11-25. Virling has no Cal.com integration; everything here runs on your pages and your server.

What Cal.com keeps from the booking address

Cal.com saves utm_source, utm_medium, utm_campaign, utm_term and utm_content with no setup (source: Cal.com, UTM parameter tracking):

https://cal.com/YOUR_NAME/30min?utm_source=newsletter&utm_medium=email&utm_campaign=october-launch

Anything else rides on a booking question. Cal.com fills any question from a query parameter named after its identifier (source: Cal.com, pre-fill fields), so a hidden, optional Short Text question with the identifier gclid or virling_vid stores that value too. Tags made in the UTM builder stay consistent across campaigns.

The hosted booking page lives on cal.com, where your Virling script cannot load. Send visitors through a page of yours first, or run Cal.com on your own domain as described below. With the Virling script on your site and cookieless mode off, this adds the tags and the visitor ID to each Cal.com link:

<script>
addEventListener("load", function () {
  var query = new URLSearchParams(location.search);
  var vid = window.virling?.vid?.();
  document.querySelectorAll('a[href^="https://cal.com/"]').forEach(function (a) {
    var link = new URL(a.href);
    ["utm_source", "utm_medium", "utm_campaign", "utm_content", "utm_term"].forEach(function (k) {
      var value = window.leadUtm ? leadUtm.tags[k] : query.get(k);
      if (value) link.searchParams.set(k, value);
    });
    if (vid) link.searchParams.set("virling_vid", vid);
    a.href = link.href;
  });
});
</script>

leadUtm is the tag memory from UTM parameters in hidden form fields. Leave it out and only tags in the current address are copied.

Embeds: config, metadata or forwarding

An inline, popup or floating button embed takes the tags in its config (source: Cal.com, UTM tracking in embeds). The other option is one line after the generated snippet (source: Cal.com, auto-forwarding query parameters):

<script>
  Cal.config = Cal.config || {};
  Cal.config.forwardQueryParams = true;
</script>

Forwarding starts off, copies every parameter of the host page unchanged, and per Cal.com does not work on Framer. It also knows nothing about a landing page the visitor saw earlier. The config route can use remembered tags and has a field the booker never sees: metadata[myKey], which reaches the webhook as payload.metadata["myKey"] and stays off the booking details page (source: Cal.com, prefill booking form in embed). Keep the loader and init lines of your snippet and swap its inline call for this, with 30min as the namespace the generator gave you:

<div id="my-cal-inline"></div>
<script>
addEventListener("load", function () {
  var query = new URLSearchParams(location.search), config = {};
  ["utm_source", "utm_medium", "utm_campaign", "utm_content", "utm_term"].forEach(function (k) {
    var value = window.leadUtm ? leadUtm.tags[k] : query.get(k);
    if (value) config[k] = value;
  });
  var vid = window.virling?.vid?.();
  if (vid) config["metadata[virling_vid]"] = vid;
  Cal.ns["30min"]("inline", {
    elementOrSelector: "#my-cal-inline",
    calLink: "YOUR_NAME/30min",
    config: config
  });
  Cal.ns["30min"]("on", {
    action: "bookingSuccessfulV2",
    callback: function () { window.virling?.("goal", "booking"); }
  });
});
</script>

The last call counts bookings as a Virling goal. bookingSuccessfulV2 fires on a new booking that may still need confirming, and its listed properties carry no email (source: Cal.com, embed events). Metadata is documented for embeds only, which is why plain links use the hidden question. Logged-in hosts of a booking see its tags and hidden answers on the booking details page (source: Cal.com, UTM parameter tracking).

If you redirect after booking, Forward parameters is on by default and puts the booker’s email in the address (source: Cal.com, booking success redirect parameters). Switch it off unless your page reads it, since addresses end up in history and logs.

Self-hosted Cal.com on your own domain

The self-hostable edition is now called Cal.diy. Its README describes it as the MIT-licensed community edition of Cal.com, with Teams, Organizations, Workflows and other enterprise features removed, and recommends it for personal, non-production use (source: Cal.diy on GitHub). Check that a feature in this guide exists in your copy before you depend on it.

What changes for tracking is the domain. Put the instance on a subdomain such as book.example.com and add the Virling script to its pages in your copy of the code. Virling counts pages on subdomains of example.com as the same site, and the virling_vid cookie is set on the registrable domain, so the booking page sees the same visitor as your marketing pages (source: Virling script docs). The booking page becomes part of the visit, and a direct link in an email is no longer a blind spot.

Two smaller differences: the embed snippets Cal.com generates point at the instance you copy them from (source: Cal.com, adding an embed), and a self-hosted instance accepts plain HTTP and private IP webhook addresses, where cal.com accepts only HTTPS (source: Cal.com, webhooks). Your receiver can sit on an internal network. The visitor ID still has to reach the webhook through a hidden question or metadata, because a webhook carries no cookies.

What the Cal.com webhook payload carries

Create the subscription at /settings/developer/webhooks with a secret, and check X-Cal-Signature-256, an SHA-256 HMAC of the raw body. Most triggers wrap the data as triggerEvent, createdAt and payload; Meeting Started and Meeting Ended send a flat object. The payload version is in the x-cal-webhook-version header. Inside payload are uid, bookingId, eventTypeId, status, organizer, attendees, responses and metadata, and for a seated event attendees holds only the seat that triggered it (source: Cal.com, webhooks).

No UTM field appears in those example payloads, so the tags stay on the booking details page. Each answer sits in responses under its question identifier with a value (source: Cal.com, booking questions). The optional custom payload template lists metadata and attendees among its variables but not responses, so keep the default payload if the ID comes from a hidden question. On Booking Created, send Virling one identify event:

const p = body.payload;
const vid = p?.metadata?.virling_vid || p?.responses?.virling_vid?.value;
const email = p?.responses?.email?.value;
if (body.triggerEvent === "BOOKING_CREATED" && vid && email) {
  await fetch("https://app.virling.com/api/event", {
    method: "POST",
    headers: { "User-Agent": "booking-webhook/1.0" },
    body: JSON.stringify({ n: "identify", u: "https://yourproduct.com/", s: "yourproduct.com", v: vid, m: email }),
  });
}

For no-shows, use Booking No-show Updated, sent when someone is marked on /bookings/past. Meeting Ended fires at the scheduled end whether or not anyone joined.

Routing forms

A routing form asks a few questions and then sends the person to an event, an outside address or a message, based on rules you set (source: Cal.com, routing overview). Three parts of it matter here:

  • URL parameters fill fields. Headless routing takes an address such as https://your-org.cal.com/router?form=YOUR_FORM_ID&email=..., and each parameter name must match a field identifier (source: Cal.com, headless routing).
  • Fields flow into the booking. A form field and a booking question with the same identifier pass the answer through (source: Cal.com, connect routing form to booking questions). A virling_vid field and a hidden virling_vid question carry the visitor ID to the webhook above.
  • The form has its own webhooks. Form Submitted sends formId, formName, teamId and the responses. Form Submitted No Event fires 15 minutes after a submission that led to no booking (source: Cal.com, webhooks).

That last trigger is useful: if the form asks for a work email, you can send the identify event at submission, so a lead who never books but pays later is still matched. A form embeds like an event, with forms/YOUR_FORM_ID as the link (source: Cal.com, adding an embed). Cal.com’s routing pages do not say whether a form field can be hidden, or whether incoming UTM tags pass through to the event the form redirects to, so make a test booking through the form and check the booking details page.

From booked call to paid invoice

Once Virling has the email and visitor ID together, a Stripe invoice later paid from that email is credited to the visit that led to the booking. The version without a server, the lookback window and the privacy notes are in demo booking revenue tracking.

Invented figures for one quarter, with no-shows taken from the Cal.com webhook:

Paid filled the calendar with 50 of 85 bookings, yet only half of those calls happened and they produced $3,000. Per booking that is $60, against $480 for Organic search and $320 for Email. Paid lost twice, on attendance and on deal size, and the attendance part may be fixable with reminders before anyone cuts the budget. With this few deals, wait until most have had time to close; the lead value calculator turns a close rate and deal size into a value per booking.

In Virling, revenue per channel is on the Channels card and the booking goal count is on the Goals tab. A goal stays with the visit where it happened, while revenue follows your attribution model.

Gaps that remain

  • Hosted cal.com links shared outside your site. No page of yours loaded, so there is no ID; a self-hosted instance on your domain closes this one.
  • Routing to an outside address. Nothing is booked in Cal.com, so no booking webhook fires.
  • Someone else pays. Matching needs the exact same email.
  • Identify sent late. If the payment syncs first, it stays Unattributed.

Frequently asked questions

How do I add UTM parameters to a Cal.com link?

Add them after a question mark, separated by ampersands, such as ?utm_source=newsletter&utm_medium=email&utm_campaign=october-launch. Cal.com saves the five standard tags with the booking without any setup; other names need a hidden booking question.

Where do I see UTM data in Cal.com?

Open the booking details page while logged in. Cal.com shows the tags and hidden answers there only to the hosts of that booking.

Do UTM tags work in a Cal.com embed?

Only if you pass them. Put them in the embed config, or set Cal.config.forwardQueryParams to true, which copies every parameter of the page address, not just the tags.

Can the Virling script run on a self-hosted Cal.com?

Yes, if you add it to the pages of your own instance. On a subdomain of your site, such as book.example.com, the booking page shares the visitor ID cookie with the rest of your site, so it counts as part of the same visit.

Does Virling read my Cal.com bookings?

No. There is no Cal.com integration. Virling gets the visit, the booking goal from your page, the identify event from your webhook receiver, and the payment from your payment provider.

How do I join a Cal.com booking to a Stripe invoice?

Carry the Virling visitor ID into the booking as embed metadata or a hidden question. Your Booking Created webhook receiver then sends it with the email to Virling, and a later invoice paid from that email is credited to the visit.
