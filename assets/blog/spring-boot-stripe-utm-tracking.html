Spring Boot Stripe UTM tracking: Checkout metadata with stripe-java

By Devendra Variya, co-founder of Virling. Published 2026-11-22.

Spring Boot Stripe UTM tracking comes down to one value. Load the Virling script in your Thymeleaf layout or frontend, then read the virling_vid cookie with @CookieValue in the controller that creates the Stripe Checkout Session and pass it as client_reference_id, or as metadata.virling_vid. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each, so you see which channel brought the buyer.

This post covers a Java backend with Spring Boot and stripe-java. The same steps for other stacks are in ASP.NET Core Stripe UTM tracking, Go Stripe UTM tracking and Next.js Stripe UTM tracking. For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Why Stripe Checkout loses your UTM tags

UTM tags live on the landing URL. Stripe Checkout runs on Stripe's domain and only stores what your server passes when it creates the session, so the tags of the visit are gone unless you carry them over. The same thing happens on any redirect that drops the query string, as covered in UTM parameters lost after redirect. Passing one visitor ID instead of the tags keeps earlier visits and untagged ones, such as search and referrals, too.

Step 1: add the script to the Thymeleaf layout

Paste the tag before </head> in the template that every page uses, such as src/main/resources/templates/layout.html or a shared head fragment. If your pages are served by a separate frontend, such as React or Vue, put it in that app's index.html instead. If you self-host, replace app.virling.com with your Virling server.

<!-- src/main/resources/templates/layout.html -->
<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: create the Checkout Session in a controller

Your server receives the cookie with every request from the browser on the same domain. Read it with @CookieValue where you create the session and pass it with setClientReferenceId:

package com.example.billing;

import com.stripe.Stripe;
import com.stripe.exception.StripeException;
import com.stripe.model.checkout.Session;
import com.stripe.param.checkout.SessionCreateParams;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.CookieValue;
import org.springframework.web.bind.annotation.PostMapping;

@Controller
public class CheckoutController {

    public CheckoutController(@Value("${stripe.secret-key}") String secretKey) {
        Stripe.apiKey = secretKey;
    }

    @PostMapping("/checkout")
    public String checkout(
            @CookieValue(name = "virling_vid", required = false) String vid)
            throws StripeException {
        SessionCreateParams.Builder params = SessionCreateParams.builder()
                .setMode(SessionCreateParams.Mode.SUBSCRIPTION)
                .addLineItem(SessionCreateParams.LineItem.builder()
                        .setPrice("price_...")
                        .setQuantity(1L)
                        .build())
                .setSuccessUrl("https://yourdomain.com/thanks");
        if (vid != null && !vid.isEmpty()) {
            params.setClientReferenceId(vid);
        }

        Session session = Session.create(params.build());
        return "redirect:" + session.getUrl();
    }
}

Add com.stripe:stripe-java to your pom.xml or build.gradle, and keep the secret key in an environment variable with stripe.secret-key=${STRIPE_SECRET_KEY} in application.properties, not the key itself. Post to the controller from a plain form in your Thymeleaf page, so the browser follows the redirect to Stripe's domain. With th:action, Spring Security adds its CSRF token to the form for you:

<form method="post" th:action="@{/checkout}">
  <button type="submit">Subscribe</button>
</form>

Using metadata instead

If client_reference_id already holds your own user or order ID, put the visitor ID in the session's metadata. Virling reads either:

if (vid != null && !vid.isEmpty()) {
    params.putMetadata("virling_vid", vid);
}

With a separate frontend

If a React or Vue app on your domain or a subdomain calls the Spring Boot API, the browser sends the virling_vid cookie with the request and the controller above works as is. If the API is on another domain, the cookie is not sent, so read the ID in the browser with window.virling?.vid?.() and send it in the request body. It returns nothing when the script is blocked or not loaded yet, so check the value before using it:

const vid = window.virling?.vid?.() || null;
const res = await fetch("https://api.yourdomain.com/checkout", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ vid }),
});
const { url } = await res.json();
window.location.href = url;

On the server, take vid from a @RequestBody in a @RestController, build the same SessionCreateParams, and return session.getUrl() as JSON instead of a redirect.

The full lookup order, including PaymentIntents you create for Elements, is in the Stripe docs, and the Stripe for SaaS page shows what you get per channel. How to pass the visitor ID with other providers is in link checkout to visits, and the script tag for other frameworks in the framework docs.

Subscriptions and renewals

Only the first payment needs the visitor ID. A renewal takes the attribution of the customer's first payment, so each monthly or yearly charge of the subscription is credited to the same visit, with no code on your side.

Check that it works

Make a test payment from a page that runs the script, wait for the next sync, and open the payments list at /app/yourdomain.com/payments. The payment should show a channel instead of Unattributed. Open it to see its journey. If it still shows Unattributed, check that the page you bought from loads the script, that the controller reads the virling_vid cookie, and that the checkout request goes to the same domain, so the cookie is sent. The full checklist, with a tagged test visit and a Stripe test key, is in test your setup.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Stripe revenue by traffic source.

Frequently asked questions

How do I pass UTM parameters to Stripe Checkout in Spring Boot?

Read the visitor ID with @CookieValue(name = "virling_vid", required = false) in the controller method that creates the Checkout Session and set it with setClientReferenceId on SessionCreateParams. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

How do I add Stripe Checkout metadata in Spring Boot?

Call putMetadata("virling_vid", vid) on the SessionCreateParams builder. Use it when client_reference_id already holds your own user or order ID. Virling reads either metadata.virling_vid or client_reference_id on the session.

Does this work with a React or Vue frontend?

Yes. If the frontend calls the API on your domain or a subdomain, the browser sends the virling_vid cookie and the controller reads it. If the API is on another domain, read the ID in the browser with window.virling?.vid?.() and send it in the request body. The stripe-java code stays the same.

Are subscription renewals attributed?

Yes. A renewal takes the attribution of the customer's first payment, so every monthly or yearly charge is credited to the visit that led to the first one, even though the renewal itself has no visit.

What happens if the cookie is missing?

With required = false, the parameter is null, and the session is created without a visitor ID, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.
