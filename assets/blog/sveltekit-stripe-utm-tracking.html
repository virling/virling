SvelteKit Stripe UTM tracking: tie each payment to its source

By Devendra Variya, co-founder of Virling. Published 2026-11-22.

To see which traffic source each Stripe payment came from in a SvelteKit app, add the Virling script to src/app.html, then read the virling_vid cookie in the form action or +server.ts endpoint that creates the Checkout Session and pass it as client_reference_id. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each. Two files change, and the rest of your checkout stays as it is.

For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Why Stripe Checkout loses your UTM tags

UTM tags live on the landing URL. Stripe Checkout runs on Stripe's domain and only stores what your server passes when it creates the session, so the tags of the visit are gone unless you carry them over. Passing one visitor ID instead of the tags keeps earlier visits and untagged ones, such as search and referrals, too. If the tags never reach your landing page at all, a redirect is usually dropping them; see UTM parameters lost after redirect.

Step 1: add the script to src/app.html

Paste the tag into src/app.html, before %sveltekit.head%. That file is the shell of every page, so the script loads once and client-side navigation is counted on its own. If you self-host, replace app.virling.com with your Virling server.

<!-- src/app.html -->
<head>
  <meta charset="utf-8" />
  <script defer src="https://app.virling.com/v.js"
    data-site="yourdomain.com"></script>
  %sveltekit.head%
</head>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: create the Checkout Session in a form action

Your server receives the virling_vid cookie with every request from the browser, and SvelteKit hands it to you on cookies. Read it in the action that creates the session and pass it as client_reference_id:

// src/routes/pricing/+page.server.ts
import { redirect } from "@sveltejs/kit";
import Stripe from "stripe";
import { STRIPE_SECRET_KEY } from "$env/static/private";
import type { Actions } from "./$types";

const stripe = new Stripe(STRIPE_SECRET_KEY);

export const actions = {
  checkout: async ({ cookies }) => {
    const session = await stripe.checkout.sessions.create({
      client_reference_id: cookies.get("virling_vid"),
      line_items: [{ price: "price_...", quantity: 1 }],
      mode: "subscription",
      success_url: "https://yourdomain.com/thanks",
    });
    redirect(303, session.url!);
  },
} satisfies Actions;

A plain form on the same page posts to it, and the browser sends the cookie along:

<!-- src/routes/pricing/+page.svelte -->
<form method="POST" action="?/checkout">
  <button type="submit">Buy</button>
</form>

Or in a +server.ts endpoint, with metadata

If several pages share one checkout, use an endpoint instead. If client_reference_id already holds your own user or cart ID, put the visitor ID in the session's metadata.virling_vid. Virling reads either:

// src/routes/api/checkout/+server.ts
import { redirect } from "@sveltejs/kit";
import Stripe from "stripe";
import { STRIPE_SECRET_KEY } from "$env/static/private";
import type { RequestHandler } from "./$types";

const stripe = new Stripe(STRIPE_SECRET_KEY);

export const POST: RequestHandler = async ({ cookies }) => {
  const vid = cookies.get("virling_vid");
  const session = await stripe.checkout.sessions.create({
    // client_reference_id stays free for your own ID
    metadata: vid ? { virling_vid: vid } : {},
    line_items: [{ price: "price_...", quantity: 1 }],
    mode: "subscription",
    success_url: "https://yourdomain.com/thanks",
  });
  redirect(303, session.url!);
};

Post to it from any page with <form method="POST" action="/api/checkout">. The full lookup order, including PaymentIntents you create for Elements, is in the Stripe docs and on the Stripe integration page. The checkout snippet generator writes the same call for other providers.

Check that it works

Make a test payment from a page that runs the script, wait for the next sync, and open the payments list at /app/yourdomain.com/payments. The payment should show a channel instead of Unattributed. Open it to see its journey. If it still shows Unattributed, check that the page you bought from loads the script and that the form posts to your own domain, so the cookie is sent.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Stripe revenue by traffic source, and the SaaS page shows what you get per channel. On Next.js, see Next.js Stripe Checkout UTM tracking.

Frequently asked questions

How do I pass UTM parameters to a Stripe Checkout Session in SvelteKit?

Read the visitor ID from the virling_vid cookie with cookies.get in a form action or a +server.ts endpoint, and pass it as client_reference_id when you create the session. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

How do I read the virling_vid cookie in SvelteKit?

Form actions, +server.ts handlers and server load functions all receive a cookies object on the request event, so cookies.get("virling_vid") returns the ID. It is a first-party cookie on your domain, so the browser sends it with every request to your app.

Should I use client_reference_id or metadata.virling_vid?

Use client_reference_id unless it already holds your own user or cart ID. In that case put the visitor ID in the session's metadata.virling_vid. Virling reads either.

What happens if the cookie is missing?

The session is created without a visitor ID, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.

Do Stripe Payment Links in a SvelteKit app need code?

No. Use a normal link to buy.stripe.com on a page that runs the script. The script adds client_reference_id to the link when the page loads and again on click, unless the link already has one.

Is client-side navigation in SvelteKit counted?

Yes. With the script tag in src/app.html it loads once for the whole app, and page changes made by the SvelteKit router are counted on their own.
