Stripe Payment Link UTM tracking: see which source sold

By Devendra Variya, co-founder of Virling. Published 2026-11-18.

To see which channel brought each Stripe Payment Link sale, the payment has to carry an ID that points back to the visit. Stripe does not keep the UTM tags or the referrer of the page that sent the buyer to buy.stripe.com, so on its own every sale looks the same. Put a visitor ID in the link's client_reference_id, record the visit's source on your side, and join the two. With the Virling script on the page, that takes no code: it tags every Payment Link, and each sale shows its channel.

What Stripe keeps and drops on a Payment Link

  • UTM tags on your page: dropped. They are on your landing URL, not on the Payment Link, so Stripe never sees them. Payment Links accept utm_source, utm_medium, utm_campaign, utm_content and utm_term only when they are in the link URL itself, and Stripe's docs describe passing them on to your redirect URL after payment (Stripe Payment Link URL parameters). Tags you hard-code on a link describe the link, not the visit.
  • Referrer: dropped. A Checkout Session has no field for the page or site that sent the buyer, so the payment does not say where the visit came from.
  • client_reference_id: kept. Add it to the link URL, with letters, digits, dashes and underscores up to 200 characters, and Stripe copies it onto the Checkout Session. It arrives in the checkout.session.completed event. Invalid values are dropped without an error.

So client_reference_id is the one place a Payment Link can carry the source of a sale. One short visitor ID is enough, because the visits behind it, with their UTM tags and referrers, live in your analytics. What else the field can hold, and how to read it back, is in Stripe client_reference_id.

Track the source of a Payment Link with no code

Step 1: add the script to the pages that hold the link. Put one tag in the <head>. The app shows the exact tag for your site:

<script defer src="https://app.virling.com/v.js" data-site="yourdomain.com"></script>

The script records the referrer and UTM tags of every visit against a visitor ID in the first-party virling_vid cookie.

Step 2: leave your Payment Links as they are. A plain link is enough:

<a href="https://buy.stripe.com/abc123">Buy now</a>

The script adds client_reference_id with the visitor ID to every buy.stripe.com link when the page loads and again on click, and never replaces a value that is already there.

Step 3: connect Stripe with a restricted key. Create a restricted key with Read on Charges, Checkout Sessions, Customers, Events, Invoices, Subscriptions and PaymentIntents, and paste it into Virling. Virling reads the visitor ID from the Checkout Session behind each charge and credits the payment to the visit, under the attribution model you pick: last non-direct by default, or first touch or last touch.

Step 4: test one sale. Use a test-mode key and a test Payment Link, visit your page from a tagged URL such as ?utm_source=test, and pay with a Stripe test card. Wait a minute for the next sync, and the payment shows the test source instead of Unattributed.

Each step is in the Stripe docs, and the full setup is on the Stripe integration page.

When a Payment Link sale has no source

  • The link was opened off your site. Links in emails, QR codes, social posts or other sites never pass through a page with the script, so they carry no visitor ID and show as Unattributed. Send people to a page on your site instead, and let them click through from there.
  • The link is on a custom domain. The script only tags links on buy.stripe.com. For a Payment Link on your own checkout domain, add the ID yourself from window.virling.vid().
  • The button is not a link. The link must be a normal <a href>. A button that opens the URL from JavaScript is not tagged.
  • Cookieless mode. With data-cookieless there is no visitor ID to pass, so new payments are Unattributed.

If you create Checkout Sessions on your server instead of using Payment Links, you pass the ID yourself; see Stripe Checkout UTM parameters. For payment forms on your own page, see Stripe embedded checkout UTM tracking and Stripe Elements UTM tracking. How the join works, step by step, is in how to track Stripe revenue by traffic source.

Frequently asked questions

Does a Stripe Payment Link keep the UTM parameters from my page?

No. The tags are on your page URL, not on the buy.stripe.com link, so Stripe never sees them. Stripe only reads utm_source, utm_medium, utm_campaign, utm_content and utm_term when they are in the Payment Link URL itself, and passes them on to your redirect URL after payment.

Can I see the referrer of a Payment Link sale in Stripe?

No. A Checkout Session has no field for the page or site that sent the buyer, so the payment does not say where the visit came from. You need your own record of the visit and an ID that joins it to the payment.

Do I need code to track the source of a Payment Link?

Not with Virling. Put the script on the pages that hold the link and connect Stripe with a restricted key. The script adds client_reference_id to every buy.stripe.com link, and Virling matches the payment to the visit.

What if my Payment Link already has a client_reference_id?

The script never replaces a value that is already there, so your own ID stays. Virling then has no visitor ID for that sale, and it shows as Unattributed.

Why does a Payment Link sale show as Unattributed?

The buyer did not reach the link from a page running the script: they opened it from an email, a QR code, a social post or another site. It also happens when the link is on a custom domain instead of buy.stripe.com, when it is opened by a button without an a href, or when the script runs in cookieless mode.
