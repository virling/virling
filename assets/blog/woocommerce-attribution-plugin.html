WooCommerce attribution plugin: a buyer's checklist

By Devendra Variya, co-founder of Virling. Published 2026-11-24.

A WooCommerce attribution plugin links each order to the visit that brought the buyer, so you see revenue per channel and campaign. Before you pick one, check eight things: that it saves its data in the order meta, works with the block checkout, subtracts refunds, keeps the channel on subscription renewals, survives page caching, is honest about ad blockers, lets you own the data, and adds little weight to each page. WooCommerce's built-in order attribution may already be enough. Below is what it does, what to ask for each point, and where Virling meets it or falls short.

What WooCommerce already does

Order attribution is part of WooCommerce. Turn it on or off under WooCommerce, Settings, Advanced, Features. With each order it saves the referring site, the UTM source, medium, campaign, content and term, the device type and the session's page views. You see them in the Order attribution box on the order, and the orders list has an Origin column.

It uses last-click attribution. A session lasts 30 minutes by default, and WooCommerce says it cannot be used to track visitors across sessions. A UTM or organic visit always overrides an earlier source, and a direct visit never does. Orders placed while it is off get no attribution data. Source: WooCommerce order attribution tracking.

If most of your buyers click and buy in one visit, that may be all you need. Where the values show up and why they go missing is in WooCommerce UTM tracking, and orders with no source at all are covered in why WooCommerce order attribution says Unknown.

1. Order meta

What to check: whether the source, or an ID that leads to it, is saved in the order's meta data when the order is placed. Data on the order can be checked and exported, and does not depend on the thank-you page loading.

Virling: a short PHP snippet saves the visitor ID on each new order as virling_vid, and Virling joins it to that visitor's earlier visits. Open any order on the Payments page to see them. If an order has no visitor ID, Virling compares its billing email with emails your site sent as identify events, kept only as salted hashes. An exact match credits that visitor and shows Matched by email. Falls short: you add the snippet yourself, in functions.php or a snippets plugin, and Virling does not read the source values WooCommerce's own attribution saves on an order.

2. Block checkout

What to check: WooCommerce has a classic checkout and a block checkout, and code written for one may not run in the other. Place a test order through every checkout path you offer, express buttons included.

Virling: the snippet covers the classic and the block checkout. Copy it from the WooCommerce integration page.

3. Refunds

What to check: whether a refund lowers the revenue of the channel that brought the order. In a made-up example, a campaign with $4,000 of orders and $1,500 of refunds brought $2,500, and a report that stops at the order hides that.

Virling: full and partial refunds lower the revenue of the order's channel. Orders from the last 60 days are read again every 6 hours, so later refunds show up. Falls short: a refund made on an order older than that is not picked up.

4. Subscriptions

What to check: a renewal has no visit of its own, so ask which channel it is credited to, and whether you can compare channels by the subscribers who keep paying.

Virling: with WooCommerce Subscriptions, a renewal order keeps the channel of the customer's first payment, and subscription status is read once an hour; see WooCommerce Subscriptions attribution. Falls short: the first run imports 90 days of orders, so renewals of older subscriptions are usually Unattributed. Guest orders have no customer ID, so each counts as its own customer, and without WooCommerce Subscriptions retention uses payment recency.

5. Page caching

What to check: whether the source is read in the browser or written into the page by PHP. A cached page is the same for every visitor, so anything PHP writes into it can be wrong for the next one.

Virling: the script reads UTM tags and creates the visitor ID in the browser, so a cached page or a CDN copy works for everyone. Falls short: combining, inlining, delaying or locally hosting v.js can stop or delay it, so exclude it from those settings. The order snippet runs on your server, so keep cart, checkout and account pages out of the cache. The settings are in page caching and CDNs.

6. Ad blockers

What to check: what still gets counted when the script is blocked. Be careful with any promise to see every visitor.

Virling: orders come from your store's REST API, so a blocked visitor's order still counts toward revenue, as Unattributed. Serving the script and /api/event from your own domain through a proxy helps. Falls short: a visit that was blocked cannot be recovered, and a tested proxy setup for each platform is not available yet. The visitor ID is a first-party cookie in one browser, so cookieless mode, declined consent, cleared cookies or a second device also break the link.

7. Data ownership

What to check: where visits and orders are stored, what access it needs to your store, and what you keep if you stop paying. WooCommerce's own attribution saves its data in your store.

Virling: it is open source under AGPL and free to self-host with every feature, so visits and orders stay on your own server. The hosted version starts at $19 a month after a 14-day free trial; see pricing. It connects with a REST API key set to Read, so it cannot change or refund anything. Falls short: it runs outside WordPress, so its reports are not in wp-admin and self-hosting means running a server for it.

8. Page weight

What to check: load a product page with and without the plugin, and compare the scripts, requests and bytes in the browser's network tab. Reports that run on your store's database also use the same server as checkout.

Virling: one deferred script of about 2 KB compressed, which sends events to your Virling server. Reports run there, not on your store. Falls short: Virling asks your store's REST API for new orders every minute, and the store must be reachable over https with pretty permalinks on.

What Virling does not do

  • It does not show reports inside wp-admin
  • It does not import ad spend, so return on ad spend needs your ad platform's numbers
  • It does not read coupon codes; orders are credited by visit
  • It does not read the source values WooCommerce saves on an order; an order needs virling_vid or an email match
  • Linear and position-based models are not available yet; the choices are last non-direct (the default), first touch and last touch
  • The first import goes back 90 days, and orders placed before the snippet was added are mostly Unattributed

Frequently asked questions

Do I need a WooCommerce attribution plugin?

Not always. WooCommerce has order attribution built in, which shows the last source of each order within a session. Look for something more when buyers come back days later, when you want refunds and subscription renewals counted by channel, or when you want to see every visit before an order.

What should I look for in a WooCommerce attribution plugin?

Check that it saves the source or a visitor ID in the order meta, works with the block checkout, subtracts refunds, keeps the channel on subscription renewals, survives page caching, is honest about ad blockers, lets you own the data and adds little to each page.

Does WooCommerce have built-in attribution?

Yes. Order attribution is turned on or off under WooCommerce, Settings, Advanced, Features. It uses last-click attribution, saves the referrer, UTM tags, device type and session page views with the order, and shows an Origin column in the orders list.

Is Virling a WooCommerce plugin?

Not in the usual sense. Reports are in Virling, not in wp-admin. You add the Virling script, by hand or with its WordPress plugin, add a short PHP snippet that saves the visitor ID on each order, and connect a read-only REST API key.

Does page caching break WooCommerce attribution?

Caching the HTML does not break Virling, because the script sets the visitor ID in the browser. Combining, inlining or delaying the script can, and so can caching checkout, so exclude v.js from those settings and keep cart, checkout and account pages out of the cache.
