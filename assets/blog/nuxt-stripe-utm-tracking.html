Nuxt Stripe UTM tracking: tie each payment to its source

By Devendra Variya, co-founder of Virling. Published 2026-11-22, updated 2026-11-25.

To see which traffic source each Stripe payment came from in a Nuxt app, add the Virling script to app.head in nuxt.config.ts, then read the virling_vid cookie in the server/api route that creates the Checkout Session and pass it as client_reference_id. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each. Two files change, and the rest of your checkout stays as it is.

This post covers Nuxt 3. Using Polar instead? See Nuxt Polar UTM tracking. For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Why Stripe Checkout loses your UTM tags

UTM tags live on the landing URL. Stripe Checkout runs on Stripe's domain and only stores what your server passes when it creates the session, so the tags of the visit are gone unless you carry them over. Passing one visitor ID instead of the tags keeps earlier visits and untagged ones, such as search and referrals, too. If the tags never reach your landing page at all, a redirect is usually dropping them; see UTM parameters lost after redirect.

Step 1: add the script to nuxt.config.ts

Add the tag to the app head in the Nuxt config. Nuxt renders it into the HTML of every page, and route changes are tracked through history.pushState, so client-side navigation is counted. If you self-host, replace app.virling.com with your Virling server.

// nuxt.config.ts
export default defineNuxtConfig({
  app: {
    head: {
      script: [
        { src: "https://app.virling.com/v.js", defer: true,
          "data-site": "yourdomain.com" },
      ],
    },
  },
  runtimeConfig: {
    stripeSecretKey: "", // set NUXT_STRIPE_SECRET_KEY
  },
});

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it. The runtimeConfig entry keeps your Stripe secret key on the server.

Step 2: create the Checkout Session in a server/api route

Your server receives the virling_vid cookie with every request from the browser, and getCookie reads it from the event. Read it in the route that creates the session and pass it as client_reference_id:

// server/api/checkout.post.ts
import Stripe from "stripe";

export default defineEventHandler(async (event) => {
  const stripe = new Stripe(useRuntimeConfig(event).stripeSecretKey);
  const session = await stripe.checkout.sessions.create({
    client_reference_id: getCookie(event, "virling_vid"),
    line_items: [{ price: "price_...", quantity: 1 }],
    mode: "subscription",
    success_url: "https://yourdomain.com/thanks",
  });
  return sendRedirect(event, session.url!, 303);
});

A plain form posts to it, and the browser sends the cookie along:

<!-- pages/pricing.vue -->
<template>
  <form method="POST" action="/api/checkout">
    <button type="submit">Buy</button>
  </form>
</template>

Or return the URL to the page, with metadata

If you would rather start checkout from a click handler, return the session URL as JSON and navigate to it. If client_reference_id already holds your own user or cart ID, put the visitor ID in the session's metadata.virling_vid instead. Virling reads either:

// server/api/checkout-url.post.ts
import Stripe from "stripe";

export default defineEventHandler(async (event) => {
  const stripe = new Stripe(useRuntimeConfig(event).stripeSecretKey);
  const vid = getCookie(event, "virling_vid");
  const session = await stripe.checkout.sessions.create({
    // client_reference_id stays free for your own ID
    metadata: vid ? { virling_vid: vid } : {},
    line_items: [{ price: "price_...", quantity: 1 }],
    mode: "subscription",
    success_url: "https://yourdomain.com/thanks",
  });
  return { url: session.url };
});

Call it from the page. $fetch runs in the browser here, so the cookie goes with the request:

<!-- pages/pricing.vue -->
<script setup lang="ts">
async function buy() {
  const { url } = await $fetch("/api/checkout-url", { method: "POST" });
  await navigateTo(url!, { external: true });
}
</script>

<template>
  <button type="button" @click="buy">Buy</button>
</template>

The full lookup order, including PaymentIntents you create for Elements, is in the Stripe docs and on the Stripe integration page. The checkout snippet generator writes the same call for other providers.

Prerendered, server rendered and cached pages

The script runs in the browser, so it works the same on every kind of page: it creates the cookie and reads the UTM tags from the address there, never from your HTML. What changes is when your own code runs, and so whether it can see the cookie.

PageWhat changesWhere the cookie is read
Prerendered, with routeRules or nuxt generateThe HTML is made once at build time, and useCookie finds nothing thereIn the server/api route. A form on the prerendered page posts to it
Server rendered, the defaultEach request renders the page, and useCookie can read the cookie once the browser has itIn the server/api route
Browser only, with ssr: falseThe server sends a shell, and app.head puts the tag in itIn the server/api route, which still runs on the server
Cached, with swr or isrOne copy of the HTML serves many visitors. It is not rendered for this visitor, so the page itself never sees the IDIn a POST route. Nitro caches GET and HEAD only
Static site, with nuxt generate for the whole appThere is no server, so no server/api routesBy the script in the browser, which adds the ID to Payment Links

One rule covers every row: read the cookie in the request that creates the session, not when the page is rendered to be viewed. On a first visit the server renders the page before the script has set the cookie, and in a prerendered or cached page there is no cookie of this visitor at all. The same goes for a hidden field filled in while the page renders: from a shared copy, every buyer would send the same value.

Vue Router navigates with the History API, so route changes are counted on their own. Each change of path or query is one pageview, and a change of only the #hash is none. Later routes carry no referrer, so they stay in the channel of the landing page. The cookie stays in the browser through all of it, so it is sent from whichever page the buyer presses Buy on. Payment Links that appear after a route change get the visitor ID when they are clicked.

Check that it works

Run one test payment through the whole path, from your own dev server:

  1. In Virling, connect a restricted Stripe key that starts with rk_test_. Your app keeps its own test secret key in NUXT_STRIPE_SECRET_KEY, for example in .env, and uses a price created in test mode.
  2. Add the line 127.0.0.1 dev.yourdomain.com to your hosts file and start the dev server on that name with npm run dev -- --host dev.yourdomain.com. The script does nothing on localhost, and Virling keeps a visit only when the page's host is your site's domain or one of its subdomains.
  3. Open a private window and visit the dev server through a tagged link, such as http://dev.yourdomain.com:3000/?utm_source=test&utm_medium=email. Run window.virling.vid() in the browser console and note the ID. Click through to the pricing page, so a client-side navigation is part of the test.
  4. In the same window, press Buy. Pay with the card 4242 4242 4242 4242, any future date and any three-digit CVC (Stripe testing).
  5. Check the Checkout Session with the log line below, in the terminal that runs the dev server. client_reference_id, or virling_vid in the session's metadata if you use that, should be the ID from step 3. The charge and PaymentIntent do not need it: Stripe does not copy session metadata to them.
  6. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed. Open it to see its journey.

For step 5, add this right after stripe.checkout.sessions.create() and remove it afterwards:

console.log(session.id, session.client_reference_id, session.metadata);

The dev server renders prerendered pages on request and has no CDN in front of it, so it cannot show a page that was baked or cached wrongly. Repeat steps 3 to 6 once on a deployed subdomain, such as staging.yourdomain.com. Go straight there if your browser insists on https for the dev address, as it does for domains that end in .dev or .app.

If your code passes customer, use a new customer for each test: a later payment by the same customer is a renewal and keeps the first payment's channel. A site has one Stripe connection, and test payments stay in your reports after you replace the key with a live one. If you want only real payments in your numbers, make one small live payment instead and refund it. If a step fails, see test your setup.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Stripe revenue by traffic source, and the SaaS page shows what you get per channel. On other frameworks, see Next.js, SvelteKit and Astro. For a Vue app without Nuxt, see Vue Stripe UTM tracking.

Frequently asked questions

How do I pass UTM parameters to a Stripe Checkout Session in Nuxt?

Read the visitor ID from the virling_vid cookie with getCookie in a server/api route, and pass it as client_reference_id when you create the session. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

How do I read the virling_vid cookie in a Nuxt server route?

Call getCookie(event, "virling_vid") inside defineEventHandler. Both are auto-imported in the server directory. It is a first-party cookie on your domain, so the browser sends it with every request to your app, including $fetch calls from the page.

Should I use client_reference_id or metadata.virling_vid?

Use client_reference_id unless it already holds your own user or cart ID. In that case put the visitor ID in the session's metadata.virling_vid. Virling reads either.

What happens if the cookie is missing?

The session is created without a visitor ID, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.

Do Stripe Payment Links in a Nuxt app need code?

No. Use a normal link to buy.stripe.com on a page that runs the script. The script adds client_reference_id to the link when the page loads and again on click, unless the link already has one.

Is client-side navigation in Nuxt counted?

Yes. With the script in app.head of nuxt.config.ts it is rendered into every page, and route changes made by the Nuxt router are tracked through history.pushState.
