Flask Stripe UTM tracking: Checkout in Python

By Devendra Variya, co-founder of Virling. Published 2026-11-22, updated 2026-11-25.

Flask Stripe UTM tracking comes down to one value. Load the Virling script in your base Jinja template, then read the virling_vid cookie with request.cookies.get("virling_vid") in the route that creates the Stripe Checkout Session and pass it as client_reference_id, or as metadata.virling_vid if that field is taken. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each, so you see which traffic source each payment came from.

This post covers Flask with the stripe Python library. The same steps for other stacks are in Django Stripe UTM tracking and Next.js Stripe UTM tracking. For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Step 1: add the script to the base template

Paste the tag before </head> in the template every page extends, usually templates/base.html. If you self-host, replace app.virling.com with your Virling server.

<!-- templates/base.html -->
<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: create the Checkout Session in a route

Your server receives the cookie with every request from the browser. The script sets it as a plain cookie, separate from Flask's signed session, so read it from request.cookies. With the stripe Python library, read it where you create the session and pass it as client_reference_id:

# app.py
import os

import stripe
from flask import Flask, redirect, request

app = Flask(__name__)
stripe.api_key = os.environ["STRIPE_SECRET_KEY"]


@app.post("/checkout")
def checkout():
    params = {
        "line_items": [{"price": "price_...", "quantity": 1}],
        "mode": "subscription",
        "success_url": "https://yourdomain.com/thanks",
    }
    vid = request.cookies.get("virling_vid")
    if vid:
        params["client_reference_id"] = vid

    checkout_session = stripe.checkout.Session.create(**params)
    return redirect(checkout_session.url, code=303)

Post to it from a template form. The browser sends the cookie along:

<form action="{{ url_for('checkout') }}" method="post">
  <button type="submit">Subscribe</button>
</form>

If you use Flask-WTF's CSRFProtect, add <input type="hidden" name="csrf_token" value="{{ csrf_token() }}"> inside the form. For other payment providers, the checkout snippet generator gives the matching code.

When client_reference_id is taken

If you already use client_reference_id for your own user or order ID, put the visitor ID in the session's metadata instead. Virling reads either:

    vid = request.cookies.get("virling_vid")
    if vid:
        params["metadata"] = {"virling_vid": vid}

If you create your own PaymentIntent for Elements instead of a Checkout Session, set the same metadata on stripe.PaymentIntent.create(). The full lookup order is in the Stripe docs and in link checkout to visits, and the Stripe integration page shows what Virling imports.

Optional: keep the UTM tags in Stripe too

Virling does not need the tags on the payment, since the visitor ID points to every visit. If you also want them readable in the Stripe Dashboard, save them from the landing URL into Flask's session and copy them into metadata. Stripe does not copy session metadata to the Subscription, so set subscription_data.metadata as well, or payment_intent_data.metadata for mode="payment":

from flask import session

app.secret_key = os.environ["FLASK_SECRET_KEY"]
UTM_KEYS = ("utm_source", "utm_medium", "utm_campaign", "utm_content", "utm_term")


@app.before_request
def keep_utm():
    tags = {k: request.args[k] for k in UTM_KEYS if request.args.get(k)}
    if tags:
        session["utm"] = tags

# in checkout(), before stripe.checkout.Session.create(**params):
    utm = session.get("utm", {})
    if utm:
        params["metadata"] = {**params.get("metadata", {}), **utm}
        params["subscription_data"] = {"metadata": utm}

These tags record one visit, the last tagged one. Keep passing the visitor ID: it is what ties the payment to the whole path.

Subscriptions and renewals

Only the first payment needs the visitor ID. A renewal takes the attribution of the customer's first payment, so each monthly or yearly charge of the subscription is credited to the same visit, with no code on your side. Plan changes count as renewals too.

Check that it works

Run one tagged visit and one test-mode checkout through the whole path:

  1. In Virling, connect a restricted Stripe key that starts with rk_test_. Your app keeps its own test secret key in STRIPE_SECRET_KEY and uses a price created in test mode.
  2. Run the app in test mode on your domain or a subdomain of it, such as staging.yourdomain.com. Visits on localhost are not recorded for your site.
  3. Open a private window and visit a page that runs the script through a tagged link, such as https://staging.yourdomain.com/?utm_source=test&utm_medium=email. Run window.virling.vid() in the browser console and note the ID.
  4. In the same window, press the Subscribe button, so the form posts to the checkout route. Pay with the card 4242 4242 4242 4242, any future date and any three-digit CVC (Stripe testing).
  5. In Stripe, open the Events tab in Workbench and the checkout.session.completed event of your payment. client_reference_id, or virling_vid in the session's metadata if you use that, should be the ID from step 3. The log line below shows the same. The charge and PaymentIntent do not need it: Stripe does not copy session metadata to them.
  6. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed. Open it: Visitor under Details is the ID from step 3, and the journey starts at your tagged visit.

For the log line in step 5, add this right after stripe.checkout.Session.create() and remove it afterwards:

print(checkout_session.id, checkout_session.client_reference_id, checkout_session.metadata)

If your code sets customer, use a new customer for each test: a later payment by the same customer is a renewal and keeps the first payment's channel. A site has one Stripe connection, and test payments stay in your reports after you replace the key with a live one. If you want only real payments in your numbers, make one small live payment instead and refund it. If a step fails, see test your setup.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Stripe revenue by traffic source, and the SaaS page shows what you get per channel.

Open an Unattributed payment and look for Visitor under Details. If there is none, checkout did not carry the ID.

The webhook row is about your own endpoint, for example one that unlocks an account. Virling reads Stripe with the restricted key and needs no webhook in your app. Checkout requests have to reach your server with their cookies, so keep them out of any cache and do not let a proxy or CDN remove the Cookie header, as in page caching and CDNs. A payment made before a fix usually stays Unattributed, so make a new one to check.

Frequently asked questions

How do I pass UTM parameters to Stripe Checkout in Flask?

Read the visitor ID with request.cookies.get("virling_vid") in the route that creates the Checkout Session and pass it as client_reference_id. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

How do I put the visitor ID in Stripe Checkout metadata with Python?

Add metadata={"virling_vid": vid} to stripe.checkout.Session.create(). Use it when client_reference_id already holds your own user or order ID. Virling reads metadata.virling_vid or client_reference_id on the session.

Is virling_vid stored in the Flask session?

No. The script sets virling_vid as its own plain cookie in the browser, outside Flask's signed session cookie. Read it with request.cookies.get("virling_vid").

Are subscription renewals attributed?

Yes. A renewal takes the attribution of the customer's first payment, so every monthly or yearly charge is credited to the visit that led to the first one, even though the renewal itself has no visit.

What happens if the cookie is missing?

The session is created without a visitor ID, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.

Do Stripe Payment Links in a Flask app need code?

No. Use a normal link to buy.stripe.com on a page that runs the script. The script adds client_reference_id to the link when the page loads and again on click, unless the link already has one.

Does a Flask app need a Stripe webhook for this?

No. Virling reads charges from Stripe with a restricted key and finds the visitor ID on the Checkout Session. Keep your own webhook if your app needs one, for example to unlock an account, and pass request.get_data() to stripe.Webhook.construct_event() so the signature matches.
