How to track WooCommerce revenue by traffic source

By Devendra Variya, co-founder of Virling. Published 2026-11-16.

To track WooCommerce revenue by traffic source, give each visitor an ID, save it on the order when checkout creates it, and join each order back to the visits that came before it. WooCommerce knows who ordered and how much. Its built-in order attribution can show an origin, but it relies on short-lived cookies and a script that has to run on every page, and many orders end up as Unknown.

Step 1: set a visitor ID

Your analytics script sets one first-party ID per visitor and remembers the first source: referrer, UTM tags or direct. Put the script in your theme so it runs on every page of the store, including the product, cart and checkout pages, and on any blog or landing page that links to the store. Because the ID lives in a cookie on your own domain, WordPress receives it with every request from the browser, so the server can read it at checkout without any extra JavaScript.

Step 2: save the ID on the order

WooCommerce orders carry meta data, so the ID can travel with the order. Hook into order creation and copy the ID from the cookie into the order's meta. WooCommerce has two checkouts, the classic shortcode checkout and the newer block checkout, and each fires its own hook when it builds the order, so use both:

add_action('woocommerce_checkout_create_order', 'virling_vid_on_order');
add_action('woocommerce_store_api_checkout_update_order_from_request', 'virling_vid_on_order');
function virling_vid_on_order($order) {
  $vid = $_COOKIE['virling_vid'] ?? '';
  if (preg_match('/^[A-Za-z0-9-]{8,64}$/', $vid)) $order->update_meta_data('virling_vid', $vid);
}

Put it in your theme's functions.php or in a snippets plugin. A snippets plugin is often the safer home, because a theme update can replace functions.php. The pattern check means only a well-formed ID is saved, and an order placed without the cookie simply gets no ID.

Step 3: read orders from the REST API

In WordPress, open WooCommerce, Settings, Advanced, REST API, and add a key with Read permissions. A read-only key is all an analytics tool needs: it reads orders, refunds and subscriptions, and never changes them. The store has to answer over https, with pretty permalinks on, so that /wp-json/wc/v3/ works.

Decide which order statuses count as paid. Processing and completed orders have been paid. Failed and cancelled orders have not. Pending and on-hold orders are not paid yet, so wait for them to move on instead of counting or dropping them straight away.

Step 4: join orders to visits

Match each order's virling_vid to that visitor's earlier visits and credit one of them with a rule you keep fixed (see first touch or last touch). Orders with no ID have no visit to join, so they show as Unattributed. They still count toward revenue, so your totals stay right even when the channel is missing.

WooCommerce allows guest checkout. Guest orders have no customer ID, so each one counts as its own customer. That is worth knowing before you read a customers column next to a revenue column.

Step 5: handle refunds and renewals

Two things change the numbers after the first order. Refunds lower an order's revenue, and they can arrive weeks after the sale, so read recent orders again from time to time to catch them. Otherwise a channel that looks good on day one keeps looking good after its buyers asked for their money back.

If you sell subscriptions with WooCommerce Subscriptions, each renewal is a new order created without a store visit, so it carries no visitor ID of its own. Mark renewal orders as renewals and give them the channel of the customer's first payment, or they will pile up as Unattributed and the channel that won the customer will look smaller than it is.

Step 6: report revenue per channel

Group the joined orders by channel and divide by visitors to get revenue per visitor. That is the table that tells you where to spend time and ad budget: a channel with fewer visitors can still bring more revenue per visitor than a busy one.

Checkout on another domain, a subdomain or a second site? See cross-domain checkout attribution.

What goes wrong

  • Hooking only the classic checkout, so orders from the block checkout arrive with no visitor ID
  • Losing the snippet in a theme update because it lived in a theme you do not control
  • Orders created in the admin, through the REST API or by import, which have no web visit and so no visitor ID
  • Counting pending and on-hold orders as revenue before they are paid
  • Ignoring refunds, which overstates a channel

Frequently asked questions

Can WooCommerce show which traffic source an order came from?

Partly. WooCommerce order attribution shows an origin for some orders, and the rest show as Unknown. For a view you control, save a visitor ID on each order and join it to that visitor's earlier visits in your analytics.

Where does the visitor ID go in WooCommerce?

In the order's meta data, under virling_vid. A short snippet in your theme's functions.php, or in a snippets plugin, copies it from the virling_vid cookie when the order is created, in the classic and the block checkout.

Which channel do WooCommerce subscription renewals get?

With WooCommerce Subscriptions, a renewal order is marked as a renewal and keeps the channel of the customer's first payment.

What kind of REST API key does Virling need?

A WooCommerce REST API key with Read permissions. Virling only reads orders, refunds and subscriptions, so it never needs write access.
