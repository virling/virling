Laravel Paddle UTM tracking: Cashier Paddle checkout

By Devendra Variya, co-founder of Virling. Published 2026-11-23, updated 2026-11-25.

Laravel Paddle UTM tracking comes down to one value. Load the Virling script in your Blade layout, leave the virling_vid cookie out of Laravel's cookie encryption, then read it with $request->cookie('virling_vid') in the controller that builds the Cashier Paddle checkout and add it with customData(['virling_vid' => $vid]). Paddle stores it in the transaction's custom_data, and Virling joins the payment to every visit behind that visitor ID, with the UTM tags of each.

This post covers Laravel with Cashier Paddle for Paddle Billing, and with the Paddle API directly. The same steps for other stacks are in Next.js Paddle UTM tracking and Rails Paddle UTM tracking, and with other providers in Laravel Stripe UTM tracking and Laravel LemonSqueezy UTM tracking. For hosted checkout and where the values show up in Paddle, see the general guide to Paddle checkout UTM parameters.

Why Paddle checkout loses your UTM tags

UTM tags live on the landing URL. Paddle only stores what you pass when checkout opens, and by then the visitor is usually a few pages past the landing page. Passing one visitor ID instead of the tags keeps earlier visits and untagged ones, such as search and referrals, too.

Step 1: add the script to the Blade layout

Paste the tag before </head> in the layout every page extends, usually resources/views/layouts/app.blade.php, next to Cashier's @paddleJS directive. If you self-host, replace app.virling.com with your Virling server.

<!-- resources/views/layouts/app.blade.php -->
<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>
@paddleJS

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: leave the cookie out of encryption

Laravel encrypts cookies by default, and $request->cookie() returns nothing for a cookie it did not set itself. The script sets virling_vid in the browser, so exclude it. In Laravel 11 and later, in bootstrap/app.php:

->withMiddleware(function (Middleware $middleware) {
    $middleware->encryptCookies(except: ['virling_vid']);
})

In older versions, add it to $except in app/Http/Middleware/EncryptCookies.php:

protected $except = [
    'virling_vid',
];

Step 3: add the visitor ID to the Cashier checkout

Cashier Paddle builds the checkout on the server and hands it to Paddle.js in the browser. Read the cookie in the controller and pass it with customData():

// app/Http/Controllers/BillingController.php
namespace App\Http\Controllers;

use Illuminate\Http\Request;

class BillingController extends Controller
{
    public function show(Request $request)
    {
        $checkout = $request->user()
            ->subscribe('pri_...', 'default')
            ->customData(['virling_vid' => $request->cookie('virling_vid')])
            ->returnTo(route('dashboard'));

        return view('billing', ['checkout' => $checkout]);
    }
}

Then render Cashier's checkout button in the Blade view. Paddle saves the custom data on the transaction when the buyer pays:

<!-- resources/views/billing.blade.php -->
<x-paddle-button :checkout="$checkout">
    Subscribe
</x-paddle-button>

For a one-off purchase, $request->user()->checkout('pri_...') returns the same checkout object, so customData() works there too. The inline <x-paddle-checkout> component takes the same $checkout.

Or create the transaction with the Paddle API

If your server creates the transaction itself, set custom_data on it and open checkout with its ID:

use Illuminate\Http\Request;
use Illuminate\Support\Facades\Http;

Route::post('/checkout', function (Request $request) {
    $transaction = Http::withToken(config('services.paddle.key'))
        ->post('https://api.paddle.com/transactions', [
            'items' => [['price_id' => 'pri_...', 'quantity' => 1]],
            'custom_data' => ['virling_vid' => $request->cookie('virling_vid')],
        ])->json('data');

    return ['transactionId' => $transaction['id']];
})->name('checkout');

The browser then calls Paddle.Checkout.open({ transactionId }). The full setup is in the Paddle docs, and the Paddle integration page shows what Virling imports.

Subscriptions and renewals

Only the first payment needs the visitor ID. Renewals carry no custom data of their own; Virling marks them as renewals and credits them to the channel of the subscription's first payment, with no code on your side. Plan changes with Cashier's swap() count as renewals too.

Check that it works

Run one sandbox payment through the whole path:

  1. In Virling, connect a read-only Paddle API key from the sandbox, which starts with pdl_sdbx_.
  2. In .env, set PADDLE_SANDBOX=true and your app's own sandbox API key, client-side token and webhook secret, and use a sandbox price ID (Cashier sandbox). @paddleJS then switches Paddle.js to the sandbox. In the API example, change the host to sandbox-api.paddle.com.
  3. Run the app on your domain or a subdomain of it, such as staging.yourdomain.com. Visits on localhost or a .test address are not recorded for your site.
  4. Open a private window and visit a page that runs the script through a tagged link, such as https://staging.yourdomain.com/?utm_source=test&utm_medium=email. Run window.virling.vid() in the browser console and note the ID.
  5. In the same window, sign in as a new user with a new email address, open the billing page and press the Subscribe button. Before you pay, the button's data-custom-data attribute should hold the ID from step 4. Pay with one of Paddle's test cards.
  6. In the Paddle sandbox, open the transaction. Its custom data should list virling_vid with the same ID.
  7. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed. Open it to see its journey.

Use a new email address for each test: a later payment by the same customer is a renewal and keeps the first payment's channel. A site has one Paddle connection, and test payments stay in your reports after you replace the key with a live one. If a step fails, see test your setup.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Paddle revenue by traffic source.

Frequently asked questions

How do I pass UTM parameters to Paddle checkout in Laravel?

Pass the Virling visitor ID instead. Read it with $request->cookie('virling_vid') in the controller that builds the checkout and add it with Cashier's customData(['virling_vid' => $vid]). Paddle stores it in the transaction's custom_data, and the Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

Why does $request->cookie('virling_vid') return null?

Laravel encrypts cookies by default and returns nothing for a cookie it did not set. Leave virling_vid out of encryption: in Laravel 11 and later with $middleware->encryptCookies(except: ['virling_vid']) in bootstrap/app.php, in older versions by adding it to $except in app/Http/Middleware/EncryptCookies.php.

Where does Virling read the visitor ID on a Paddle transaction?

From virling_vid in the transaction's custom_data. Cashier Paddle passes the custom data you set on the checkout to Paddle.js, which saves it on the transaction.

What about transactions I create on my server?

Set custom_data: { virling_vid: ... } when you create the transaction through the Paddle API, with the value read from the virling_vid cookie, then open checkout with that transaction ID.

Which channel do Paddle renewals get?

Renewals carry no custom data of their own. Virling credits them to the channel of the subscription's first payment, so there is nothing to add for them.

What happens if the cookie is missing?

The checkout opens without a visitor ID, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.

Does customData() keep the Cashier subscription type?

No. subscribe() stores the type as subscription_type in the custom data, and customData() replaces that data, so Cashier saves the subscription with the type default. For another type, call checkout('pri_...')->customData(['subscription_type' => 'team', 'virling_vid' => $vid]) instead of subscribe().
