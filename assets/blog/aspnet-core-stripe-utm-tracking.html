ASP.NET Core Stripe UTM tracking: Checkout with Stripe.net

By Devendra Variya, co-founder of Virling. Published 2026-11-22.

ASP.NET Core Stripe UTM tracking comes down to one value. Load the Virling script in your shared layout, then read the virling_vid cookie with Request.Cookies in the endpoint that creates the Stripe Checkout Session and pass it as ClientReferenceId, or as metadata.virling_vid. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each.

This post covers a .NET backend with ASP.NET Core and Stripe.net. The same steps for other stacks are in Spring Boot Stripe UTM tracking, Go Stripe UTM tracking and Next.js Stripe UTM tracking. For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Why Stripe Checkout loses your UTM tags

UTM tags live on the landing URL. Stripe Checkout runs on Stripe's domain and only stores what your server passes when it creates the session, so the tags of the visit are gone unless you carry them over. The same thing happens on any redirect that drops the query string, as covered in UTM parameters lost after redirect. Passing one visitor ID instead of the tags keeps earlier visits and untagged ones, such as search and referrals, too.

Step 1: add the script to the shared layout

Paste the tag before </head> in the layout that every page uses: Pages/Shared/_Layout.cshtml for Razor Pages, Views/Shared/_Layout.cshtml for MVC, or Components/App.razor for Blazor. If your pages are served by a separate frontend, put it in that app's layout instead. If you self-host, replace app.virling.com with your Virling server.

<!-- Pages/Shared/_Layout.cshtml -->
<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: create the Checkout Session in an endpoint

Your server receives the cookie with every request from the browser on the same domain. Read it from Request.Cookies where you create the session and pass it as ClientReferenceId. Here it is as a minimal API in Program.cs:

using Stripe;
using Stripe.Checkout;

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

StripeConfiguration.ApiKey = builder.Configuration["Stripe:SecretKey"];

app.MapPost("/checkout", async (HttpRequest request) =>
{
    var options = new SessionCreateOptions
    {
        Mode = "subscription",
        LineItems = new List<SessionLineItemOptions>
        {
            new() { Price = "price_...", Quantity = 1 },
        },
        SuccessUrl = "https://yourdomain.com/thanks",
    };
    if (request.Cookies.TryGetValue("virling_vid", out var vid) && !string.IsNullOrEmpty(vid))
    {
        options.ClientReferenceId = vid;
    }

    var session = await new SessionService().CreateAsync(options);
    return Results.Redirect(session.Url);
});

app.Run();

Install the Stripe.net NuGet package and keep the secret key in user secrets or an environment variable (Stripe__SecretKey), not in appsettings.json. Post to the endpoint from a plain form, so the browser follows the redirect to Stripe's domain:

<form method="post" action="/checkout">
  <button type="submit">Subscribe</button>
</form>

Using metadata instead

If ClientReferenceId already holds your own user or order ID, put the visitor ID in the session's metadata. Virling reads either:

if (request.Cookies.TryGetValue("virling_vid", out var vid) && !string.IsNullOrEmpty(vid))
{
    options.Metadata = new Dictionary<string, string> { ["virling_vid"] = vid };
}

The full lookup order, including PaymentIntents you create for Elements, is in the Stripe docs, and the Stripe integration page shows what Virling imports. How to pass the visitor ID with other providers is in link checkout to visits, and the script tag for other frameworks in the framework docs.

Subscriptions and renewals

Only the first payment needs the visitor ID. A renewal takes the attribution of the customer's first payment, so each monthly or yearly charge of the subscription is credited to the same visit, with no code on your side.

Check that it works

Make a test payment from a page that runs the script, wait for the next sync, and open the payments list at /app/yourdomain.com/payments. The payment should show a channel instead of Unattributed. Open it to see its journey. If it still shows Unattributed, check that the page you bought from loads the script, that the endpoint reads the virling_vid cookie, and that the checkout request goes to the same domain, so the cookie is sent.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Stripe revenue by traffic source, and the SaaS page shows what you get per channel.

Frequently asked questions

How do I pass UTM parameters to Stripe Checkout in ASP.NET Core?

Read the visitor ID with Request.Cookies["virling_vid"] in the endpoint that creates the Checkout Session and set it as ClientReferenceId on SessionCreateOptions. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

Does this work with MVC controllers, Razor Pages or Blazor?

Yes. In a controller action or a Razor Pages handler, read Request.Cookies["virling_vid"] the same way. In Blazor, create the session in a server endpoint or controller that the checkout button posts to, so the request carries the cookie. The Stripe.net code stays the same.

Should I use ClientReferenceId or metadata.virling_vid?

Use ClientReferenceId unless it already holds your own user or order ID. In that case put the visitor ID in the session's Metadata under virling_vid. Virling reads either.

Are subscription renewals attributed?

Yes. A renewal takes the attribution of the customer's first payment, so every monthly or yearly charge is credited to the visit that led to the first one, even though the renewal itself has no visit.

What happens if the cookie is missing?

TryGetValue returns false, and the session is created without a visitor ID, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.
