Convex Stripe UTM tracking: Checkout from a Convex action

By Devendra Variya, co-founder of Virling. Published 2026-11-24.

Convex Stripe UTM tracking needs one value carried through checkout. Read the visitor ID in the browser with window.virling?.vid?.(), pass it as an argument to the Convex action that creates the Stripe Checkout Session, and set it there as metadata.virling_vid. The virling_vid cookie cannot do this alone: it belongs to your domain, and the action runs on your Convex deployment. Stripe keeps the ID, and Virling joins the payment to every visit behind it, with the UTM tags of each.

The same idea with an Edge Function is in Supabase and Stripe UTM tracking. For Payment Links and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters. For other payment providers, the checkout snippet generator writes the code.

Why Stripe Checkout loses your UTM tags

UTM tags live on the landing URL. Stripe Checkout runs on Stripe's domain and only stores what your action passes when it creates the session, so the tags of the visit are gone unless you carry them over. Passing one visitor ID instead of the tags keeps earlier visits and untagged ones, such as search and referrals, too.

Step 1: add the script to every page

Paste the tag before </head> in your app's index.html, or in the layout every route uses. Keep defer. If you self-host, replace app.virling.com with your Virling server.

<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: send the visitor ID from the browser

window.virling?.vid?.() returns the same ID as the cookie. The script loads with defer, so wait briefly for it, and leave the argument out if the ID is still missing. In React, call the action with useAction:

// src/CheckoutButton.jsx
import { useAction } from "convex/react";
import { api } from "../convex/_generated/api";

async function visitorId() {
  for (let i = 0; i < 20 && !window.virling?.vid; i++) {
    await new Promise((r) => setTimeout(r, 100));
  }
  return window.virling?.vid?.() || null;
}

export function CheckoutButton() {
  const createCheckout = useAction(api.checkout.create);

  async function checkout() {
    const vid = await visitorId();
    const url = await createCheckout(vid ? { vid } : {});
    if (url) window.location.href = url;
  }

  return <button onClick={checkout}>Subscribe</button>;
}

Convex advises against calling actions straight from the client in most cases, in favor of a mutation that schedules the action. Here the browser needs the Checkout URL back, so this example calls the action directly. See the Convex actions docs.

Step 3: create the Checkout Session in a Convex action

Install the library with npm install stripe and put the action in convex/checkout.ts. The file name and the export name make up api.checkout.create. The "use node" line runs it in the Convex Node.js runtime, so keep queries and mutations in other files:

"use node";

import Stripe from "stripe";
import { v } from "convex/values";
import { action } from "./_generated/server";

export const create = action({
  args: { vid: v.optional(v.string()) },
  handler: async (_ctx, { vid }) => {
    const visitor = vid && /^[A-Za-z0-9-]{8,64}$/.test(vid) ? vid : undefined;

    const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);
    const session = await stripe.checkout.sessions.create({
      metadata: visitor ? { virling_vid: visitor } : {},
      line_items: [{ price: "price_...", quantity: 1 }],
      mode: "subscription",
      success_url: "https://yourdomain.com/thanks",
    });

    return session.url;
  },
});

Set the key with npx convex env set STRIPE_SECRET_KEY, which asks for the value. The check on vid keeps anything that is not a visitor ID out of Stripe. A public action can be called by anyone who has your deployment URL, so choose the price in the action and check the user there if checkout needs a signed-in one.

Metadata or client_reference_id

Virling reads metadata.virling_vid or client_reference_id on the Checkout Session. The key name must be exactly virling_vid. Stripe allows 50 metadata keys per object, with names up to 40 characters and values up to 500, and a client_reference_id of up to 200 characters. A visitor ID has 8 to 64 letters, digits and hyphens, so it fits either. If you have no other use for client_reference_id, this works too:

const session = await stripe.checkout.sessions.create({
  client_reference_id: visitor,
  line_items: [{ price: "price_...", quantity: 1 }],
  mode: "subscription",
  success_url: "https://yourdomain.com/thanks",
});

All the fields are in the Stripe Checkout Session reference. If you use the @convex-dev/stripe component, pass metadata: { virling_vid: visitor } to createCheckoutSession. Its subscriptionMetadata goes to the Subscription, which Virling does not read.

You do not need to send the UTM tags themselves: the script has already recorded them against the visitor ID. The full lookup order is in the Stripe docs, and the Stripe integration page shows what Virling imports.

Test it locally

Run npx convex dev, which pushes the action to your dev deployment, and set that deployment's STRIPE_SECRET_KEY to a Stripe test key and price_... to a test price. You can call the action without the browser:

npx convex run checkout:create '{"vid":"vtest12345678"}'

It prints a Checkout URL. Open that session in the Stripe Dashboard and look for virling_vid in its metadata. The ID in this command is made up, so it only shows that the value reaches Stripe.

To try the button as well, add data-dev to the script tag, because the script skips localhost without it. Virling still does not count localhost visits toward yourdomain.com, so this checks the ID, not the channel. Remove data-dev before you deploy.

Check that it works on your site

Set the key on production with npx convex env set STRIPE_SECRET_KEY --prod and deploy with npx convex deploy. Open your site from a tagged link such as https://yourdomain.com/?utm_source=test&utm_medium=test, pay, wait for the next sync, and open the payments list at /app/yourdomain.com/payments. The payment should show the test source instead of Unattributed. Open it to see its journey.

Virling only sees payments made in the mode of the key you connected: a restricted rk_test_ key for test payments, rk_live_ for live ones. Payments imported with a test key stay in your reports, so if you want only real ones, make a small live payment and refund it.

Usual mistakes

  • Reading the virling_vid cookie in the action. It is not there: send the ID as an argument.
  • Sending null. v.optional(v.string()) takes a string or no value, so leave the argument out when there is no ID.
  • Making the argument required. Checkout then fails for visitors who block the script.
  • Reading the ID as soon as the page renders. The script loads with defer, so read it on click and wait for it.
  • Setting STRIPE_SECRET_KEY on the dev deployment only. Dev and production keep separate environment variables.
  • Putting the ID in subscription_data.metadata, or on the customer or product. Virling does not read those.
  • Pasting the Stripe secret key into Virling. The action needs a key that can create sessions, while Virling refuses sk_ keys and asks for a restricted read-only one.

If a payment still shows as Unattributed, open its Checkout Session in the Stripe Dashboard. If virling_vid is missing there, check the argument your browser sends to the action. Payments without a visitor ID still count toward revenue, as Unattributed.

Frequently asked questions

Does the virling_vid cookie reach a Convex action?

No. The cookie is set on your domain, and the action runs on your Convex deployment, so the browser does not send it there. Read the ID in the browser with window.virling?.vid?.() and pass it as an argument.

Should I use metadata.virling_vid or client_reference_id?

Either works. This page uses metadata.virling_vid so client_reference_id stays free for your own user or order ID. If both hold a value, Virling uses metadata.virling_vid first.

Do I need to pass the UTM tags to Stripe?

No. The Virling script records the UTM tags of every visit against the visitor ID, so passing the ID is enough. Virling joins the payment to all the visits behind it, including untagged ones such as search and referrals.

Do I need a Stripe webhook in Convex for this?

Not for attribution. Virling reads charges and Checkout Sessions from Stripe with a restricted read-only key. Your app may still need a webhook to unlock the product after payment.

What happens if the visitor ID is missing?

The session is created without one, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.
