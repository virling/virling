Rails Paddle UTM tracking: pass the visitor ID to checkout

By Devendra Variya, co-founder of Virling. Published 2026-11-25.

Rails Paddle UTM tracking comes down to one value. Load the Virling script in your layout, read the virling_vid cookie with cookies[:virling_vid] in a controller, and pass it to Paddle Checkout as customData. Paddle keeps it in the transaction's custom_data, and Virling joins the payment to every visit behind that ID, with the UTM tags of each.

This post covers Paddle Billing with the overlay checkout and with transactions your server creates. For hosted checkout, see Paddle checkout UTM parameters. Other stacks are in Rails Stripe UTM tracking and Laravel Paddle UTM tracking.

Why Paddle checkout loses your UTM tags

UTM tags live on the landing URL, and the buyer is usually a few pages past it when checkout opens. Paddle's docs list capturing UTM information as a use for custom data that you pass yourself (source: Paddle, Work with custom data). One visitor ID is better than copied tags, because it also keeps earlier visits and untagged ones, such as search.

Step 1: add both scripts to the layout

Paste this before </head>. If you self-host, replace app.virling.com with your Virling server. PADDLE_CLIENT_TOKEN is a client-side token, never an API key. Sandbox tokens start with test_.

<%# app/views/layouts/application.html.erb %>
<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>
<% paddle_token = ENV.fetch("PADDLE_CLIENT_TOKEN") %>
<script src="https://cdn.paddle.com/paddle/v2/paddle.js"
  data-turbo-track="reload"></script>
<script data-turbo-track="reload">
  <% if paddle_token.start_with?("test_") %>
  Paddle.Environment.set("sandbox");
  <% end %>
  Paddle.Initialize({ token: "<%= paddle_token %>" });
</script>

The Virling script sets the first-party virling_vid cookie on your domain and records each visit against it.

Step 2: read the cookie in a controller

The script sets a plain cookie, so use cookies, not cookies.signed or cookies.encrypted.

# config/routes.rb
get "pricing", to: "pricing#show"

# app/controllers/pricing_controller.rb
class PricingController < ApplicationController
  def show
    @vid = cookies[:virling_vid].presence
  end
end

The view puts the price and the ID on the button. When the ID is nil, Rails leaves the attribute out:

<%# app/views/pricing/show.html.erb %>
<%= tag.button "Subscribe", type: "button",
      data: { buy: "pri_...", vid: @vid } %>

Step 3: open the overlay checkout with custom data

Add one click listener to your JavaScript entry file:

// app/javascript/application.js
document.addEventListener("click", (event) => {
  const button = event.target.closest("[data-buy]");
  if (!button) return;
  const vid = window.virling?.vid?.() || button.dataset.vid;
  Paddle.Checkout.open({
    items: [{ priceId: button.dataset.buy, quantity: 1 }],
    ...(vid && { customData: { virling_vid: vid } }),
  });
});

The ID from the browser comes first, because the cookie may not exist yet when the first page is requested. The one from Rails is the fallback. Paddle requires customData to hold at least one key, so the code leaves it out when there is no ID (source: Paddle.Checkout.open). An inline checkout takes the same customData.

Or create the transaction on your server

If Rails creates the transaction, set custom_data on it. Add resource :checkout, only: :create to your routes:

# app/controllers/checkouts_controller.rb
require "net/http"

class CheckoutsController < ApplicationController
  def create
    body = { items: [{ price_id: "pri_...", quantity: 1 }] }
    vid = cookies[:virling_vid]
    body[:custom_data] = { virling_vid: vid } if vid.present?

    response = Net::HTTP.post(
      URI("#{ENV.fetch("PADDLE_API_URL")}/transactions"),
      body.to_json,
      "Authorization" => "Bearer #{ENV.fetch("PADDLE_API_KEY")}",
      "Content-Type" => "application/json"
    )
    transaction = JSON.parse(response.body).fetch("data")
    redirect_to transaction.dig("checkout", "url"),
      allow_other_host: true, status: :see_other
  end
end

Post to it from a view with Turbo off:

<%= button_to "Subscribe", checkout_path,
      form: { data: { turbo: false } } %>

PADDLE_API_URL is https://api.paddle.com, or https://sandbox-api.paddle.com for the sandbox. This key needs transaction.write (source: Paddle, Create a transaction), so keep it apart from the read-only key you give Virling. checkout.url is your default payment link with ?_ptxn= and the transaction ID, and Paddle.js on that page opens the checkout (source: Paddle, Pass a transaction to a checkout).

Create the transaction in the request the buyer sends. A background job or a webhook has no cookie to read.

Turbo navigation

  • Visits are counted. Turbo page visits use history.pushState, and the Virling script records each one.
  • Initialize once. Paddle allows one Paddle.Initialize() call on a page (source: Paddle.Initialize). Turbo keeps scripts already in the <head> and evaluates scripts in the <body> on every render (source: Turbo, Building your Turbo application).
  • Two layouts. Moving from a layout without Paddle.js, Turbo adds the missing head scripts, and the inline one can run before Paddle.js has loaded. data-turbo-track="reload" makes that move a full page load.
  • Redirects to a payment link. Paddle.js has to start on the page with ?_ptxn=. A Turbo visit does not start it again, so the form turns Turbo off.

What a renewal is credited to

A renewal is credited to the channel of the customer's first payment, matched by Paddle customer ID, and so is a plan change. Paddle says that a subscription's custom data is copied to transactions created from it. That changes nothing here: when the first payment has a channel, the renewal takes it.

A made-up example: a buyer clicks a link tagged utm_medium=email in your newsletter in March and pays $29. In April they open a Google result, and Paddle renews the plan the next day. Both payments, $58 in all, are credited to Email.

Two limits. The first import reads 90 days, so renewals of older subscriptions are usually Unattributed. And a free trial is recorded only from a $0 subscription transaction of origin web, the origin Paddle gives to checkouts Paddle.js creates. Transactions from its API have origin api, so open trials with the overlay from step 3. More is in renewals and on Paddle for SaaS.

Test it in the sandbox

  1. In Virling, connect a sandbox API key that starts with pdl_sdbx_, with the permissions in the Paddle docs.
  2. Give Rails the sandbox token, API key, API URL and price ID. Sandbox and live accounts share none of these. For server-created transactions, set the sandbox default payment link too.
  3. Run the app on your domain or a subdomain, such as staging.yourdomain.com. Paddle's sandbox opens on localhost, but Virling does not record visits there for your site.
  4. Open a private window at https://staging.yourdomain.com/pricing?utm_source=test&utm_medium=email, press Subscribe, and pay with 4242 4242 4242 4242 and a future date (source: Paddle, Sandbox).
  5. In Paddle, check that the transaction's custom data lists virling_vid.
  6. Wait a minute for the next sync, then open /app/yourdomain.com/payments. The payment shows the test source and the Email channel.

Sandbox payments stay in your reports after you replace the key with a live one. If a step fails, see test your setup.

Frequently asked questions

How do I pass UTM parameters to Paddle checkout in Rails?

Pass the Virling visitor ID instead. Read it with cookies[:virling_vid] in the controller, hand it to the view, and set it as virling_vid in customData when Paddle.js opens checkout. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

Do I need a gem for Paddle in Rails?

No. The overlay checkout needs only Paddle.js, and a server-created transaction is one POST request, which Net::HTTP can send. If you use a gem, set custom_data on the transaction it creates.

Why is cookies[:virling_vid] nil in my Rails controller?

On a visitor's first page the script has not set the cookie yet, so that request does not carry it. It is also nil in a background job or a webhook, with cookieless mode, or when the script is blocked. In the browser, window.virling?.vid?.() returns the ID once the script has run.

Does Turbo break Paddle checkout?

Not if Paddle.js is loaded and initialized in the head and one click listener is added on the document. Turn Turbo off for a form that redirects to Paddle's checkout.url on your own domain, so the page loads fully and Paddle.js opens the checkout.

Which channel do Paddle renewals get?

The channel of the customer's first payment, matched by Paddle customer ID. Renewals and plan changes need no code in your Rails app.
