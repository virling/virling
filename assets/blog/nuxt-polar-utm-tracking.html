Nuxt Polar UTM tracking: see which source brought each order

By Devendra Variya, co-founder of Virling. Published 2026-11-25.

For Nuxt Polar UTM tracking, add the Virling script to app.head in nuxt.config.ts, then read the virling_vid cookie in the server route that creates the Polar checkout and set it in metadata. Checkout links on buy.polar.sh need no server code: the script adds the ID as reference_id. Polar keeps that one ID on the order, and Virling joins the order to every visit behind it, with the UTM tags of each.

This post covers Nuxt 4. For the reasoning, see Polar UTM tracking. Using Stripe instead? See Nuxt Stripe UTM tracking. On Svelte, see SvelteKit Polar UTM tracking.

Why Polar checkout loses your UTM tags

UTM tags live on the landing URL. By the time someone presses Buy, they have usually moved to another route, and Polar checkout runs on Polar's domain, which knows only what you pass into it. A visitor ID points back to every visit, including earlier ones and untagged ones such as search.

Step 1: add the script to nuxt.config.ts

Nuxt renders this entry into the HTML of every page, and route changes are tracked through history.pushState. Use the domain you added in Virling as data-site. If you self-host, replace app.virling.com with your Virling server.

// nuxt.config.ts
export default defineNuxtConfig({
  app: {
    head: {
      script: [
        { src: "https://app.virling.com/v.js", defer: true,
          "data-site": "yourdomain.com" },
      ],
    },
  },
  runtimeConfig: {
    polarAccessToken: "", // set NUXT_POLAR_ACCESS_TOKEN
  },
});

The script sets the first-party virling_vid cookie on your domain. Subdomains such as app.yourdomain.com share it. The runtimeConfig entry keeps the Polar token on the server: Nuxt fills it from NUXT_POLAR_ACCESS_TOKEN (source: Nuxt, runtime config). A built server does not read .env, so set the variable on your host.

Step 2a: checkout links, no server code

If you sell through Polar checkout links, keep the link as a normal <a href> on a page that runs the script:

<!-- app/pages/pricing.vue -->
<template>
  <a href="https://buy.polar.sh/YOUR_CHECKOUT_LINK">Buy now</a>
</template>

The script adds reference_id=<visitor ID> when the page loads and again on click, so links that appear after a route change are covered. It never replaces a reference_id that is already there. Polar attaches that parameter to the checkout session's metadata (source: Polar, checkout links), and Virling reads it from the order.

Step 2b: create the checkout in a server route

Install @polar-sh/sdk and create an access token with the checkouts:write scope. It is a different token from the one you give Virling. getCookie reads the visitor ID from the request:

// server/api/checkout.post.ts
import { createPolar } from "@polar-sh/sdk/2026-10";

export default defineEventHandler(async (event) => {
  const { polarAccessToken } = useRuntimeConfig(event);
  const polar = createPolar({ accessToken: polarAccessToken });
  const vid = getCookie(event, "virling_vid");
  const checkout = await polar.checkouts.create({
    products: ["PRODUCT_ID"],
    success_url: "https://yourdomain.com/thanks",
    metadata: vid ? { virling_vid: vid } : {},
  });
  // Send the customer to checkout.url
  return sendRedirect(event, checkout.url, 303);
});

A plain form posts to it, and the browser sends the cookie along:

<!-- app/pages/pricing.vue -->
<template>
  <form method="POST" action="/api/checkout">
    <button type="submit">Buy</button>
  </form>
</template>

The import path pins the API version (source: Polar, TypeScript SDK). On 0.x releases of the SDK, use new Polar({ accessToken }) from @polar-sh/sdk and write successUrl. Polar copies checkout metadata to the resulting order and/or subscription, with text values of 1 to 500 characters (source: Polar, create checkout session). So the route sends no key, not an empty string, when there is no cookie.

Polar also has a Nuxt module. Its checkout handler takes metadata from the query string of a GET request, so you would have to put the ID in the URL yourself.

Virling reads virling_vid from, in order: the order's metadata, its custom field data, then the customer's metadata. A checkout link's reference_id is read after those. See the Polar docs.

Step 3: connect Polar to Virling

In Polar, create an Organization Access Token with the orders:read and refunds:read scopes, plus subscriptions:read so Retention can tell who still pays, and paste it into Virling. The last 90 days of orders are imported first, then new orders every minute. Your Nuxt app needs no webhook for this.

Rendering modes: where the cookie is read

The script runs in the browser, so it works the same in every mode. What changes is whether your own code can see the cookie. See Nuxt, rendering modes.

PageWhat happensHow to pass the ID
Server rendered, the defaultThe first visit is rendered before the script has set the cookieRead it in the POST route
ssr: falseThe browser renders the page, and server routes still runRead it in the POST route
Prerendered with routeRulesThe HTML is made once, at build time, with no visitorPost a form from the page to the route
Cached with swr or isrOne copy of the HTML serves many visitorsPost a form to the route, and keep the route out of the cached patterns
Whole app built with nuxt generateNo server is included in the outputUse checkout links

Read the cookie in the request that creates the checkout, never while a page is rendered.

Test it in the Polar sandbox

The sandbox has its own account, products and tokens, and production tokens do not work there (source: Polar, sandbox).

  1. In the sandbox, create a product and two tokens: one with checkouts:write for your app, one with the read scopes for Virling. Connect the second one.
  2. Deploy a test version on your domain or a subdomain of it, with the sandbox token and product ID, and createPolar({ accessToken: polarAccessToken, environment: "sandbox" }) in the route. On SDK 0.x the option is server: "sandbox".
  3. Open a private window and visit a page that runs the script through a tagged link, such as https://yourdomain.com/?utm_source=test&utm_medium=email, on the host of your test version. Click through to the pricing page.
  4. In the same window, press Buy and pay with the card 4242 4242 4242 4242, a future date and any CVC.
  5. Wait a minute for the next sync and open /app/yourdomain.com/payments. The payment shows the test source and the Email channel instead of Unattributed.

The script does not tag sandbox links, so step 2a cannot be tested there. Test it with one small live payment, then refund it. Sandbox orders stay in your reports after you switch to a production token.

What a renewal is credited to

A renewal has no visit of its own, so it keeps the channel, referrer, campaign and landing page of the customer's first order, matched by Polar customer ID. Orders with billing reason subscription_cycle or subscription_update count as renewals, and so does any later order by that customer.

A made-up example: someone reads your newsletter on Monday through a link tagged utm_source=newsletter&utm_medium=email, and buys a $20 monthly plan on Thursday after typing your address. With the default model the first order goes to Email. Three renewals later, Email has $80 from that customer, and nothing in your Nuxt app ran again.

A free trial starts with a $0 order of billing reason subscription_create. Virling does not count it as a payment; a later payment with no visitor ID of its own is credited from the visits before the trial. If the first order is older than the 90-day import, its renewals are usually Unattributed. More is in the renewals docs and on Polar for SaaS.

Open an Unattributed payment and look for Visitor under Details. If there is none, checkout did not carry the ID.

Frequently asked questions

How do I pass UTM parameters to a Polar checkout in Nuxt?

Pass the Virling visitor ID instead. In the server/api route that calls polar.checkouts.create, read it with getCookie(event, "virling_vid") and set it in metadata as virling_vid. The Virling script records the UTM tags of every visit against that ID, so the order is joined to all of them.

Do Polar checkout links in a Nuxt app need server code?

No. Keep the link to buy.polar.sh as a normal <a href> on a page that runs the script. The script adds reference_id=<visitor ID> to it, unless it is already there, and Polar stores it in the order's metadata, where Virling reads it.

What happens if the virling_vid cookie is missing?

Create the checkout without it. The order still counts toward revenue, as Unattributed unless it is a renewal. Do not send an empty string: Polar requires metadata text values to have at least one character.

Does this work with nuxt generate?

Yes, with checkout links. A site built with nuxt generate includes no server, so a server/api route cannot run there. To create checkouts in a route, deploy with nuxt build.

Does this work with the Polar sandbox?

Yes, for checkouts your server creates. Set environment: "sandbox" on the Polar client and connect a sandbox token to Virling. The script does not add the visitor ID to sandbox links, so test with a session that has virling_vid in its metadata.

Which channel does a Polar renewal go to?

To the channel of that customer's first order, matched by Polar customer ID. If that order has no channel, or is older than the first import, the renewal is usually Unattributed.
