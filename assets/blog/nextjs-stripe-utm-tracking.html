Next.js Stripe Checkout UTM tracking: pass the visit to the session

By Devendra Variya, co-founder of Virling. Published 2026-11-19, updated 2026-11-25.

To tie a Stripe Checkout payment in a Next.js app to the visit that brought it, load the Virling script in your root layout, then read the virling_vid cookie in the route handler or server action that creates the Checkout Session and pass it as client_reference_id. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each. Two files change, and the rest of your checkout stays as it is.

This post covers the App Router. For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Step 1: add the script to the root layout

Use next/script with strategy="afterInteractive" in app/layout.tsx, so it loads once and runs on every route. Client-side navigation is counted too. If you self-host, replace app.virling.com with your Virling server.

import Script from "next/script";

export default function RootLayout({ children }) {
  return (
    <html lang="en">
      <body>
        {children}
        <Script src="https://app.virling.com/v.js"
          data-site="yourdomain.com" strategy="afterInteractive" />
      </body>
    </html>
  );
}

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: create the Checkout Session in a route handler

Your server receives the virling_vid cookie with every request from the browser. Read it where you create the session and pass it as client_reference_id:

// app/api/checkout/route.ts
import { NextRequest, NextResponse } from "next/server";
import Stripe from "stripe";

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);

export async function POST(req: NextRequest) {
  const session = await stripe.checkout.sessions.create({
    client_reference_id: req.cookies.get("virling_vid")?.value,
    line_items: [{ price: "price_...", quantity: 1 }],
    mode: "subscription",
    success_url: "https://yourdomain.com/thanks",
  });
  return NextResponse.redirect(session.url!, 303);
}

A plain form posts to it, and the browser sends the cookie along:

<form action="/api/checkout" method="POST">
  <button type="submit">Buy</button>
</form>

Or in a server action, with metadata

If client_reference_id already holds your own user or cart ID, put the visitor ID in the session's metadata.virling_vid instead. Virling reads either. In a server action, cookies() from next/headers gives you the cookie:

// app/actions.ts
"use server";
import { cookies } from "next/headers";
import { redirect } from "next/navigation";
import Stripe from "stripe";

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);

export async function checkout() {
  const vid = (await cookies()).get("virling_vid")?.value;
  const session = await stripe.checkout.sessions.create({
    // client_reference_id stays free for your own ID
    metadata: vid ? { virling_vid: vid } : {},
    line_items: [{ price: "price_...", quantity: 1 }],
    mode: "subscription",
    success_url: "https://yourdomain.com/thanks",
  });
  redirect(session.url!);
}

Call it from a form with <form action={checkout}>. The full lookup order, including PaymentIntents you create for Elements, is in the Stripe docs and on the Stripe integration page.

Prerendered, server rendered and cached pages

Read the cookie in the route handler or server action: both run on request, also when the form is on a static page. Leave force-static off the checkout route, where cookies() and req.cookies are empty, and call cookies() outside any use cache function. With output: "export" there is no server, so use Payment Links, which the script fills in the browser. First visits, prerendered and cached copies, hidden fields and route changes work the same in every framework; see reading the visitor cookie in server code.

Check that it works

Run one test payment through the whole path, from your own dev server:

  1. In Virling, connect a restricted Stripe key that starts with rk_test_. Your app keeps its own test secret key in STRIPE_SECRET_KEY, for example in .env.local, and uses a price created in test mode.
  2. Add the line 127.0.0.1 dev.yourdomain.com to your hosts file and start the dev server on that name with npm run dev -- -H dev.yourdomain.com. The script does nothing on localhost, and Virling keeps a visit only when the page's host is your site's domain or one of its subdomains.
  3. Open a private window and visit the dev server through a tagged link, such as http://dev.yourdomain.com:3000/?utm_source=test&utm_medium=email. Run window.virling.vid() in the browser console and note the ID. Click through to the pricing page, so a client-side navigation is part of the test.
  4. In the same window, press Buy. Pay with the card 4242 4242 4242 4242, any future date and any three-digit CVC (Stripe testing).
  5. Check the Checkout Session with the log line below, in the terminal that runs the dev server. client_reference_id, or virling_vid in the session's metadata if you use that, should be the ID from step 3. The charge and PaymentIntent do not need it: Stripe does not copy session metadata to them.
  6. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed. Open it to see its journey.

For step 5, add this right after stripe.checkout.sessions.create() and remove it afterwards:

console.log(session.id, session.client_reference_id, session.metadata);

The dev server renders static pages on request and has no CDN in front of it, so it cannot show a page that was cached wrongly. Repeat steps 3 to 6 once on a deployed subdomain, such as staging.yourdomain.com. Go straight there if your browser insists on https for the dev address, as it does for domains that end in .dev or .app.

If your code passes customer, use a new customer for each test: a later payment by the same customer is a renewal and keeps the first payment's channel. A site has one Stripe connection, and test payments stay in your reports after you replace the key with a live one. If you want only real payments in your numbers, make one small live payment instead and refund it. If a step fails, see test your setup.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Stripe revenue by traffic source, and the SaaS page shows what you get per channel.

Frequently asked questions

How do I pass UTM parameters to a Stripe Checkout Session in Next.js?

Read the visitor ID from the virling_vid cookie in a route handler or server action and pass it as client_reference_id when you create the session. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

How do I read the virling_vid cookie in the App Router?

In a route handler, use req.cookies.get("virling_vid")?.value on the NextRequest. In a server action, use cookies() from next/headers. It is a first-party cookie on your domain, so the browser sends it with every request to your app.

Should I use client_reference_id or metadata.virling_vid?

Use client_reference_id unless it already holds your own user or cart ID. In that case put the visitor ID in the session's metadata.virling_vid. Virling reads either.

What happens if the cookie is missing?

The session is created without a visitor ID, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.

Do Stripe Payment Links in a Next.js app need code?

No. Use a normal link to buy.stripe.com on a page that runs the script. The script adds client_reference_id to the link when the page loads and again on click, unless the link already has one.

Does this work with the Pages Router?

Yes. Load the script with next/script in pages/_app.tsx, and in an API route read req.cookies.virling_vid when you create the Checkout Session.
