Astro Stripe UTM tracking: tie each payment to its source

By Devendra Variya, co-founder of Virling. Published 2026-11-22, updated 2026-11-25.

To see which traffic source each Stripe payment came from in an Astro site, add the Virling script to your layout with is:inline, then read the virling_vid cookie in the API endpoint or page that creates the Checkout Session and pass it as client_reference_id. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each. Two files change, and the rest of your checkout stays as it is.

For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Why Stripe Checkout loses your UTM tags

UTM tags live on the landing URL. Stripe Checkout runs on Stripe's domain and only stores what your server passes when it creates the session, so the tags of the visit are gone unless you carry them over. Passing one visitor ID instead of the tags keeps earlier visits and untagged ones, such as search and referrals, too. If the tags never reach your landing page at all, a redirect is usually dropping them; see UTM parameters lost after redirect.

Step 1: add the script to your layout

Put the tag in the <head> of the layout every page uses. Mark it is:inline so Astro leaves the tag as it is instead of bundling it: the script reads its own attributes, which only works on the original tag. Route changes from view transitions are tracked through pushState, so load it once here. If you self-host, replace app.virling.com with your Virling server.

---
// src/layouts/Layout.astro
---
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <script is:inline defer src="https://app.virling.com/v.js"
      data-site="yourdomain.com"></script>
  </head>
  <body>
    <slot />
  </body>
</html>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: create the Checkout Session in an API endpoint

Your server receives the virling_vid cookie with every request from the browser, and Astro hands it to you on cookies. The endpoint has to run on request, so it needs a server adapter and prerender = false (or output: "server"). Read the cookie where you create the session and pass it as client_reference_id:

// src/pages/api/checkout.ts
import type { APIRoute } from "astro";
import Stripe from "stripe";

export const prerender = false;

const stripe = new Stripe(import.meta.env.STRIPE_SECRET_KEY);

export const POST: APIRoute = async ({ cookies, redirect }) => {
  const session = await stripe.checkout.sessions.create({
    client_reference_id: cookies.get("virling_vid")?.value,
    line_items: [{ price: "price_...", quantity: 1 }],
    mode: "subscription",
    success_url: "https://yourdomain.com/thanks",
  });
  return redirect(session.url!, 303);
};

A plain form in any Astro component posts to it, and the browser sends the cookie along. The page with the form can stay static:

<form method="POST" action="/api/checkout">
  <button type="submit">Buy</button>
</form>

Or in the page itself, with metadata

An on-demand page can handle its own form post in the frontmatter, with Astro.cookies. If client_reference_id already holds your own user or cart ID, put the visitor ID in the session's metadata.virling_vid instead. Virling reads either:

---
// src/pages/pricing.astro
import Stripe from "stripe";
import Layout from "../layouts/Layout.astro";

export const prerender = false;

if (Astro.request.method === "POST") {
  const stripe = new Stripe(import.meta.env.STRIPE_SECRET_KEY);
  const vid = Astro.cookies.get("virling_vid")?.value;
  const session = await stripe.checkout.sessions.create({
    // client_reference_id stays free for your own ID
    metadata: vid ? { virling_vid: vid } : {},
    line_items: [{ price: "price_...", quantity: 1 }],
    mode: "subscription",
    success_url: "https://yourdomain.com/thanks",
  });
  return Astro.redirect(session.url!, 303);
}
---
<Layout>
  <form method="POST">
    <button type="submit">Buy</button>
  </form>
</Layout>

The full lookup order, including PaymentIntents you create for Elements, is in the Stripe docs and on the Stripe integration page. The checkout snippet generator writes the same call for other providers.

Prerendered, server rendered and cached pages

The script runs in the browser, so it works the same on every kind of page: it creates the cookie and reads the UTM tags from the address there, never from your HTML. What changes is when your own code runs, and so whether it can see the cookie.

PageWhat changesWhere the cookie is read
Prerendered, the defaultThe HTML is made once at build time. Astro.cookies finds nothing, and a form post to the page is not handledIn an endpoint with prerender = false. A form on the prerendered page posts to it
On demand, with prerender = false or output: "server"Each request renders the page, and Astro.cookies can read the cookie once the browser has itIn the endpoint, or in the frontmatter when the page handles its own POST
Cached at the edgeOne copy of the HTML serves many visitors. The tag is the same for all of them, so the copy is safeIn the endpoint. Keep POST requests to it out of the cache
Static site, with no adapterThere is no server, so no endpoint at run timeBy the script in the browser, which adds the ID to Payment Links

One rule covers every row: read the cookie in the request that creates the session, not when the page is rendered to be viewed. On a first visit the server renders the page before the script has set the cookie, and in a prerendered or cached page there is no cookie of this visitor at all. The same goes for a hidden field filled in while the page renders: from a shared copy, every buyer would send the same value.

Without view transitions each link is a full page load, counted as usual. With <ClientRouter /> route changes go through the History API and are counted on their own. Each change of path or query is one pageview, and a change of only the #hash is none. Later routes carry no referrer, so they stay in the channel of the landing page. The cookie stays in the browser through all of it, so it is sent from whichever page the buyer presses Buy on. Payment Links that appear after a route change get the visitor ID when they are clicked.

Check that it works

Run one test payment through the whole path, from your own dev server:

  1. In Virling, connect a restricted Stripe key that starts with rk_test_. Your app keeps its own test secret key in STRIPE_SECRET_KEY, for example in .env, and uses a price created in test mode.
  2. Add the line 127.0.0.1 dev.yourdomain.com to your hosts file and start the dev server on that name with npm run dev -- --host dev.yourdomain.com. The script does nothing on localhost, and Virling keeps a visit only when the page's host is your site's domain or one of its subdomains.
  3. Open a private window and visit the dev server through a tagged link, such as http://dev.yourdomain.com:4321/?utm_source=test&utm_medium=email. Run window.virling.vid() in the browser console and note the ID. Click through to the pricing page, so a client-side navigation is part of the test.
  4. In the same window, press Buy. Pay with the card 4242 4242 4242 4242, any future date and any three-digit CVC (Stripe testing).
  5. Check the Checkout Session with the log line below, in the terminal that runs the dev server. client_reference_id, or virling_vid in the session's metadata if you use that, should be the ID from step 3. The charge and PaymentIntent do not need it: Stripe does not copy session metadata to them.
  6. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed. Open it to see its journey.

For step 5, add this right after stripe.checkout.sessions.create() and remove it afterwards:

console.log(session.id, session.client_reference_id, session.metadata);

The dev server renders prerendered pages and endpoints on request, so it also runs a checkout endpoint that a build would leave out. Repeat steps 3 to 6 once on a deployed subdomain, such as staging.yourdomain.com. Go straight there if your browser insists on https for the dev address, as it does for domains that end in .dev or .app.

If your code passes customer, use a new customer for each test: a later payment by the same customer is a renewal and keeps the first payment's channel. A site has one Stripe connection, and test payments stay in your reports after you replace the key with a live one. If you want only real payments in your numbers, make one small live payment instead and refund it. If a step fails, see test your setup.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Stripe revenue by traffic source, and the Stripe for SaaS page shows what you get per channel. On other frameworks, see Next.js, SvelteKit, Nuxt and Remix. For checkout in a plain Worker, see Cloudflare Workers Stripe UTM tracking.

Frequently asked questions

How do I pass UTM parameters to a Stripe Checkout Session in Astro?

Read the visitor ID from the virling_vid cookie in an API endpoint or an on-demand page, and pass it as client_reference_id when you create the session. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

How do I read the virling_vid cookie in Astro?

In an API endpoint, use cookies.get("virling_vid")?.value on the context. In a page frontmatter, use Astro.cookies.get("virling_vid")?.value. Both need the route to render on request, since a prerendered page has no request to read. It is a first-party cookie on your domain, so the browser sends it with every request to your site.

Why does the script tag need is:inline?

Without it Astro processes and bundles the script, and the tag loses its data-site attribute. The script reads its own attributes, which only works on the original tag.

Should I use client_reference_id or metadata.virling_vid?

Use client_reference_id unless it already holds your own user or cart ID. In that case put the visitor ID in the session's metadata.virling_vid. Virling reads either.

What happens if the cookie is missing?

The session is created without a visitor ID, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.

Do Stripe Payment Links on a static Astro site need code?

No. Use a normal link to buy.stripe.com on a page that runs the script, and no server code is needed. The script adds client_reference_id to the link when the page loads and again on click, unless the link already has one.
