GitHub revenue tracking: which README and repo visits turn into paying customers

By Devendra Variya, co-founder of Virling. Published 2026-11-17.

GitHub revenue tracking means joining the visits that come from github.com, or from links you tagged as GitHub, to the payments those visitors make later. Stars, clones and the repository traffic graph show interest in the code. They do not show who went on to pay for the hosted version or a license.

For a developer tool or an open-source SaaS, the repository is often the first page a buyer reads. They find it from a search, a list or a dependency, read the README, and click through to your site. A repository links to you from more than one place: the README, the About box, release notes, a GitHub Pages site and a Sponsors profile. Each can be measured separately.

How a GitHub visit is recognized

  • github.com. A click from any page on github.com lands in the Referral channel and is named GitHub in the Source tab. GitHub sends only https://github.com/ as the referrer, so the README, an issue comment, a release and the About box arrive alike.
  • githubusercontent.com is not GitHub. Raw files are served from raw.githubusercontent.com and README images through camo.githubusercontent.com. Loading a badge or a screenshot is not a pageview on your site, so it never counts as a visit. If a click ever arrives with a githubusercontent.com referrer, it is its own Referral row, apart from GitHub, because only github.com carries the GitHub name. The same goes for gist.github.com.
  • GitHub Pages. A project site on github.io sends its own host, such as yourname.github.io, and shows under that host.
  • No referrer. Release notification emails and links copied out of a README often arrive with no referrer. Virling then reads utm_source, or ref when it is missing; with neither, the visit is Direct.

Tag each place the repository links to you

Use utm_source=github everywhere and one utm_campaign per placement, so the Campaign tab splits them. When a referrer is present it still decides the channel and source, and the campaign is recorded alongside.

README:         https://yourdomain.com/?utm_source=github&utm_medium=referral&utm_campaign=readme
Website field:  https://yourdomain.com/?utm_source=github&utm_medium=referral&utm_campaign=repo-website
Release notes:  https://yourdomain.com/?utm_source=github&utm_medium=referral&utm_campaign=release-v2-4
Pages site:     https://yourdomain.com/?utm_source=github&utm_medium=referral&utm_campaign=pages
Sponsors:       https://yourdomain.com/?utm_source=github&utm_medium=referral&utm_campaign=sponsors
  • README. When you publish a package, the README is often shown on npmjs.com, PyPI or crates.io too, and its links go with it. A click there carries the registry's host as the referrer, so the Source tab credits the registry while the readme campaign counts README clicks from everywhere.
  • Releases. Watchers get release notes by email, and those clicks often have no referrer, so the tag is what keeps them out of Direct. A campaign per release shows which release brought buyers; use one value such as releases for a total.
  • GitHub Pages. Untagged clicks from a Pages site show under its github.io host. Tag its links to your product to count them with the rest of GitHub in the Campaign tab. If the Pages site is your own docs and should count as part of your site, serve it from a subdomain of your domain instead.
  • Sponsors. A link on your Sponsors profile arrives from github.com like any other GitHub click. The sponsorships themselves are paid to GitHub, not through your payment provider, so Virling does not count them as revenue.

Keep the values lowercase and the same everywhere. Do not use utm_medium=email or cpc, which move the visit into Email or Paid. The UTM builder makes the links, and which UTM parameters to use covers naming.

Sign in with GitHub is not a visit from GitHub

If your app offers Sign in with GitHub, visitors leave for GitHub's login page and come back seconds later. Virling treats a return from GitHub login as part of the visit already in progress, as it does with Google and Apple sign-in and with checkout pages, so GitHub does not gain a visit and the channel that brought the visitor keeps the credit. Reading the GitHub row

  • Give it months. Developers often run the open-source version for a while before they pay for hosting or a license.
  • Split the placements. The Campaign tab shows whether the README, a release or the Sponsors profile brought the buyers, including tagged clicks that arrived with no referrer.
  • Compare models. If GitHub revenue grows under first touch, developers found you through the repository and paid after coming back through search, docs or a typed URL.
  • Check retention. Retention by channel shows whether GitHub customers keep paying.

First-touch or last-touch attribution and how long a visitor takes to become a customer go deeper. For the other places developers find a tool, see which package registry visits turn into paying users, whether Stack Overflow answers bring customers and revenue from dev.to and Medium articles.

What to check when the numbers look wrong

  • The readme campaign has npmjs.com or pypi.org rows. Your README is shown on the registry and its tagged links are clicked there. The Source tab credits the registry; the campaign counts the README as a whole.
  • A github.io row instead of GitHub. Clicks from your Pages site carry its own host. Tag those links if you want them under GitHub in the Campaign tab.
  • Release clicks are in Direct. Untagged links opened from release notification emails have no referrer. Tag release links.
  • Self-hosters do not show up. People who run your open-source code on their own servers never reach your checkout, so they are not revenue. Virling measures the visitors who come to your site and pay.

Frequently asked questions

How do I track revenue from GitHub?

Tag the links in your README, About box and releases with utm_source=github, run the Virling script on the pages they reach, and pass the visitor ID into checkout. Clicks from github.com show as GitHub in the Referral channel, and each payment from your connected provider is credited to a visit before it.

Why can I not see which repository or README sent a visitor?

GitHub sends only its origin, https://github.com/, as the referrer, not the page the link was on. Every click from a README, an issue, a release or the website field looks the same. Give each placement its own utm_campaign to tell them apart in the Campaign tab.

Should links in my README carry UTM tags?

Yes. The referrer already credits clicks from github.com to GitHub, but it cannot tell the README from a release note, and links copied out of the README or opened from GitHub notification emails often arrive with no referrer. A tag keeps the placement in both cases.

Does Sign in with GitHub count as a visit from GitHub?

No. A visitor returning from the GitHub login page continues the visit they were already on, so the channel they first came from keeps the credit.

Do GitHub Sponsors payments show as revenue?

No. Sponsorships are paid to GitHub, not through a payment provider Virling reads, so they are not revenue in Virling. A click from your Sponsors profile to your site still counts as a GitHub visit, and any payment that visitor makes at your checkout is credited to it.

Does GitHub get credit if a developer pays weeks after starring the repo?

Yes, if their GitHub visit is inside the lookback window, 90 days by default, and no later non-direct visit took the credit. Switch the model to first touch to credit the visit that introduced the buyer, whatever came after. A visit in another browser or device cannot be tied to the same person.
