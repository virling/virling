GitHub revenue tracking: which README and repo visits turn into paying customers

By Devendra Variya, co-founder of Virling. Published 2026-11-17.

GitHub revenue tracking means joining the visits that come from github.com, or from links you tagged as GitHub, to the payments those visitors make later. To see which GitHub visits turn into paying customers, put UTM tags on the links in your README, repository website field and release notes, add a tracking script that keeps the referrer, pass the visitor ID into checkout, and connect your payment provider. Stars, clones and repository traffic graphs do not tell you this.

For a developer tool or an open-source SaaS, the repository is often the first page a buyer reads. They find it from a search, a list or a dependency, read the README, and click through to your site to try the hosted version. Some pay the same week; many come back weeks later. GitHub's own insights stop at the repository, so the revenue has to be measured on your side.

How a GitHub visit is recognized

  • The referrer. A click on a link on github.com usually arrives with github.com as the referrer. In Virling any host that is not a known search, AI, community or social site is in the Referral channel, so GitHub is in Referral and shows as GitHub in the Source tab.
  • Only the origin. GitHub sends https://github.com/, not the page the link was on. A click from your README, an issue comment, a release, a discussion or the website field in the About box all look the same. This is why the links you control should carry tags.
  • A tag on the link. With no referrer, Virling reads utm_source, and when that is missing it reads ref. Clicks from GitHub notification emails, feed readers and links copied out of a README often arrive with no referrer. A tagged one lands in Referral with its campaign; an untagged one is Direct. When a referrer is present it decides the channel and source, and the utm_campaign on the link is still recorded.
  • Other hosts. A README shown on npmjs.com, crates.io or PyPI sends that host as the referrer, and a project site on github.io sends its own host. Each is its own Referral row, not GitHub. A visitor returning from the GitHub sign-in page continues their current visit, so Sign in with GitHub never takes the credit.

Set up GitHub revenue tracking

  1. Tag the links you control. Use one utm_source for everything on GitHub and one utm_campaign per placement, since the Campaign tab is where placements are split: 
    README:         https://yourdomain.com/?utm_source=github&utm_medium=referral&utm_campaign=readme
Website field:  https://yourdomain.com/?utm_source=github&utm_medium=referral&utm_campaign=repo-website
Release notes:  https://yourdomain.com/?utm_source=github&utm_medium=referral&utm_campaign=release-v2-4
    Keep the values lowercase and the same everywhere. Do not use utm_medium=email or cpc, which move the visit into Email or Paid. A campaign per release shows which release brought buyers; use one shared value such as releases if you only want the total. Tag the links you post in issues and discussions the same way, for example utm_campaign=issues. The UTM builder makes the links, and which UTM parameters to use covers naming.
  2. Add the script. Put the Virling tag in the <head> of every page your links point to, including docs and pricing pages. It records the referrer and tags of the first pageview and sets the visitor cookie. See add the script, and framework guides for Next.js, Astro, WordPress, Framer and Webflow.
  3. Connect a payment provider. Virling reads payments from Stripe, Paddle, Lemon Squeezy, Polar, Dodo Payments, Creem, RevenueCat, Shopify and WooCommerce; all of them are on the integrations page, with setup in the payments docs.
  4. Pass the visitor ID into checkout. If you use Stripe Payment Links, Polar checkout links or Dodo Payments links, the script adds the ID on click. For a checkout you create on your server, pass the virling_vid cookie, for example as client_reference_id on a Stripe Checkout Session. See link checkout to visits. Without this step you get visits but no revenue.

Then click your own README link in a private window and make a test payment, and check that the visit shows as GitHub and the payment is matched. How channels are decided lists every rule and known source.

Compare GitHub customers with other channels

  1. Pick a range of at least a few months, since developers often evaluate for a while before they pay.
  2. In the Channels card, switch to the Source tab and find GitHub. The row shows visitors, revenue and revenue per visitor, with a chip that compares it with your site average. Compare it with your search, community and social rows over the same range.
  3. Click the row to filter the whole page. The Pages card shows where GitHub visitors landed, and the revenue chart shows when their money arrived.
  4. Switch to the Campaign tab to split README, website field, release and issue links. Tagged clicks that arrived with no referrer are counted here too.
  5. Open a payment from the Payments page to see the buyer's journey: every visit before the payment, with the credited one marked.

Compare the default model, last non-direct, with first touch over the same range. If GitHub revenue grows under first touch, developers found you through the repository and paid after coming back through search, docs or a typed URL. The Time to pay card shows the median days from first visit to first payment per channel, and retention by channel shows whether GitHub customers keep paying. First-touch or last-touch attribution and how long a visitor takes to become a customer go deeper.

What to check when the numbers look wrong

  • GitHub looks small but Direct is large. Clicks from notification emails, desktop apps and copied links with no referrer and no tag. Tag the links you control.
  • The Campaign tab has rows the Source tab does not. Tagged clicks with no referrer count in Referral and in their campaign, but not in the GitHub source row. Read the campaigns for placements and the source row for clicks from the site itself.
  • Visits but no revenue at all. Check the Matched revenue line under the Overview numbers. If a large share of revenue is unmatched, the visitor ID is not reaching checkout. See Unattributed revenue.
  • A customer says they found you on GitHub but the payment is credited elsewhere. A later non-direct visit took the credit under the default model, the visit is outside the lookback window, or they paid from another device. Try first touch.
  • Self-hosters do not show up. People who run your open-source code on their own servers never reach your checkout, so they are not revenue. Virling measures the visitors who come to your site and pay.

Frequently asked questions

How do I track revenue from GitHub?

Add the tracking script to your site, pass the visitor ID into checkout and connect your payment provider. Visits from github.com land in the Referral channel and show as GitHub in the Source tab, and each payment is credited to a visit before it, so the GitHub row shows the visitors, customers and revenue it brought.

Why can I not see which repository or README sent a visitor?

GitHub sends only its origin, https://github.com/, as the referrer, not the page the link was on. Every click from a README, an issue, a release or the website field looks the same. Give each placement its own utm_campaign to tell them apart in the Campaign tab.

Should links in my README carry UTM tags?

Yes. The referrer already credits clicks from github.com to GitHub, but it cannot tell the README from a release note, and links copied out of the README or opened from GitHub notification emails often arrive with no referrer. A tag keeps the placement in both cases.

Does Sign in with GitHub count as a visit from GitHub?

No. A visitor returning from the GitHub sign-in page continues the visit they were already on, so the channel they first came from keeps the credit.

Does GitHub get credit if a developer pays weeks after starring the repo?

Yes, if their GitHub visit is inside the lookback window, 90 days by default, and no later non-direct visit took the credit. Switch the model to first touch to credit the visit that introduced the buyer, whatever came after. A visit in another browser or device cannot be tied to the same person.
