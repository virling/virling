SvelteKit Polar UTM tracking: see the source of each order

By Devendra Variya, co-founder of Virling. Published 2026-11-25.

For SvelteKit Polar UTM tracking, add the Virling script to src/app.html, then read the virling_vid cookie with event.cookies in the server route that creates the Polar checkout and set it in metadata. Checkout links on buy.polar.sh need no code: the script adds the ID as reference_id. Either way, Polar keeps one visitor ID on the order, and Virling joins the order to every visit behind it, with the UTM tags of each.

For the reasoning behind a visitor ID and what you see after setup, read the general guide to Polar UTM tracking and the Polar integration page. Using Stripe instead? See SvelteKit Stripe UTM tracking. On Next.js, see the Next.js version of this post. On Nuxt, see Nuxt Polar UTM tracking.

Why Polar checkout loses your UTM tags

UTM tags live on the landing URL. By the time someone clicks Buy they have usually moved to another page, and Polar checkout runs on Polar's domain, which knows only what you pass into it. You could copy the tags into checkout metadata, but that records only the visit the buyer is on when they pay. A visitor ID keeps earlier visits and untagged ones, such as search and referrals, too.

A made-up example: someone finds you through a newsletter link tagged utm_source=newsletter on Monday, leaves, and comes back on Thursday by typing your address to buy a $49 plan. The URL on Thursday has no tags, so copying tags at checkout stores nothing. With the visitor ID, the order is joined to both visits, Monday's newsletter click included.

Step 1: add the script to src/app.html

Paste the tag into src/app.html, before %sveltekit.head%. That file is the shell of every page, and client-side navigation is counted on its own. Use the domain you added in Virling as data-site. If you self-host, replace app.virling.com with your Virling server.

<!-- src/app.html -->
<head>
  <meta charset="utf-8" />
  <script defer src="https://app.virling.com/v.js"
    data-site="yourdomain.com"></script>
  %sveltekit.head%
</head>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it. Subdomains such as app.yourdomain.com share the cookie, so the marketing site and the app can be separate deployments.

Step 2a: checkout links, no code

If you sell through Polar checkout links, there is no server route to write. Keep the link to buy.polar.sh as a normal <a href> in a Svelte component on a page that runs the script:

<!-- src/routes/pricing/+page.svelte -->
<a href="https://buy.polar.sh/YOUR_CHECKOUT_LINK">Buy now</a>

The script adds reference_id=<visitor ID> to links when the page loads and again on click, so links rendered after a client-side navigation are covered. It never replaces a reference_id that is already there. Polar stores the value in the order's metadata, where Virling reads it. A virling_vid custom field on the link still works too. Opening the URL from code, for example with window.location, skips the link, so use an anchor.

Step 2b: create the checkout in a server route

If your server creates the checkout, the browser sends the virling_vid cookie with the request. First declare the Polar token in src/env.ts, as SvelteKit 3 expects for private variables:

// src/env.ts
import { defineEnvVars } from "@sveltejs/kit/env";

export const variables = defineEnvVars({
  POLAR_ACCESS_TOKEN: {},
});

Put the value in your .env.local file or your host's settings. The token needs the checkouts:write scope, and is a different one from the token you give Virling. Then add the route with Polar's TypeScript SDK, @polar-sh/sdk:

// src/routes/api/checkout/+server.ts
import { createPolar } from "@polar-sh/sdk/2026-10";
import { POLAR_ACCESS_TOKEN } from "$app/env/private";
import type { RequestHandler } from "./$types";

const polar = createPolar({ accessToken: POLAR_ACCESS_TOKEN });

export const POST: RequestHandler = async (event) => {
  const vid = event.cookies.get("virling_vid");
  const checkout = await polar.checkouts.create({
    products: ["PRODUCT_ID"],
    success_url: "https://yourdomain.com/thanks",
    metadata: vid ? { virling_vid: vid } : {},
  });
  // Send the customer to checkout.url
  return new Response(null, {
    status: 303,
    headers: { location: checkout.url },
  });
};

A plain form on any page posts to it, and the browser sends the cookie along:

<form method="POST" action="/api/checkout">
  <button type="submit">Buy</button>
</form>

Four details matter here:

  • Plain 303 response. SvelteKit 3 only lets redirect() go to another site when you pass { external: true }. Returning a Response works on versions 2 and 3.
  • No use:enhance. It is for form actions, not for a +server.ts route. Leave it off.
  • POST, not GET. Crawlers and link previews that follow links then cannot create checkouts.
  • Same origin. In production SvelteKit rejects form posts from another origin, so keep the form and the route on one domain. Behind a reverse proxy, make sure SvelteKit knows its public origin.

On SvelteKit 2, skip src/env.ts and import the token from $env/static/private. On 0.x releases of the Polar SDK, use new Polar({ accessToken }) from @polar-sh/sdk and write successUrl instead of success_url.

Virling reads virling_vid from, in order: the order's metadata, the order's custom field data, then the customer's metadata. A checkout link's reference_id is read after those. The full setup is in the Polar docs, and the checkout snippet generator writes the call for other providers.

What to do when the cookie is missing

event.cookies.get returns undefined when there is no cookie. Never block the sale for it: the route above sends empty metadata, the customer pays as usual, and the order counts toward revenue as Unattributed. Do not fall back to an empty string, because Polar requires metadata text to have at least one character. Do not make up an ID or send your user ID either, since no visit carries it.

If it is missing often, look for the cause:

  • The script did not run. It is blocked by the browser, or the buyer reached the route without opening a page that has it.
  • Cookieless mode. With data-cookieless the cookie is never set. With Until consent, it is set only after the visitor accepts.
  • A second domain. The cookie belongs to your registrable domain. If the page is on one domain and checkout on another, the cookie does not travel.
  • Localhost. The script does nothing on localhost unless the tag has data-dev.

Polar payments are not matched by email, so a missing ID cannot be filled in that way later. A later order by the same customer keeps the channel of their first order.

Step 3: connect Polar to Virling

In Polar, create an Organization Access Token with the orders:read and refunds:read scopes, plus subscriptions:read so Retention can tell who still pays, and paste it into Virling. Virling imports orders from the last 90 days on the first run, then new orders every minute. There is no webhook to add to your SvelteKit app. Orders from before the script was on your site count as revenue but are Unattributed.

Check that it works in the Polar sandbox

The sandbox is separate from production, with its own account, products and tokens.

  1. In the sandbox, create a product and two tokens: one with checkouts:write for your app, one with the read scopes for Virling. Connect the second one.
  2. Deploy a test version on your domain or a subdomain of it, with the sandbox app token, the sandbox product ID, and createPolar({ accessToken: POLAR_ACCESS_TOKEN, environment: "sandbox" }) in the route. On SDK 0.x, the option is server: "sandbox".
  3. Open a private window and visit a page that runs the script through a tagged link, such as https://yourdomain.com/?utm_source=test&utm_medium=email.
  4. In the same window, press Buy and pay with the test card 4242 4242 4242 4242, a future date and any CVC. Use a new email address for each test, because a later payment by the same customer is a renewal and keeps the first payment's channel.
  5. Wait a minute for the next sync and open the payments list at /app/yourdomain.com/payments. The payment should show the test source and the Email channel instead of Unattributed. Open it to see its journey.

Two limits to know. The script does not add the visitor ID to sandbox links, so test with a session your server creates, as above. And a site has one Polar connection: sandbox orders stay in your reports after you replace the token with a production one.

If the payment is Unattributed, open it and look for Visitor under Details. No visitor means the cookie did not reach your route or the metadata was not set. How the join works from visit to order is in how to track Polar revenue by traffic source.

Frequently asked questions

How do I pass UTM parameters to a Polar checkout in SvelteKit?

Pass the Virling visitor ID instead. In the +server.ts route that calls polar.checkouts.create, read it with event.cookies.get("virling_vid") and set metadata: { virling_vid }. The Virling script records the UTM tags of every visit against that ID, so the order is joined to all of them.

Do Polar checkout links in a SvelteKit app need code?

No. Keep the link to buy.polar.sh as a normal <a href> on a page that runs the script. The script adds reference_id=<visitor ID> to it, unless it is already there, and Polar stores it in the order's metadata, where Virling reads it.

What happens if the virling_vid cookie is missing?

Create the checkout without it. The order still counts toward revenue, as Unattributed. Do not send an empty string: Polar requires metadata text values to have at least one character.

Do I need a Polar webhook in my SvelteKit app?

Not for Virling. It reads orders from the Polar API with an organization access token and checks for new orders every minute. Your app may still want webhooks for its own work, such as granting access.

Does this work with the Polar sandbox?

Yes, for checkouts your server creates. Set environment: "sandbox" on the Polar client and connect a sandbox token to Virling. The script does not add the visitor ID to sandbox links, so test with a session that has virling_vid in its metadata.

Can I use Polar with a static SvelteKit site?

Yes, with checkout links. A site built with adapter-static has no server to run the checkout route, but links to buy.polar.sh need no server code.
