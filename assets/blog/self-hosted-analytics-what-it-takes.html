Self-hosted analytics: server size, cost and upkeep

By Devendra Variya, co-founder of Virling. Published 2026-10-26, updated 2026-11-25.

Self-hosted analytics means the tracking and the data run on a server you control, not in a vendor's cloud. It costs a small server, an hour of setup and a little attention for upgrades and backups. The tool you pick changes that a lot: some need several databases, others run as one program. If you want a self-hosted Google Analytics alternative that also shows revenue by channel, Virling is open source on GitHub.

Why teams self-host analytics

  • Data stays with you: visits are stored on your server, under your domain, and are not shared with an ad network.
  • Fewer blocked scripts: a script served from your own subdomain is blocked less often than a well-known third-party one.
  • No per-event bill: you pay for the server, not for each pageview.
  • You can read the code: with open source you can check what is collected and change it.

What server you need

Less than most people expect. In a load test on 2026-10-31, Virling ran in a container limited to one vCPU and 1 GB of RAM:

  • 100,000 pageviews were ingested at 2,829 a second, with none failed and a p99 of 34 ms
  • Memory after the ingest was 157 MB
  • Dashboard queries on the demo data took 0.6 to 7.6 ms at the median

So a 1 vCPU, 1 GB server covers 100,000 pageviews a month with room to spare. The test script is in the repository, so you can run it on your own server. For other tools, ask the vendor for the same three numbers before you buy a bigger machine than you need.

The costs you can count

  • A server: a small virtual server is enough for a young site. Price it with the provider you already use
  • A domain: a subdomain such as stats.yourdomain.com, with HTTPS
  • Storage: events pile up. Ask how much disk a million page views takes

The costs people forget

  • Upgrades: who reads the release notes and updates it, and how often
  • Backups: where the data lives and how you copy it off the machine
  • Moving parts: each extra database is another thing to patch and watch
  • Downtime: events sent while the server is down are lost, so restarts should be short

First-day checklist

For a Virling server, in this order. Each step links to its page in the docs.

  1. Server: start Virling with Docker, or as a binary under systemd, with serve --app. The first start downloads one database extension, so allow that connection
  2. Domain and HTTPS: point a subdomain such as stats.example.com at the server, put a reverse proxy in front, and set VIRLING_BASE_URL to the public address and VIRLING_TRUST_PROXY=true. Then curl -fsS https://stats.example.com/health prints ok
  3. Sign-in email: set VIRLING_SMTP_URL and VIRLING_MAIL_FROM, as in sign-in email. Without them the sign-in link is written to the server log, which is fine for one person
  4. Site and script: add your site with its owner email, sign in at /login, and put the script tag before </head> on every page
  5. Backup: take the first backup and move it off the server. Check that it holds secret.key, or keep VIRLING_SECRET_KEY in a secret store if you set that instead
  6. Test visit: open your site in a browser and check that /api/event is answered with 202 and that Script installed turns green, as in check that it works. Then run a test visit and a test payment

Monthly checklist: upgrade and restore a backup

The commands are for a container named virling with a virling-data volume, or for the systemd service with its data in /var/lib/virling. Replace X.Y.Z with the version and YYYY-MM-DD with the date of the backup. Compose adds the project name to the container and the volume, so look yours up with docker compose ps and docker volume ls.

  1. Read the changelog. Virling is in early development and releases can break things
  2. Back up the data folder
  3. Restore that backup somewhere else and check that it opens
  4. Change the image tag or replace the binary, then start it. Migrations run on start
  5. Check the health address, then sign in and look at the dashboard
  6. Move the archive off the server and keep it private. It holds secret.key

Going back after a migration ran is not supported, so a backup you have tested is the way back. Keep the stop short: events sent while the server is down are lost.

Back up

With Docker, using the version you run now:

docker stop -s INT -t 60 virling
docker run --rm --user root --entrypoint tar \
  -v virling-data:/data:ro -v "$PWD":/backup \
  ghcr.io/virling/virling:X.Y.Z \
  czf /backup/virling-$(date +%F).tar.gz -C /data .
docker start virling

With systemd:

sudo systemctl stop virling
sudo tar czf virling-$(date +%F).tar.gz -C /var/lib virling
sudo systemctl start virling

Test the backup

Start the copy without --app, so it does not sync payments or send reports, alerts and webhooks a second time. With Docker, restore into a new volume and start the image with its default command, which is plain serve:

docker volume create virling-restored
docker run --rm --user root --entrypoint tar \
  -v virling-restored:/data -v "$PWD":/backup:ro \
  ghcr.io/virling/virling:X.Y.Z \
  xzf /backup/virling-YYYY-MM-DD.tar.gz -C /data
docker run --rm -p 127.0.0.1:8099:8080 -v virling-restored:/data \
  ghcr.io/virling/virling:X.Y.Z

With the binary, with VIRLING_APP cleared from the environment if it is set there:

mkdir restore-test
tar xzf virling-YYYY-MM-DD.tar.gz -C restore-test --strip-components=1
virling serve --data-dir restore-test --addr 127.0.0.1:8099

From a second terminal, ask the copy. If it prints ok, both databases opened:

curl -fsS http://127.0.0.1:8099/health

Stop the copy with Ctrl+C, and remove the virling-restored volume or the restore-test folder before the next test. To put a backup back for real, follow the restore steps for Docker or the binary.

Upgrade

With Docker, pull the new version, remove the old container and run your usual docker run command with the new tag. The data stays in the volume:

docker pull ghcr.io/virling/virling:X.Y.Z
docker rm -f virling
# then the same docker run command with the new tag

With systemd, the install script replaces the binary and restarts the service. It keeps your environment file:

curl -fsSL https://virling.com/install.sh | sh -s -- --version X.Y.Z
curl -fsS http://127.0.0.1:8080/health

Questions to ask before you pick

  • How many services does it need to run?
  • What is the smallest server it has been measured on?
  • Where is the data stored and how do I back it up?
  • Can I upgrade by changing one version number?
  • What happens if the server restarts?
  • Can it show which visits led to a payment, or only page views?

What it looks like with Virling

Virling is one program with its own embedded storage, so there is no separate database to run. You run it with Docker or a release binary, point a domain at it and keep one data folder. That folder holds the event database, the settings database and the key that encrypts your payment provider keys, so back them up together. Pin a version, read the changelog before you upgrade, and copy the folder on a schedule. The steps are in the Docker guide, the backup guide and the self-host page. You can also run a site without cookies; cookieless analytics and revenue covers what that keeps and what it loses.

When hosted is the better choice

If nobody on your team wants to look after a server, use the hosted version. Self-hosting is free in money and costs time; hosting costs money and saves it. With an open-source tool you can start hosted and move to your own server later, or the other way round. Frequently asked questions

What is self-hosted analytics?

Website analytics that runs on a server you control instead of the vendor's cloud. The tracking script sends visits to your own domain, and the data stays on your machine.

What server do I need to self-host analytics?

For Virling, one vCPU and 1 GB of RAM handled 100,000 pageviews a month in a load test, using 157 MB of memory. Tools that need several databases need more.

How much does it cost to self-host analytics?

A small server, a domain and some time. The software can be free; the real cost is the hours spent on upgrades and backups.

What should I back up?

The data folder. For Virling that is one folder holding the event database, the settings database and the secret key.

Is self-hosting analytics hard?

With a tool that runs as one program, it takes about an hour. Tools that need several databases take longer and need more upkeep.

Is self-hosted analytics GDPR friendly?

It helps, because visitor data never leaves your server. You still need a lawful basis and a privacy notice, so check with your own adviser.
