How to track Stripe revenue by traffic source

By Devendra Variya, co-founder of Virling. Published 2026-10-26, updated 2026-11-25.

To track Stripe revenue by traffic source, put the visitor ID on the Stripe object your checkout creates, then let Virling read the charge and credit it to that visitor's earlier visits. Without it, Stripe only knows who paid and how much, and the payment lands in Unattributed. How the visit and the payment are joined, for every provider, is in link checkout to visits.

Stripe has four common ways to take money, and each one keeps the ID in a different field. The ID itself is the value of the first-party virling_vid cookie, which your server receives with each request once the script has run.

Where the visitor ID goes on each Stripe checkout

How you sellField that carries the IDHow Virling finds it from the charge
Checkout Sessionsclient_reference_id, or metadata.virling_vid on the sessionLooks up the session through the charge's PaymentIntent, or through the subscription for a subscription's first invoice
Payment Linksclient_reference_id, added to the link by the scriptStripe copies it onto the Checkout Session the link opens
Elements with your own PaymentIntentmetadata.virling_vid on the PaymentIntentReads the PaymentIntent the charge belongs to
Invoices without a subscriptionmetadata.virling_vid on the charge or its PaymentIntentReads only those two, since no Checkout Session is looked up

Checkout Sessions

Set client_reference_id when your server creates the session:

const session = await stripe.checkout.sessions.create({
  client_reference_id: req.cookies.virling_vid,
  line_items: [{ price: "price_...", quantity: 1 }],
  mode: "subscription",
  success_url: "https://yourdomain.com/thanks",
});

If you already use client_reference_id for your own user ID, put the visitor ID in the session's metadata.virling_vid, which Virling reads first. An ID of your own in client_reference_id is read as a visitor ID and matches no visit. The field's limits and other uses are in Stripe client_reference_id.

Payment Links

Links to buy.stripe.com need no code. The Virling script adds client_reference_id to them when the page loads and again on click, and never replaces a value that is already on the link. That only works for a plain link on a page that runs the script: a Payment Link opened from an email, a QR code or another site carries no visitor ID.

Elements and your own PaymentIntent

When you build the payment form yourself, there is no Checkout Session, so put the ID in the PaymentIntent's metadata:

const intent = await stripe.paymentIntents.create({
  amount: 4900,
  currency: "usd",
  metadata: { virling_vid: req.cookies.virling_vid },
});

The cookie is created in the browser, so the very first request of a visit does not have it yet. If a buyer can reach checkout on their first page, read window.virling?.vid?.() in the browser and send it with the request that creates the PaymentIntent. The checkout snippet generator writes this code for your setup.

Invoices

A subscription's first invoice has billing_reason set to subscription_create, and Virling finds its visitor through the Checkout Session that started the subscription. For an invoice without a subscription, Virling reads only the charge and its PaymentIntent, so set metadata.virling_vid there. An invoice marked as paid outside Stripe has no charge and is not imported.

The order Virling looks for a visitor

For each Stripe charge, Virling takes the first visitor ID it finds:

  1. metadata.virling_vid on the charge.
  2. metadata.virling_vid, then client_reference_id, on the Checkout Session that created it.
  3. metadata.virling_vid on its PaymentIntent.
  4. For a charge with no visitor ID in any of these, the payer's email.

Renewals and billing_reason

Renewal charges come from invoices Stripe creates on its own, so they never carry the ID you set at checkout. Virling looks at the invoice's billing_reason instead:

  • subscription_create: the first payment, credited through its Checkout Session as above.
  • subscription_cycle: a renewal, which keeps the channel of the customer's first payment.
  • subscription_update: a plan change, which is also treated as a renewal.

Any later charge of the same customer keeps that first channel too. If a free trial started through Checkout after you connected Stripe, the first real charge is credited to the visit before the trial when it has no visitor ID of its own. The full rule is in subscription renewal attribution.

The email match fallback

When a checkout carries no ID, Virling can still credit a Stripe payment if your site told it the visitor's email. Send an identify event once you know the email, for example from your server right after signup:

await fetch("https://app.virling.com/api/event", {
  method: "POST",
  headers: { "user-agent": req.headers["user-agent"] },
  body: JSON.stringify({
    n: "identify",
    u: "https://yourdomain.com/signup",
    s: "yourdomain.com",
    v: req.cookies.virling_vid,
    m: user.email,
  }),
});

Virling keeps only a salted SHA-256 hash of the address. It compares it with the charge's billing email, or its receipt email when there is none, and a match shows as Matched by email on the payment. The limits:

  • The match is exact, apart from capitals and spaces around the address, so a customer who pays with another email is not matched.
  • It never replaces an ID that reached Stripe, even a wrong one.
  • It only applies to payments synced after the identify event, and never across sites.
  • It finds the visitor, not a visit. If none of that visitor's visits falls inside the lookback window, the payment stays Unattributed.

Forward the visitor's User-Agent, since events with an empty or bot user agent are dropped. The other fields are in the Event API reference.

Test it in Stripe test mode

  1. Create a restricted key with the Read permissions listed in the Stripe docs and connect it. It starts with rk_test_. Secret keys are refused.
  2. In a private window, land on your site through https://yourdomain.com/?utm_source=test&utm_medium=email.
  3. Pay with a Stripe test card through a test Checkout Session your server creates with the visitor ID, or a test Payment Link on buy.stripe.com.
  4. After the next sync, about a minute, the payment at /app/yourdomain.com/payments shows the test source and the Email channel.

If your server sets customer, use a new customer for each test, because a later charge of the same customer counts as a renewal. If the payment says Unattributed, open it and look for Visitor under Details. No visitor ID means none of the fields in the table above carried one. A visitor ID with no channel means no visit of that visitor was recorded inside the lookback window, often because it is your own ID rather than the virling_vid cookie. Every other cause is in Unattributed revenue.

Frequently asked questions

Can Stripe show which traffic source a payment came from?

Not by itself. A Stripe charge has no record of the page or link the buyer came from. Put the virling_vid cookie value on the Checkout Session or PaymentIntent, and Virling joins the charge to that visitor's visits.

Should I use client_reference_id or metadata?

Either works on a Checkout Session. Use metadata.virling_vid if client_reference_id already holds your own user ID, and on a PaymentIntent, which has no client_reference_id.

Does this work with Payment Links?

Yes. The Virling script adds client_reference_id to buy.stripe.com links on the page, and the value is stored on the resulting Checkout Session. A link opened from an email or a QR code carries no visitor ID.

Which Stripe billing_reason counts as a renewal?

subscription_cycle and subscription_update. Those charges keep the channel of the customer's first payment, while a subscription_create invoice is the first payment and is credited through its Checkout Session.

What happens to Stripe payments without a visitor ID?

Virling tries the payer's billing or receipt email against emails you sent in identify events. If one matches, the payment is credited to that visitor and shows Matched by email. If not, it counts toward revenue as Unattributed.

Does Virling need write access to Stripe?

No. It uses a restricted key with Read access only, and refuses secret keys, so it cannot change anything in your Stripe account.
