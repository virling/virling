How to track Stripe revenue by traffic source

By Devendra Variya, co-founder of Virling. Published 2026-10-26, updated 2026-11-25.

To track Stripe revenue by traffic source, give each visitor an ID, pass that ID into Stripe when they check out, and join each payment back to the visits that came before it. Stripe knows who paid and how much. It does not know which page or channel they came from.

Step 1: set a visitor ID

Your analytics script sets one first-party ID per visitor and remembers the first source: referrer, UTM tags or direct.

Step 2: send the ID to Stripe at checkout

The visitor ID lives in the virling_vid cookie, a first-party cookie on your domain, so your server receives it with every request. Pick the option that matches how you sell.

Checkout Session. Set client_reference_id when your server creates the session:

const session = await stripe.checkout.sessions.create({
  client_reference_id: req.cookies.virling_vid,
  line_items: [{ price: "price_...", quantity: 1 }],
  mode: "subscription",
  success_url: "https://yourdomain.com/thanks",
});

Your own PaymentIntent (Elements). Put the ID in metadata:

const intent = await stripe.paymentIntents.create({
  amount: 4900,
  currency: "usd",
  metadata: { virling_vid: req.cookies.virling_vid },
});

Payment Links. Links to buy.stripe.com need no code. The Virling script adds client_reference_id to them when the page loads and again on click, and never replaces a value that is already on the link.

In the browser. window.virling?.vid?.() returns the same ID. The script loads with defer, so if your checkout code can run before it, wait for it:

async function visitorId() {
  for (let i = 0; i < 20 && !window.virling?.vid; i++) {
    await new Promise((r) => setTimeout(r, 100));
  }
  return window.virling?.vid?.() || null;
}

The checkout snippet generator writes this code for your setup. Now every payment carries the visitor who made it.

Step 3: read payments and join them to visits

Read payments from Stripe with a read-only key, then match each one's ID to that visitor's earlier visits. Credit one of them with a rule you keep fixed (see first touch or last touch).

The order Virling looks for a visitor

For each Stripe charge, Virling takes the first visitor ID it finds:

  1. metadata.virling_vid on the charge.
  2. metadata.virling_vid, then client_reference_id, on the Checkout Session that created it.
  3. metadata.virling_vid on its PaymentIntent.
  4. For a charge with no visitor ID in any of these, the payer's email.

If you already use client_reference_id for your own ID, put the visitor ID in the session's metadata.virling_vid. An ID of your own is read as a visitor ID and matches no visit. The field's limits and its other uses are in Stripe client_reference_id. For an invoice without a subscription, Virling reads only the charge and its PaymentIntent, so set the metadata there.

A later payment by the same customer, such as a renewal, keeps the channel of that customer's first payment. The rule is in subscription renewal attribution.

What an email match can and cannot do

It can credit a payment whose checkout carried no ID, if your site sent that visitor's email in an identify event, for example after signup. Virling compares it with the charge's billing email, or its receipt email when there is none. The payment then shows Matched by email. It cannot do everything an ID does:

  • The match is exact, apart from capitals and spaces around the address, so a customer who pays with another email is not matched.
  • It never replaces an ID that reached Stripe, even a wrong one.
  • It only applies to payments synced after the identify event, and never across sites.
  • It finds the visitor, not a visit. If none of that visitor's visits falls inside the lookback window, the payment stays Unattributed.

Once your Stripe payments are joined, the Campaign tab on Virling's Channels card lists visitors, revenue and revenue per visitor for each campaign you tagged.

Step 4: report revenue per channel

Group the joined payments by channel and divide by visitors to get revenue per visitor. That is the table that tells you where to spend time. For total MRR from a Stripe subscriptions export, use the Stripe MRR calculator.

Server-side tracking

Payments need no server-side tracking: Virling reads them from Stripe. For things only your server sees, such as a signup or a checkout started from your backend, send an event to POST /api/event with the visitor ID from the cookie as v, so it joins the same visitor:

await fetch("https://app.virling.com/api/event", {
  method: "POST",
  headers: { "user-agent": req.headers["user-agent"] },
  body: JSON.stringify({
    n: "goal",
    g: "signup",
    u: "https://yourdomain.com/signup",
    s: "yourdomain.com",
    v: req.cookies.virling_vid,
  }),
});

Forward the visitor's User-Agent: requests with an empty or bot user agent are dropped. The page URL in u must be on the site's domain or a subdomain. The endpoint answers 202 once the body parses, even when an event is dropped, and accepts an array of up to 50 events. Self-hosted, use your own server's address.

When checkout cannot carry the ID, for example a Payment Link opened from an email, send an identify event with the visitor's email after signup. Virling keeps only a salted SHA-256 hash of it, and a later Stripe payment with no visitor ID whose payer email matches is credited to that visitor:

body: JSON.stringify({
  n: "identify",
  u: "https://yourdomain.com/signup",
  s: "yourdomain.com",
  v: req.cookies.virling_vid,
  m: user.email,
}),

The full field list is in the Event API reference.

Check that it works

  1. In Stripe test mode, create a restricted key with the Read permissions listed in the Stripe docs, and connect it. It starts with rk_test_.
  2. Open a private window and visit a page that runs the script through a tagged link, such as https://yourdomain.com/?utm_source=test&utm_medium=email.
  3. In the same window, go to a test Checkout Session your server creates with the visitor ID, or click a test Payment Link on buy.stripe.com, and pay with one of Stripe's test cards.
  4. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed.

If your server sets customer, use a new customer for each test, because a later payment by the same customer keeps the first payment's channel. A site has one Stripe connection, and test payments stay in your reports after you replace the key with a live one.

If the payment says Unattributed, open it and look for Visitor under Details:

  • No visitor ID: checkout did not carry one. Check in Stripe that the Checkout Session has a client_reference_id, or that the PaymentIntent has virling_vid in its metadata, and that your server reads the cookie on the request that creates the checkout.
  • A visitor ID: no visit of that visitor was recorded inside the lookback window. Check that it is the value of your virling_vid cookie and not an ID of your own, and that the script ran on the page you landed on.

Every other cause is in Unattributed revenue, and the full checklist is in test your setup.

What goes wrong

  • Forgetting step 2: payments arrive with no visitor and show as Unattributed
  • Using a different ID in the script and in checkout, so nothing matches
  • Running the script on the marketing site but not on the page that creates the checkout, so the ID never reaches Stripe

Frequently asked questions

Can Stripe show which traffic source a payment came from?

Not on its own. Stripe records the payment, not the visit. You need to pass a visitor ID into checkout and join it to your analytics.

Should I use client_reference_id or metadata?

Either works. client_reference_id is a single dedicated field, and metadata is useful when you also store other values.

Does this work with Payment Links?

Yes. The Virling script adds client_reference_id to buy.stripe.com links on the page, and the value is stored on the resulting Checkout Session. A link opened from an email or a QR code carries no visitor ID.

What if my checkout code runs before the script loads?

window.virling.vid is not there yet, so wait for it for up to two seconds, or read the virling_vid cookie on your server instead. In cookieless mode there is no visitor ID to pass.

What happens to Stripe payments without a visitor ID?

They still count toward revenue, as Unattributed. If you sent an identify event with the visitor's email, a payment whose payer email matches is credited to that visitor instead.

Can I send events to Virling from my server?

Yes. POST them to /api/event with the visitor ID from the virling_vid cookie and the visitor's User-Agent. Payments themselves are read from Stripe, so they need no event.

Does Virling need write access to Stripe?

No. It uses a restricted key with Read access only, and refuses secret keys, so it cannot change anything in your Stripe account.
