Track Stripe revenue by traffic source in an AI-built app

By Devendra Variya, co-founder of Virling. Published 2026-11-19.

If you built your app with Lovable, Bolt, Replit or Cursor and added Stripe, you can see which channel brings paying users in four steps:

  1. Add your site in Virling and connect Stripe with a read-only restricted key.
  2. Give your coding assistant the prompt below. It adds the Virling script to every page and passes the visitor ID from the virling_vid cookie to the Checkout Session as client_reference_id.
  3. Make one test payment from a page that runs the script.
  4. Open the payments list: each payment shows the channel of the visit behind it.

Why Stripe alone cannot tell you the channel

Stripe knows who paid and how much. It does not know that the buyer first came from a Reddit thread or an AI answer, because Checkout runs on Stripe's domain and only stores what your server passes when it creates the session. UTM tags on the landing URL are gone by then. Passing one visitor ID fixes that: Stripe keeps the ID, and Virling joins the payment to every visit behind it, including untagged ones such as search and referrals. The full method is in how to track Stripe revenue by traffic source.

Step 1: add your site and connect Stripe

Sign up, add your domain, and paste a Stripe restricted key with Read access on Charges, Checkout Sessions, Customers, Events, Invoices, Subscriptions and PaymentIntents. Virling refuses secret keys, so it can never write to your Stripe account. The steps are in the Stripe docs.

Step 2: paste this prompt into your coding assistant

Replace yourdomain.com with your domain, exactly as you added it. If you self-host Virling, replace app.virling.com with your server; the setup screen in the app shows the exact tag for your site.

Add Virling revenue tracking to this app. Make only these two changes.

1. Add this tag to the <head> of every page, before </head>, so it loads on every route:
<script defer src="https://app.virling.com/v.js" data-site="yourdomain.com"></script>
Keep defer. data-site is my domain without www. and without a path.

2. Find the server code that creates the Stripe Checkout Session and pass the visitor ID:
- Read the virling_vid cookie from the request and set it as client_reference_id on the session.
- If client_reference_id is already used for something else, leave it and set metadata: { virling_vid: ... } on the session instead.
- If the code that creates the session runs on another domain and does not receive my cookies (for example a Supabase Edge Function), read the ID in the browser with window.virling?.vid?.() and send it in the request body. That function returns nothing until the deferred script has loaded, so wait up to 2 seconds for window.virling.vid before reading it, and skip it if it is still missing.
- Do not change prices, products, success_url or anything else in checkout.
- buy.stripe.com Payment Links need no change: the Virling script adds client_reference_id to them.

The prompt follows the script docs and checkout docs. Review the diff before you accept it: the change to checkout should be one or two lines.

What the change should look like

On a Node server, the Checkout Session gets one new line:

const session = await stripe.checkout.sessions.create({
  client_reference_id: req.cookies.virling_vid,
  line_items: [{ price: "price_...", quantity: 1 }],
  mode: "subscription",
  success_url: "https://yourdomain.com/thanks",
});

If the session is created on another domain, the browser reads the ID and sends it along. The wait covers the deferred script loading after your checkout code:

async function visitorId() {
  for (let i = 0; i < 20 && !window.virling?.vid; i++) {
    await new Promise((r) => setTimeout(r, 100));
  }
  return window.virling?.vid?.() || null;
}

The checkout snippet generator writes this code for your provider and setup if you would rather check it by hand.

Step 3: check it with a test payment

Open your site in a new tab and make a test payment from a page that runs the script. After the next sync, open the payments list in the app. The payment should show a channel instead of Unattributed; open it to see the visits before it. Payments without a visitor ID still count toward revenue, as Unattributed.

The script does not track on localhost, and events from pages on a host other than your domain are dropped, so test on your deployed site, not in the preview inside your builder.

Step 4: ask which channel pays

Once payments carry a channel, you can read revenue by channel, referrer and campaign in the app, or ask your AI assistant. Virling serves a read-only MCP endpoint, so Claude and other assistants that speak MCP can answer "which channel made the most money last month?". The setup is in ask Claude which channel pays.

Frequently asked questions

Do I need to write code myself?

No. Paste the prompt into your coding assistant and it makes the two changes: the script tag in the head of every page, and the visitor ID on the Checkout Session. Then check the result with one test payment.

My checkout runs in a Supabase Edge Function. Does the cookie reach it?

Usually not. The virling_vid cookie is set on your domain, so a function on another domain does not receive it. Read the ID in the browser with window.virling?.vid?.() and send it in the request body, then pass it as client_reference_id.

What if I use Stripe Payment Links?

They need no code. With the Virling script on the page, it adds client_reference_id to every buy.stripe.com link when the page loads and again on click, and never replaces a value that is already there.

My app already sets client_reference_id. What then?

Keep it, and put the visitor ID in metadata.virling_vid on the Checkout Session instead. Virling reads metadata.virling_vid first, then client_reference_id.

Can I ask my AI assistant which channel pays?

Yes. Virling serves a read-only MCP endpoint, so Claude and other assistants that speak MCP can answer questions such as which channel made the most revenue last month.
