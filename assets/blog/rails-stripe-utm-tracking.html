Rails Stripe UTM tracking: Checkout and the Pay gem

By Devendra Variya, co-founder of Virling. Published 2026-11-20, updated 2026-11-25.

Rails Stripe UTM tracking comes down to one value. Load the Virling script in your application layout, then read the virling_vid cookie with cookies[:virling_vid] in the controller that creates the Stripe Checkout Session and pass it as client_reference_id, or as metadata.virling_vid in the Pay gem's checkout options. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each.

This post covers Rails with stripe-ruby and with Pay. The same steps for other stacks are in Phoenix Stripe UTM tracking, Laravel Stripe UTM tracking and Next.js Stripe UTM tracking. Selling through Paddle instead? See Rails Paddle UTM tracking. For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Step 1: add the script to the application layout

Paste the tag before </head> in app/views/layouts/application.html.erb. If you self-host, replace app.virling.com with your Virling server.

<!-- app/views/layouts/application.html.erb -->
<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it. With Turbo, page visits use history.pushState, so each one is counted.

Step 2: create the Checkout Session in a controller

Your server receives the cookie with every request from the browser. The script sets it as a plain cookie, so read it with cookies[:virling_vid], not cookies.signed or cookies.encrypted. With stripe-ruby, read it where you create the session and pass it as client_reference_id:

# app/controllers/checkouts_controller.rb
class CheckoutsController < ApplicationController
  def create
    session_params = {
      line_items: [{ price: "price_...", quantity: 1 }],
      mode: "subscription",
      success_url: "https://yourdomain.com/thanks",
    }
    vid = cookies[:virling_vid]
    session_params[:client_reference_id] = vid if vid.present?

    checkout_session = Stripe::Checkout::Session.create(session_params)
    redirect_to checkout_session.url, allow_other_host: true, status: :see_other
  end
end

This assumes Stripe.api_key is set in an initializer. Add resource :checkout, only: :create to config/routes.rb and post to it from a view. Turn Turbo off for this form, so the browser follows the redirect to Stripe's domain itself:

<%= button_to "Subscribe", checkout_path, form: { data: { turbo: false } } %>

With the Pay gem

Pay's checkout takes Checkout Session options and sends the ones it does not handle itself to Stripe when it creates the session. Add the visitor ID there. This example uses metadata.virling_vid, so client_reference_id stays free for your own ID; Virling reads either:

def create
  current_user.set_payment_processor :stripe
  options = {
    mode: "subscription",
    line_items: "price_...",
    success_url: "https://yourdomain.com/thanks",
    cancel_url: "https://yourdomain.com/pricing",
  }
  vid = cookies[:virling_vid]
  options[:metadata] = { virling_vid: vid } if vid.present?

  checkout_session = current_user.payment_processor.checkout(**options)
  redirect_to checkout_session.url, allow_other_host: true, status: :see_other
end

The full lookup order, including PaymentIntents you create for Stripe Elements, is in the Stripe docs, and the Stripe integration page shows what Virling imports. How to pass the visitor ID with other providers is in link checkout to visits, and the script tag for other frameworks in the framework docs.

Subscriptions and renewals

Only the first payment needs the visitor ID: each renewal keeps the channel of the customer's first payment, with no code on your side, as described in renewals. Set the visitor ID on the Checkout Session, not only on the subscription:

session_params = {
  mode: "subscription",
  line_items: [{ price: "price_...", quantity: 1 }],
  success_url: "https://yourdomain.com/thanks",
  # Virling does not read the subscription's metadata
  subscription_data: { metadata: { plan: "pro" } },
}
vid = cookies[:virling_vid]
# Virling reads this one, on the session
session_params[:metadata] = { virling_vid: vid } if vid.present?

If the buyer already has a Stripe customer, pass its ID as customer so a plan they buy later is matched to their first payment. Pay does this for you. A free trial that starts through Checkout after you connect Stripe is kept too: its first charge is credited to the visit before the trial.

Check that it works

Run one tagged visit and one test payment through the form that posts to checkouts#create, as in test your setup. Connect a restricted Stripe key that starts with rk_test_ in Virling; your app keeps its own test secret key in Stripe.api_key and uses a price created in test mode.

To see the visitor ID on the Checkout Session, add this right after the session is created, with stripe-ruby or with Pay, and remove it afterwards. client_reference_id, or virling_vid in the session's metadata, should match window.virling.vid() in the browser console:

Rails.logger.info "#{checkout_session.id} #{checkout_session.client_reference_id} #{checkout_session.metadata.to_h}"

If the host you test on runs in the development environment, add it to config.hosts. Pay creates the session for the signed-in user's Stripe customer, so sign in as a new user for each test: a later payment by the same customer is a renewal and keeps the first payment's channel. With stripe-ruby, do the same if you pass customer.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Stripe revenue by traffic source, and the SaaS page shows what you get per channel.

Open an Unattributed payment and look for Visitor under Details. If there is none, checkout did not carry the ID.

Caching an ordinary page is fine, because the script sets the cookie in the browser. Checkout requests have to reach your server with their cookies, as in page caching and CDNs. Every other cause is in Unattributed revenue. A payment made before a fix usually stays Unattributed, so make a new one to check.

Frequently asked questions

How do I pass UTM parameters to Stripe Checkout in Rails?

Read the visitor ID with cookies[:virling_vid] in the controller that creates the Checkout Session and pass it as client_reference_id. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

How do I add the visitor ID with the Pay gem?

Pass it in the options of payment_processor.checkout, for example metadata: { virling_vid: cookies[:virling_vid] }. Pay sends those options to Stripe when it creates the Checkout Session. client_reference_id works there too.

Should I use client_reference_id or metadata.virling_vid?

Use client_reference_id unless it already holds your own user or order ID. In that case put the visitor ID in the session's metadata.virling_vid. Virling reads either.

What happens if the cookie is missing?

cookies[:virling_vid] is nil, so vid.present? is false and the session is created without client_reference_id, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.
