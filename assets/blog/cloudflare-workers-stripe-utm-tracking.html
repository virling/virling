Cloudflare Workers and Stripe UTM tracking: Checkout from a Worker

By Devendra Variya, co-founder of Virling. Published 2026-11-22.

Cloudflare Workers and Stripe UTM tracking comes down to one value. Load the Virling script on your pages, then read the virling_vid cookie from the request in the Worker that creates the Stripe Checkout Session and pass it as client_reference_id, or as metadata.virling_vid if that field is taken. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each, so each payment shows the channel that brought it.

This post covers a Worker with a plain fetch handler and the same thing with Hono, in TypeScript. For a Node server, see Express Stripe UTM tracking, and for the App Router, Next.js Stripe UTM tracking. For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Why Stripe Checkout loses your UTM tags

UTM tags live on the landing URL. Stripe Checkout runs on Stripe's domain and only stores what your Worker passes when it creates the session, so the tags of the visit are gone unless you carry them over. The same thing happens on any redirect that drops the query string, as covered in UTM parameters lost after redirect. Passing one visitor ID instead of the tags keeps earlier visits and untagged ones, such as search and referrals, too.

Step 1: add the script to your pages

Paste the tag before </head> in the HTML or layout every page uses, whether the pages come from Cloudflare Pages, Workers static assets or another host on your domain. If you self-host, replace app.virling.com with your Virling server.

<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: create the Checkout Session in the Worker

When the Worker runs on your domain or one of its subdomains, through a route or a custom domain, the browser sends the cookie with every request. Read it from the Cookie header where you create the session and pass it as client_reference_id:

// src/index.ts
import Stripe from "stripe";

interface Env {
  STRIPE_SECRET_KEY: string;
}

function visitorId(req: Request): string | undefined {
  const m = (req.headers.get("Cookie") ?? "").match(/(?:^|;\s*)virling_vid=([A-Za-z0-9-]{8,64})(?:;|$)/);
  return m ? m[1] : undefined;
}

export default {
  async fetch(req: Request, env: Env): Promise<Response> {
    const url = new URL(req.url);
    if (req.method !== "POST" || url.pathname !== "/checkout") {
      return new Response("Not found", { status: 404 });
    }

    const stripe = new Stripe(env.STRIPE_SECRET_KEY, {
      httpClient: Stripe.createFetchHttpClient(),
    });

    const session = await stripe.checkout.sessions.create({
      client_reference_id: visitorId(req),
      line_items: [{ price: "price_...", quantity: 1 }],
      mode: "subscription",
      success_url: "https://yourdomain.com/thanks",
    });

    return Response.redirect(session.url!, 303);
  },
} satisfies ExportedHandler<Env>;

Set the key with npx wrangler secret put STRIPE_SECRET_KEY and deploy with npx wrangler deploy. When the cookie is missing, visitorId() returns undefined and the stripe library leaves the field out. The pattern also keeps anything that is not a visitor ID out of Stripe. A plain form posts to the Worker, and the browser sends the cookie along:

<form action="/checkout" method="POST">
  <button type="submit">Subscribe</button>
</form>

The same route with Hono

Hono reads cookies with getCookie from hono/cookie, and the secret comes from c.env:

// src/index.ts
import { Hono } from "hono";
import { getCookie } from "hono/cookie";
import Stripe from "stripe";

const app = new Hono<{ Bindings: { STRIPE_SECRET_KEY: string } }>();

app.post("/checkout", async (c) => {
  const stripe = new Stripe(c.env.STRIPE_SECRET_KEY, {
    httpClient: Stripe.createFetchHttpClient(),
  });
  const vid = getCookie(c, "virling_vid");

  const session = await stripe.checkout.sessions.create({
    client_reference_id: vid && /^[A-Za-z0-9-]{8,64}$/.test(vid) ? vid : undefined,
    line_items: [{ price: "price_...", quantity: 1 }],
    mode: "subscription",
    success_url: "https://yourdomain.com/thanks",
  });

  return c.redirect(session.url!, 303);
});

export default app;

When client_reference_id is taken

If you already use client_reference_id for your own user or order ID, put the visitor ID in the session's metadata instead. Virling reads either:

  const vid = visitorId(req);
  const session = await stripe.checkout.sessions.create({
    client_reference_id: user.id, // your own ID stays
    metadata: vid ? { virling_vid: vid } : {},
    line_items: [{ price: "price_...", quantity: 1 }],
    mode: "subscription",
    success_url: "https://yourdomain.com/thanks",
  });

If you create your own PaymentIntent for Elements instead of a Checkout Session, set the same metadata on stripe.paymentIntents.create(). The full lookup order is in the Stripe docs and in link checkout to visits, and the Stripe integration page shows what Virling imports.

When the Worker is on workers.dev

The browser only sends the cookie to your own domain and its subdomains, so a Worker on a workers.dev address never sees it. Either move the Worker onto a route or custom domain, or read the ID in the browser with window.virling?.vid?.() and send it in the request body. The script loads with defer, so wait for it:

async function visitorId() {
  for (let i = 0; i < 20 && !window.virling?.vid; i++) {
    await new Promise((r) => setTimeout(r, 100));
  }
  return window.virling?.vid?.() || null;
}

async function checkout() {
  const res = await fetch("https://checkout.example.workers.dev/checkout", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ vid: await visitorId() }),
  });
  location.href = (await res.json()).url;
}

In the Worker, answer the browser's OPTIONS preflight with Access-Control-Allow-Origin set to your site, read vid from await req.json() with the same pattern check, and return { url: session.url } instead of redirecting. The ID is null in cookieless mode, and the payment then counts as Unattributed.

Subscriptions and renewals

Only the first payment needs the visitor ID. A renewal takes the attribution of the customer's first payment, so each monthly or yearly charge of the subscription is credited to the same visit, with no code on your side.

Check that it works

Make a test payment from a page on your live site that runs the script, wait for the next sync, and open the payments list at /app/yourdomain.com/payments. The payment should show a channel instead of Unattributed. Open it to see its journey. The script does not track on localhost, so test on your deployed site, not with wrangler dev.

If it still shows Unattributed, open the Checkout Session in the Stripe Dashboard and look for the visitor ID in client_reference_id or the metadata. If it is empty, check that the page you bought from loads the script and that the checkout request goes to your domain or one of its subdomains, so the cookie is sent. Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Stripe revenue by traffic source.

Frequently asked questions

How do I pass UTM parameters to Stripe Checkout from a Cloudflare Worker?

Read the visitor ID from the virling_vid cookie in the Worker that creates the Checkout Session and pass it as client_reference_id. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

Does the virling_vid cookie reach my Worker?

Only when the Worker runs on your own domain or one of its subdomains, for example through a route or custom domain. On a workers.dev address the browser does not send it, so read the ID in the browser with window.virling?.vid?.() and send it in the request body.

Should I use client_reference_id or metadata.virling_vid?

Use client_reference_id unless it already holds your own user or order ID. In that case put the visitor ID in the session's metadata.virling_vid. Virling reads either.

Are subscription renewals attributed?

Yes. A renewal takes the attribution of the customer's first payment, so every monthly or yearly charge is credited to the visit that led to the first one, even though the renewal itself has no visit.

What happens if the visitor ID is missing?

The session is created without one, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.
