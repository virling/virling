Phoenix Elixir Stripe UTM tracking: controllers and LiveView

By Devendra Variya, co-founder of Virling. Published 2026-11-24.

Phoenix Elixir Stripe UTM tracking comes down to one value. Load the Virling script in root.html.heex, read the virling_vid cookie from the conn in the controller that creates the Stripe Checkout Session, and pass it as client_reference_id. A LiveView cannot read cookies from its socket, so post a form to that controller, or read the cookie before the LiveView mounts. Virling joins the payment to every visit behind that ID, with the UTM tags of each.

This post covers Phoenix with the community library stripity_stripe. The code follows the Phoenix 1.8, LiveView 1.2 and Stripe documentation linked in each step. For another stack, see Next.js Stripe UTM tracking or Rails Stripe UTM tracking. For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Step 1: add the script to the root layout

Paste the tag before </head> in lib/my_app_web/components/layouts/root.html.heex, the base template around every page, LiveViews included (Phoenix layouts). If you self-host, replace app.virling.com with your Virling server.

<%!-- lib/my_app_web/components/layouts/root.html.heex --%>
<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it. LiveView navigation uses history.pushState, so each page is counted.

Step 2: read the cookie on the server

The browser sends the cookie with every HTTP request. In a controller, read it with get_cookies/1 (Plug.Conn):

vid = get_cookies(conn)["virling_vid"]

The cookies must be fetched first. The default :browser pipeline does it, since fetch_session also fetches cookies (Plug.Conn). The cookie is plain, so it needs no :signed or :encrypted option. When it is not there, the value is nil.

Step 3: create the Checkout Session with client_reference_id

Add {:stripity_stripe, "~> 3.3"} to mix.exs and set the key in config/runtime.exs (stripity_stripe):

config :stripity_stripe, api_key: System.get_env("STRIPE_SECRET_KEY")

This controller takes a one-time payment (Stripe.Checkout.Session) and redirects to Stripe with :external, which Phoenix requires for a URL outside the app (Phoenix controllers):

# lib/my_app_web/controllers/checkout_controller.ex
defmodule MyAppWeb.CheckoutController do
  use MyAppWeb, :controller

  def create(conn, _params) do
    params =
      put_visitor(
        %{
          line_items: [%{price: "price_...", quantity: 1}],
          mode: :payment,
          success_url: "https://yourdomain.com/thanks"
        },
        get_cookies(conn)["virling_vid"]
      )

    case Stripe.Checkout.Session.create(params) do
      {:ok, session} ->
        conn
        |> put_status(:see_other)
        |> redirect(external: session.url)

      {:error, _error} ->
        conn
        |> put_flash(:error, "Checkout is not available right now.")
        |> redirect(to: ~p"/")
    end
  end

  defp put_visitor(params, vid) when vid in [nil, ""], do: params
  defp put_visitor(params, vid), do: Map.put(params, :client_reference_id, vid)
end

Add the route inside the scope that pipes through :browser:

post "/checkout", CheckoutController, :create

Then post to it from a template. With an action, <.form> adds the CSRF token that the pipeline checks (Phoenix.Component):

<.form for={%{}} action={~p"/checkout"}>
  <button type="submit">Buy</button>
</.form>

Stripe allows up to 200 characters in client_reference_id (Stripe API reference). If it already holds your own user or order ID, put the visitor ID in the session's metadata instead. Virling reads either:

defp put_visitor(params, vid), do: Map.put(params, :metadata, %{"virling_vid" => vid})

The checkout snippet generator has the code for other providers, the Stripe docs have the full lookup order, including PaymentIntents you create for Elements, and the Stripe integration page shows what Virling imports.

Checkout from a LiveView page

A LiveView talks over a WebSocket, and cookies are not among the keys of get_connect_info/2 (Phoenix.LiveView). The cookie has to be read from the connection of an HTTP request, not from the socket.

Post a form to the controller

This is the simplest way. The form above works unchanged inside a LiveView: without phx-submit the browser submits it over HTTP, and the request carries the current cookie.

To run your own checks in the LiveView first, add phx-submit and phx-trigger-action. LiveView handles the event, then submits the form to the controller (LiveView form bindings):

# lib/my_app_web/live/pricing_live.ex
defmodule MyAppWeb.PricingLive do
  use MyAppWeb, :live_view

  def mount(_params, _session, socket) do
    {:ok, assign(socket, trigger_submit: false)}
  end

  def handle_event("buy", _params, socket) do
    {:noreply, assign(socket, trigger_submit: true)}
  end

  def render(assigns) do
    ~H"""
    <.form
      for={%{}}
      id="checkout"
      action={~p"/checkout"}
      phx-submit="buy"
      phx-trigger-action={@trigger_submit}
    >
      <button type="submit">Buy</button>
    </.form>
    """
  end
end

Or read the cookie before the LiveView mounts

If the LiveView must create the Checkout Session itself, pass the cookie in with the :session option of live_session. Phoenix calls the function with the conn of the page request and merges the map, which needs string keys, into the LiveView session (live_session):

# lib/my_app_web/visitor.ex
defmodule MyAppWeb.Visitor do
  def session(conn) do
    %{"virling_vid" => Plug.Conn.get_cookies(conn)["virling_vid"]}
  end
end

# lib/my_app_web/router.ex, in the scope that pipes through :browser
live_session :pricing, session: {MyAppWeb.Visitor, :session, []} do
  live "/pricing", PricingLive
end

In the LiveView, keep the value from the second argument of mount/3 and use it when you create the session, with the same put_visitor/2 as in the controller:

def mount(_params, session, socket) do
  {:ok, assign(socket, vid: session["virling_vid"])}
end

def handle_event("buy", _params, socket) do
  params =
    put_visitor(
      %{
        line_items: [%{price: "price_...", quantity: 1}],
        mode: :payment,
        success_url: "https://yourdomain.com/thanks"
      },
      socket.assigns.vid
    )

  case Stripe.Checkout.Session.create(params) do
    {:ok, session} ->
      {:noreply, redirect(socket, external: session.url)}

    {:error, _error} ->
      {:noreply, put_flash(socket, :error, "Checkout is not available right now.")}
  end
end

This value is as old as the page request. On a new visitor's first page the script has not set the cookie yet when the server reads it, and live navigation inside the same live_session makes no new HTTP request. A visitor who lands on the LiveView and buys there has no ID, so prefer the form when the page can be a landing page.

A subscription example

For a subscription, use a recurring price and set mode to :subscription. The visitor ID stays on the session. Virling does not read subscription_data.metadata, so an ID placed only there is not found:

params =
  put_visitor(
    %{
      # a recurring price
      line_items: [%{price: "price_...", quantity: 1}],
      mode: :subscription,
      success_url: "https://yourdomain.com/thanks"
    },
    get_cookies(conn)["virling_vid"]
  )

Only the first payment needs the visitor ID. A renewal takes the attribution of the customer's first payment, so each monthly or yearly charge is credited to the same visit, with no code on your side.

Cookieless mode and visitors without an ID

With data-cookieless on the script tag there is no virling_vid cookie, so the value is nil. The same happens when a browser blocks the script. The first put_visitor/2 clause leaves the field out, checkout works as before, and the payment counts toward revenue as Unattributed. Do not send a session or user ID in its place: Virling has no visits recorded under it.

To set the cookie only after the visitor agrees, use cookieless until consent. The controller does not change.

Step 4: verify with a test payment

  1. Connect a restricted Stripe key that starts with rk_test_ in Virling, and use your test secret key in Phoenix. Payments imported with a test key stay in your reports, so use a separate site in Virling if you want to keep them out.
  2. In a private window, open your deployed site with ?utm_source=test&utm_medium=test. The script does not count localhost unless the tag has data-dev.
  3. Go to checkout and pay with the card 4242 4242 4242 4242, any future date and any three-digit CVC (Stripe testing).
  4. Wait a minute for the next sync and open /app/yourdomain.com/payments. The payment should show the test source instead of Unattributed. Open it to see its journey.

If it shows Unattributed, check that the page you bought from loads the script, that the form posts to the same domain, so the cookie is sent, and that the session in Stripe has a client_reference_id. If only LiveView purchases lack it, use the form. The full checklist is in test your setup, and how the join works from visit to payment is in how to track Stripe revenue by traffic source.

Frequently asked questions

How do I pass UTM parameters to Stripe Checkout in Phoenix?

Read the visitor ID with get_cookies(conn)["virling_vid"] in the controller that creates the Checkout Session and pass it as client_reference_id. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

Can a LiveView read the cookie from the socket?

No. Cookies are not among the connect info a socket offers. Post a normal form to a controller, or read the cookie from the conn in the session function of a live_session.

Do I need fetch_cookies in the router?

Not in the default browser pipeline. Its fetch_session plug also fetches cookies. In a pipeline without it, add plug :fetch_cookies, or get_cookies/1 raises an error.

Should I use client_reference_id or metadata.virling_vid?

Use client_reference_id unless it already holds your own user or order ID. In that case put the visitor ID in the session's metadata.virling_vid. Virling reads either.

Are subscription renewals attributed?

Yes. A renewal takes the attribution of the customer's first payment, so every monthly or yearly charge is credited to the visit that led to the first one, even though the renewal itself has no visit.

What happens if the cookie is missing?

The session is created without a visitor ID, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.
