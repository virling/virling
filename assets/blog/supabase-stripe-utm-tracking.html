Supabase and Stripe UTM tracking: Checkout from an Edge Function

By Devendra Variya, co-founder of Virling. Published 2026-11-22, updated 2026-11-25.

If your app creates Stripe Checkout Sessions in a Supabase Edge Function, the virling_vid cookie does not reach that function: it runs on supabase.co, not on your domain. So read the visitor ID in the browser with window.virling?.vid?.(), send it in the request body, and pass it to the session as client_reference_id or metadata.virling_vid. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each.

This is a common setup for apps made with AI builders. If you would rather hand the change to your coding assistant, the prompt is in track Stripe revenue in an AI-built app. For a server on your own domain, see Next.js Stripe UTM tracking. For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Step 1: add the script to every page

Paste the tag before </head> in your app's index.html, or in the layout every route uses. Keep defer. If you self-host, replace app.virling.com with your Virling server.

<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: send the visitor ID from the browser

window.virling?.vid?.() returns the same ID as the cookie. The script loads with defer, so wait briefly for it before reading, and send nothing if it is still missing, for example when the script is blocked or runs in cookieless mode. Then call the function with supabase-js:

async function visitorId() {
  for (let i = 0; i < 20 && !window.virling?.vid; i++) {
    await new Promise((r) => setTimeout(r, 100));
  }
  return window.virling?.vid?.() || null;
}

async function checkout() {
  const { data, error } = await supabase.functions.invoke("create-checkout", {
    body: { vid: await visitorId() },
  });
  if (error) throw error;
  window.location.href = data.url;
}

Step 3: attach it to the Checkout Session

In the Edge Function, read the ID from the body and pass it as client_reference_id. The function answers the browser's preflight request, since the call comes from your domain:

// supabase/functions/create-checkout/index.ts
import Stripe from "npm:stripe";

const stripe = new Stripe(Deno.env.get("STRIPE_SECRET_KEY")!, {
  httpClient: Stripe.createFetchHttpClient(),
});

const cors = {
  "Access-Control-Allow-Origin": "https://yourdomain.com",
  "Access-Control-Allow-Headers": "authorization, x-client-info, apikey, content-type",
};

Deno.serve(async (req) => {
  if (req.method === "OPTIONS") return new Response("ok", { headers: cors });

  const { vid } = await req.json().catch(() => ({}));
  const visitor = typeof vid === "string" && /^[A-Za-z0-9-]{8,64}$/.test(vid)
    ? vid
    : undefined;

  const session = await stripe.checkout.sessions.create({
    client_reference_id: visitor,
    line_items: [{ price: "price_...", quantity: 1 }],
    mode: "subscription",
    success_url: "https://yourdomain.com/thanks",
  });

  return new Response(JSON.stringify({ url: session.url }), {
    headers: { ...cors, "Content-Type": "application/json" },
  });
});

Set the key with supabase secrets set STRIPE_SECRET_KEY=sk_... and deploy with supabase functions deploy create-checkout. The check on vid keeps anything that is not a visitor ID out of Stripe.

Or with metadata

If client_reference_id already holds your Supabase user ID, keep it there and put the visitor ID in the session's metadata.virling_vid instead. Virling reads either:

const session = await stripe.checkout.sessions.create({
  client_reference_id: user.id, // your own ID stays
  metadata: visitor ? { virling_vid: visitor } : {},
  line_items: [{ price: "price_...", quantity: 1 }],
  mode: "subscription",
  success_url: "https://yourdomain.com/thanks",
});

You do not need to send the UTM tags themselves: the script has already recorded them against the visitor ID. The full lookup order, including PaymentIntents you create for Elements, is in the Stripe docs and on the Stripe integration page.

Check that it works

Run one test payment through the whole path. Use a separate Supabase project for it: on the live project, a test key in STRIPE_SECRET_KEY would put your real buyers into test mode too.

  1. In Virling, connect a restricted Stripe key that starts with rk_test_. Set your own test secret key on the test project with supabase secrets set STRIPE_SECRET_KEY=sk_test_..., and use a price created in test mode. A new secret is read right away, without another deploy (environment variables).
  2. Deploy the app on a subdomain of your domain, such as staging.yourdomain.com, and put that origin in Access-Control-Allow-Origin. The script does not track on localhost, and visits on a host other than your domain or its subdomains, such as a builder's preview, are dropped.
  3. Open a private window and visit a page that runs the script through a tagged link, such as https://staging.yourdomain.com/?utm_source=test&utm_medium=email. Run window.virling.vid() in the browser console and note the ID.
  4. In the same window, start checkout. In the network tab, the body of the create-checkout request should hold the ID from step 3 as vid. Pay with the card 4242 4242 4242 4242, any future date and any three-digit CVC (Stripe testing).
  5. Check the Checkout Session with the log line below, in the Logs tab of the function in the Supabase Dashboard (logging). client_reference_id, or virling_vid in the session's metadata if you use that, should be the same ID.
  6. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed. Open it to see its journey.

For step 5, add this right after the session is created, and remove it afterwards:

console.log(session.id, session.client_reference_id, session.metadata);

If your function sets customer, use a new customer for each test: a later payment by the same customer is a renewal and keeps the first payment's channel. A site has one Stripe connection, and test payments stay in your reports after you replace the key with a live one. If a step fails, see test your setup.

If it still shows Unattributed, open the Checkout Session in the Stripe Dashboard and look for the visitor ID in client_reference_id or the metadata. If it is empty, check the request body your browser sends to the function. Payments without a visitor ID still count toward revenue, as Unattributed.

Frequently asked questions

Does the virling_vid cookie reach a Supabase Edge Function?

No. The cookie is set on your domain, and the function runs on supabase.co, so the browser does not send it. Read the ID in the browser with window.virling?.vid?.() and send it in the request body.

Should I use client_reference_id or metadata.virling_vid?

Use client_reference_id unless it already holds your own ID, such as the Supabase user ID. In that case put the visitor ID in the session's metadata.virling_vid. Virling reads either.

Do I need to pass the UTM tags to Stripe?

No. The Virling script records the UTM tags of every visit against the visitor ID, so passing the ID is enough. Virling joins the payment to all the visits behind it, including untagged ones such as search and referrals.

What happens if the visitor ID is missing?

The session is created without one, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.

Do Stripe Payment Links need an Edge Function?

No. Use a normal link to buy.stripe.com on a page that runs the script. The script adds client_reference_id to the link when the page loads and again on click, unless the link already has one.

Why does my checkout Edge Function return a CORS error?

Either Access-Control-Allow-Origin is not exactly the origin of your page, such as www or a staging subdomain, or the function failed and its error response has no CORS headers. Check the function's logs, then return the same headers on every response, errors included.
