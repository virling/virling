Django Stripe UTM tracking: Checkout in Python

By Devendra Variya, co-founder of Virling. Published 2026-11-20, updated 2026-11-25.

Django Stripe UTM tracking comes down to one value. Load the Virling script in your base template, then read the virling_vid cookie with request.COOKIES.get('virling_vid') in the view that creates the Stripe Checkout Session and pass it as client_reference_id, or as metadata.virling_vid if that field is taken. Stripe keeps that one ID, and Virling joins the payment to every visit behind it, with the UTM tags of each.

This post covers Django with the stripe Python library. The same steps for other stacks are in Next.js Stripe UTM tracking, Flask Stripe UTM tracking, Laravel Stripe UTM tracking, Symfony Stripe UTM tracking and Phoenix Stripe UTM tracking. For Payment Links, metadata limits and where the values show up in Stripe, see the general guide to Stripe Checkout UTM parameters.

Why Stripe Checkout loses your UTM tags

UTM tags live on the landing URL. Stripe Checkout runs on Stripe's domain and only stores what your server passes when it creates the session, so the tags of the visit are gone unless you carry them over. The same thing happens on any redirect that drops the query string, as covered in UTM parameters lost after redirect. Passing one visitor ID instead of the tags keeps earlier visits and untagged ones, such as search and referrals, too.

Step 1: add the script to the base template

Paste the tag before </head> in the template every page extends, usually templates/base.html. If you self-host, replace app.virling.com with your Virling server.

<!-- templates/base.html -->
<script defer src="https://app.virling.com/v.js"
  data-site="yourdomain.com"></script>

The script sets the first-party virling_vid cookie on your domain and records the UTM tags of each visit against it.

Step 2: create the Checkout Session in a view

Your server receives the cookie with every request from the browser. The script sets it as a plain cookie, so read it with request.COOKIES.get('virling_vid'), not get_signed_cookie(). With the stripe Python library, read it where you create the session and pass it as client_reference_id:

# billing/views.py
import stripe
from django.conf import settings
from django.shortcuts import redirect
from django.views.decorators.http import require_POST

stripe.api_key = settings.STRIPE_SECRET_KEY


@require_POST
def checkout(request):
    params = {
        "line_items": [{"price": "price_...", "quantity": 1}],
        "mode": "subscription",
        "success_url": "https://yourdomain.com/thanks",
    }
    vid = request.COOKIES.get("virling_vid")
    if vid:
        params["client_reference_id"] = vid

    session = stripe.checkout.Session.create(**params)
    return redirect(session.url)

Add it to your URLs with path("checkout/", views.checkout, name="checkout") and post to it from a template form. The browser sends the cookie along:

<form action="{% url 'checkout' %}" method="post">
  {% csrf_token %}
  <button type="submit">Subscribe</button>
</form>

When client_reference_id is taken

If you already use client_reference_id for your own user or order ID, put the visitor ID in the session's metadata instead. Virling reads either:

    vid = request.COOKIES.get("virling_vid")
    if vid:
        params["metadata"] = {"virling_vid": vid}

If you create your own PaymentIntent for Elements instead of a Checkout Session, set the same metadata on stripe.PaymentIntent.create(), as in Stripe Elements UTM tracking. The full lookup order is in the Stripe docs and in link checkout to visits, and the Stripe integration page shows what Virling imports.

Subscriptions and renewals

Only the first payment needs the visitor ID. A renewal takes the attribution of the customer's first payment, so each monthly or yearly charge of the subscription is credited to the same visit, with no code on your side. Plan changes count as renewals too.

Set the visitor ID on the Checkout Session, not only on the subscription:

vid = request.COOKIES.get("virling_vid")
params = {
    "mode": "subscription",
    "line_items": [{"price": "price_...", "quantity": 1}],
    "success_url": "https://yourdomain.com/thanks",
    # Virling does not read the subscription's metadata
    "subscription_data": {"metadata": {"plan": "pro"}},
}
if vid:
    # Virling reads this one, on the session
    params["metadata"] = {"virling_vid": vid}

The first invoice finds its visitor through the session. Each renewal is then matched to the customer's first payment by Stripe customer ID, so it needs no metadata. If the buyer already has a Stripe customer, pass its ID as customer so a plan they buy later is matched to their first payment. A free trial that starts through Checkout after you connect Stripe is kept too: its first charge, when it has no visitor ID of its own, is credited to the visit before the trial. The rules are in renewals.

Check that it works

Run one test payment through the whole path:

  1. In Virling, connect a restricted Stripe key that starts with rk_test_. Your app keeps its own test secret key in settings.STRIPE_SECRET_KEY and uses a price created in test mode.
  2. Run the app in test mode on your domain or a subdomain of it, such as staging.yourdomain.com, and add that host to ALLOWED_HOSTS. Visits on localhost are not recorded for your site.
  3. Open a private window and visit a page that runs the script through a tagged link, such as https://staging.yourdomain.com/?utm_source=test&utm_medium=email. Run window.virling.vid() in the browser console and note the ID.
  4. In the same window, press the Subscribe button, so the form posts to the checkout view. Pay with the card 4242 4242 4242 4242, any future date and any three-digit CVC (Stripe testing).
  5. Check the Checkout Session with the log line below. client_reference_id, or virling_vid in the session's metadata if you use that, should be the ID from step 3. The charge and PaymentIntent do not need it: Stripe does not copy session metadata to them.
  6. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed. Open it to see its journey.

For step 5, add this right after stripe.checkout.Session.create() and remove it afterwards:

print(session.id, session.client_reference_id, session.metadata)

If the view passes customer, use a new customer for each test: a later payment by the same customer is a renewal and keeps the first payment's channel. A site has one Stripe connection, and test payments stay in your reports after you replace the key with a live one. If you want only real payments in your numbers, make one small live payment instead and refund it. If a step fails, see test your setup.

Payments without a visitor ID still count toward revenue, as Unattributed. How the join works from visit to payment is in how to track Stripe revenue by traffic source, and the SaaS page shows what you get per channel.

Frequently asked questions

How do I pass UTM parameters to Stripe Checkout in Django?

Read the visitor ID with request.COOKIES.get('virling_vid') in the view that creates the Checkout Session and pass it as client_reference_id. The Virling script records the UTM tags of every visit against that ID, so the payment is joined to all of them.

How do I put the visitor ID in Stripe Checkout metadata with Python?

Add metadata={'virling_vid': vid} to stripe.checkout.Session.create(). Use it when client_reference_id already holds your own user or order ID. Virling reads metadata.virling_vid or client_reference_id on the session.

Should I use get_signed_cookie for virling_vid?

No. The script sets virling_vid as a plain cookie in the browser, so Django has no signature to check. Read it with request.COOKIES.get('virling_vid').

Are subscription renewals attributed?

Yes. A renewal takes the attribution of the customer's first payment, so every monthly or yearly charge is credited to the visit that led to the first one, even though the renewal itself has no visit.

What happens if the cookie is missing?

The session is created without a visitor ID, for example when the script is blocked or runs in cookieless mode. The payment still counts toward revenue, as Unattributed.
