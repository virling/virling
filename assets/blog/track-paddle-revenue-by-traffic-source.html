How to track Paddle revenue by traffic source

By Devendra Variya, co-founder of Virling. Published 2026-11-05, updated 2026-11-25.

To track Paddle revenue by traffic source, give each visitor an ID, pass it to Paddle as custom data when they check out, and join each transaction back to the visits that came before it. Paddle knows who paid and how much. It does not know which page or channel they came from.

Step 1: set a visitor ID

Your analytics script sets one first-party ID per visitor and remembers the first source: referrer, UTM tags or direct. Put the script on the page that opens checkout as well as on your marketing pages.

Step 2: send the ID to Paddle at checkout

The visitor ID lives in the virling_vid cookie, and window.virling?.vid?.() returns it in the browser. Pick the option that matches how you sell. Hosted checkout is covered in Paddle UTM tracking, and the App Router in Next.js Paddle UTM tracking.

Paddle.js. Pass the ID as customData when you open checkout:

Paddle.Checkout.open({
  items: [{ priceId: "pri_...", quantity: 1 }],
  customData: { virling_vid: window.virling?.vid?.() },
});

Transactions you create on your server. Read the cookie from the request and set custom_data on the transaction:

const res = await fetch("https://api.paddle.com/transactions", {
  method: "POST",
  headers: { authorization: `Bearer ${process.env.PADDLE_API_KEY}`, "content-type": "application/json" },
  body: JSON.stringify({
    items: [{ price_id: "pri_...", quantity: 1 }],
    custom_data: { virling_vid: req.cookies.virling_vid },
  }),
});
// Open it with Paddle.Checkout.open({ transactionId: (await res.json()).data.id })

Now every transaction carries the visitor who made it. If your checkout code can run before the analytics script has loaded, the value will be empty. The script loads with defer, so wait for it:

async function visitorId() {
  for (let i = 0; i < 20 && !window.virling?.vid; i++) {
    await new Promise((r) => setTimeout(r, 100));
  }
  return window.virling?.vid?.() || null;
}

Step 3: read transactions and join them to visits

Read completed transactions from Paddle with a read-only API key, then match each one's ID to that visitor's earlier visits. Credit one of them with a rule you keep fixed (see first touch or last touch).

Step 4: handle refunds and renewals

Two things change the numbers after the first sale. Refunds and chargebacks lower a transaction's revenue, so a channel that looks good on day one can shrink later. Subscription renewals carry no custom data of their own, so they should keep the channel of the first payment instead of landing in Direct.

Step 5: report revenue per channel

Group the joined transactions by channel and divide by visitors to get revenue per visitor. That is the table that tells you where to spend time.

Server-side tracking

Transactions need no server-side tracking: Virling reads them from Paddle. For things only your server sees, such as a signup or a transaction created by your backend, send an event to POST /api/event with the visitor ID from the cookie as v, so it joins the same visitor:

await fetch("https://app.virling.com/api/event", {
  method: "POST",
  headers: { "user-agent": req.headers["user-agent"] },
  body: JSON.stringify({
    n: "goal",
    g: "signup",
    u: "https://yourdomain.com/signup",
    s: "yourdomain.com",
    v: req.cookies.virling_vid,
  }),
});

Forward the visitor's User-Agent: requests with an empty or bot user agent are dropped. The page URL in u must be on the site's domain or a subdomain. The endpoint answers 202 once the body parses, even when an event is dropped, and accepts an array of up to 50 events. Self-hosted, use your own server's address. The full field list is in the Event API reference.

What goes wrong

  • Forgetting step 2: transactions arrive with no visitor, so no channel gets the credit
  • Reading the ID before the script has loaded, so checkout opens with an empty value
  • Using a different name for the ID in checkout than the one your analytics expects, so nothing matches
  • Counting only the first sale and ignoring refunds, which overstates a channel

Doing it with Virling

Virling reads Paddle Billing through a read-only key with the transaction.read and adjustment.read permissions, plus subscription.read for retention. It imports the last 90 days on the first run, then new transactions every minute, and it does the join for you. It reads the ID from virling_vid in the transaction's custom data. The snippet is in the docs, and the setup is on the Paddle integration page.

Check that it works

  1. Connect a sandbox key that starts with pdl_sdbx_.
  2. On your server, create the transaction at https://sandbox-api.paddle.com/transactions with a sandbox price ID and your server's own sandbox API key. Virling's read-only key cannot create transactions. Set Paddle.js on the page to the sandbox environment too.
  3. Open a private window and visit a page that runs the script through a tagged link, such as https://yourdomain.com/?utm_source=test&utm_medium=email.
  4. In the same window, go to checkout, so your server reads the virling_vid cookie and sets custom_data. Open the transaction with Paddle.js and pay with one of Paddle's test cards.
  5. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed.

Use a new email address for each test, because a later payment by the same customer is a renewal and keeps the first payment's channel. A site has one Paddle connection, and sandbox payments stay in your reports after you replace the key with a live one. If a step fails, see test your setup.

Frequently asked questions

Can Paddle show which traffic source a sale came from?

Not on its own. Paddle records the transaction, not the visit. You need to pass a visitor ID into checkout as custom data and join it to your analytics.

Where do I put the visitor ID in Paddle?

In custom data. With Paddle.js, pass customData when you open checkout. For transactions you create on your server, set custom_data on the transaction.

Which channel do Paddle renewals get?

Renewals carry no custom data of their own, so they keep the channel of the subscription's first payment.

Does this work in the Paddle sandbox?

Yes. Virling accepts sandbox keys, which start with pdl_sdbx_, so you can test the join before going live.

What happens to Paddle transactions without a visitor ID?

They still count toward revenue, as Unattributed. Matching a payment to a visitor by email works for Stripe only for now, so with Paddle pass virling_vid in custom data.

Can I send events to Virling from my server?

Yes. POST them to /api/event with the visitor ID from the virling_vid cookie and the visitor's User-Agent. Transactions themselves are read from Paddle, so they need no event.

What if Paddle checkout opens before the script loads?

window.virling.vid is not there yet and customData gets an empty value. Wait for it for up to two seconds, or create the transaction on your server with the ID from the cookie.

Do refunds change a channel's revenue?

Yes. Approved refund and chargeback adjustments lower the transaction's revenue, and transactions from the last 60 days are read again every 6 hours, so later refunds show up.
