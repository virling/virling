How to track Paddle revenue by traffic source

By Devendra Variya, co-founder of Virling. Published 2026-11-05, updated 2026-11-25.

To track Paddle revenue by traffic source, put the visitor ID in the transaction's custom_data as virling_vid, and Virling credits each completed transaction to that visitor's earlier visits. The rest of this post covers what is different about Paddle: it is the merchant of record, it bills through transactions, and its amounts include tax. How the visit and the payment are joined for every provider is in link checkout to visits.

Paddle is the merchant of record

Paddle sells your product to the buyer on your behalf. It is the seller on the receipt, it collects and remits sales tax and VAT, and it pays you out afterwards. For attribution, that has two effects:

  • Checkout runs in Paddle's overlay, inline frame or hosted page, so your landing page's UTM tags and referrer never reach it. Paddle only stores the custom data you hand it.
  • Virling does not match Paddle payments to visitors by email. The virling_vid in the transaction's custom data is the only link between a sale and a visit, so every checkout path needs to set it.

The same setup for the other merchants of record Virling supports is in set up a merchant of record checkout.

Transactions, not subscriptions

In Paddle Billing, money moves through transactions. A subscription is the agreement, and each time it bills, Paddle creates a new transaction for it. Virling reads revenue from transactions with status completed or paid, and uses each one's origin to tell first payments from repeat ones:

Transaction originWhat it isHow Virling credits it
webA checkout opened with Paddle.jsFrom virling_vid in its custom data
apiA transaction your server createdFrom virling_vid in its custom data
subscription_recurringA renewalThe channel of the customer's first payment
subscription_updateA plan changeThe channel of the customer's first payment
subscription_chargeA one-off charge on a subscriptionThe channel of the customer's first payment

Subscription transactions carry no visitor ID of their own, so the first payment is the one that matters. A subscription that starts with a free trial creates a first transaction with nothing to pay, and the customer's later payments are credited to the visit before that trial. Virling reads the subscriptions themselves, once an hour, only when the key has subscription.read, and only for retention.

custom_data on overlay and hosted checkout

Overlay and inline checkout. Paddle.js opens both with Paddle.Checkout.open, which takes customData:

Paddle.Checkout.open({
  items: [{ priceId: "pri_...", quantity: 1 }],
  customData: { virling_vid: window.virling?.vid?.() },
});

The Virling script does not add the ID to Paddle checkouts by itself. It loads with defer, so if checkout can open before it, for example an inline checkout on page load, wait for the ID first:

async function visitorId() {
  for (let i = 0; i < 20 && !window.virling?.vid; i++) {
    await new Promise((r) => setTimeout(r, 100));
  }
  return window.virling?.vid?.() || null;
}

Hosted checkout. Paddle's hosted checkout links document no custom_data parameter. Create the transaction on your server with the ID from the cookie, then send the buyer to your hosted checkout link with ?transaction_id= and the new transaction's ID:

const res = await fetch("https://api.paddle.com/transactions", {
  method: "POST",
  headers: { authorization: `Bearer ${process.env.PADDLE_API_KEY}`, "content-type": "application/json" },
  body: JSON.stringify({
    items: [{ price_id: "pri_...", quantity: 1 }],
    custom_data: { virling_vid: req.cookies.virling_vid },
  }),
});
const { data } = await res.json();
// Hosted: redirect to your checkout link with ?transaction_id=${data.id}
// Overlay: Paddle.Checkout.open({ transactionId: data.id })

Custom data on a customer, product or price is not read; it has to be on the transaction. More on hosted checkout is in Paddle UTM tracking, and for the App Router, Next.js Paddle UTM tracking.

Amounts include tax

Virling counts each transaction's total, which is after discounts and includes the tax Paddle collected. It is not your payout: Paddle keeps the tax and its fee before paying you. So the revenue Virling shows for Paddle is higher than what reaches your bank, and a channel whose buyers live in high VAT countries looks slightly larger than one with the same sales in low tax countries. Compare channels with each other, not with your Paddle payout report.

Refunds and chargebacks

Paddle records a refund or a chargeback as an adjustment on the transaction, which is why the key needs adjustment.read. Virling subtracts approved refund and chargeback adjustments from the transaction's revenue, on the transaction's date, and marks it partially refunded or refunded. A pending refund counts once Paddle approves it. Transactions from the last 60 days are read again every 6 hours, so a refund can take that long to show, and one on an older transaction is not picked up automatically.

Try it in the Paddle sandbox

Connect a sandbox key, which starts with pdl_sdbx_ and needs transaction.read and adjustment.read. Set Paddle.js to the sandbox environment, or create the transaction at https://sandbox-api.paddle.com/transactions with your server's own sandbox key, since Virling's read-only key cannot create one. Land on your site in a private window through https://yourdomain.com/?utm_source=test&utm_medium=email, check out with a Paddle test card, and within about a minute the sale at /app/yourdomain.com/payments shows the test source and the Email channel. Pay with a new email address each time, since a second sale to the same customer counts as a renewal. Sandbox sales stay in your reports after you switch to a live key. The setup is also on the Paddle integration page, and checkout on another domain is covered in cross-domain checkout attribution.

Frequently asked questions

Can Paddle show which traffic source a sale came from?

No. Paddle is the merchant of record and runs checkout on its own overlay or page, so it never sees your UTM tags or referrer. Pass the visitor ID as custom data and Virling joins the transaction to the visits behind it.

Where do I put the visitor ID in Paddle?

On the transaction's custom data. With Paddle.js, pass customData when you open checkout. For hosted checkout or transactions you create on your server, set custom_data on the transaction.

Which channel do Paddle renewals get?

Transactions with origin subscription_recurring, subscription_update or subscription_charge carry no custom data of their own, so they keep the channel of the customer's first payment.

Is Paddle revenue in Virling before or after tax?

It includes tax. Virling counts the transaction total, which includes the tax Paddle collected as merchant of record, before Paddle's fee, so it is higher than your payout.

Does Virling match Paddle payments by email?

No. Email matching covers Stripe, Shopify and WooCommerce. A Paddle transaction without virling_vid in its custom data counts toward revenue as Unattributed.

Do refunds change a channel's revenue?

Yes. Approved refund and chargeback adjustments lower the transaction's revenue, and transactions from the last 60 days are read again every 6 hours, so later refunds show up.
