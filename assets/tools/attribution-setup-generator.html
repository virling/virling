    How revenue attribution works

    1. The Virling script stores a visitor ID in the first-party virling_vid cookie and records each visit with its referrer and UTM tags.
    2. Virling reads payments from your provider with a read-only key, polling once a minute.
    3. When checkout carries the visitor ID, the payment is joined to the visits behind it. Payments without it still count toward revenue, as Unattributed.

    Hosted checkout links on buy.stripe.com, buy.polar.sh, checkout.dodopayments.com and *.lemonsqueezy.com need no code: the script adds the visitor ID to them. The full reference is in link checkout to visits.

    Attribution setup FAQ

    How do I track revenue by traffic source?

    Add the Virling script to your site, connect your payment provider with a read-only key, and pass the visitor ID from the virling_vid cookie into checkout. Virling then joins each payment to the visit that led to it, with its referrer and UTM tags.

    Do I need a backend?

    Not always. Hosted checkout links on buy.stripe.com, buy.polar.sh, checkout.dodopayments.com and *.lemonsqueezy.com need no code, and Paddle.js can read the ID in the browser. Checkouts you create with a secret API key, such as Creem checkouts, need a server.

    Does Virling change anything in my payment account?

    No. Virling reads payments with a read-only key and never creates, changes or refunds anything. LemonSqueezy keys cannot be made read-only, and Creem and RevenueCat keys need webhook access so Virling can add its one webhook.

    Are subscription renewals attributed?

    Yes. A renewal keeps the channel of the customer's first payment, so every renewal is credited to the visit that led to the first one.

    What happens to payments without the visitor ID?

    They still count toward revenue, as Unattributed, but are not credited to any visit or channel.
