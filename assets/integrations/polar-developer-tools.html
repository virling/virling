integrations / polar for developer tools

See which channel brings the developers who pay you on Polar.

For open source maintainers and developer tool makers who sell licenses, sponsorships or subscriptions through Polar. Virling ties each Polar payment to the channel and campaign that brought the buyer, whether that was your README, a launch post, a search result or a newsletter. Open source under AGPL, hosted or self-hosted.

Start free trial See the demo

Polar records who paid and how much. It does not record the visit that brought the buyer to your site. Virling reads your Polar orders with a read-only organization access token and joins each one to the visitor who checked out.

What you get

  • Each payment credited to a channel and campaign. When checkout carries the visitor ID, the order is joined to the visits before it, so you see whether a buyer came from GitHub, a search result, a post or a tagged campaign.
  • Checkout links that need no code. Links on buy.polar.sh carry the visitor ID by themselves: the script adds reference_id to every such link on the page, and again on click.
  • Renewals that keep the first channel. An order with billing reason subscription_cycle is a renewal and takes the channel, referrer, campaign and landing page of the customer's first payment, matched by Polar customer ID. Plan changes (subscription_update) keep it too.
  • Trials kept apart from revenue. A $0 order with billing reason subscription_create starts a trial. It is never counted as revenue, a payment or a customer; the customer's later payment is credited from the visits before the trial started.
  • Refunds taken off. New refunds update the order they belong to, and a pending refund is read again once it settles. Unpaid orders are checked again every 10 minutes for up to 30 days and imported once paid.
  • Who still pays. With subscriptions:read, subscription status is read once an hour so Retention can tell who still pays; without it, retention falls back to payment recency.

Set it up

  1. Add the site. Click + Add a site and enter your project's domain, such as yourproject.dev.
  2. Install the script. Paste the tag before </head> on the pages where people buy, including the page that holds your checkout links.
  3. Connect Polar. In your Polar organization's settings, create an Organization Access Token with orders:read and refunds:read, plus subscriptions:read for retention, and paste it into Virling. It starts with polar_oat_; production and sandbox tokens both work. Orders from the last 90 days are imported on the first run, then new orders every minute.
  4. Link checkout to visits. Keep each buy.polar.sh checkout link as a normal <a href> on a page that runs the script, and the script adds reference_id=<visitor ID>, which Polar stores in the order's metadata. For a checkout session you create on your server, set virling_vid in metadata from the virling_vid cookie. Virling reads it from the order's metadata, then the order's custom field data, then the customer's metadata.
const checkout = await polar.checkouts.create({
  products: ["PRODUCT_ID"],
  success_url: "https://yourproject.dev/thanks",
  metadata: { virling_vid: req.cookies.virling_vid },
});
// Send the customer to checkout.url

To check it, make a test payment from a page that runs the script, wait for the next sync, and open the payments list. The payment should show a channel instead of Unattributed. Payments without a visitor ID still count toward revenue, as Unattributed.

Every setting is on the Polar integration page, and Virling for developer tools covers the wider setup. The full walkthrough is in how to track Polar revenue by traffic source, Polar UTM tracking covers tagging links so each order shows its campaign, and GitHub revenue tracking shows how to tag README, repository and release links.

What to know

  • Orders older than the 90-day backfill are not imported, so renewals of subscriptions that started before that are Unattributed.
  • The script adds the visitor ID only to normal <a href> links on pages that run it, never replaces a parameter already on the link, and adds nothing in cookieless mode.
  • Payments without a customer ID cannot be linked to a first payment.

Open source

Virling is open source under AGPLv3, and the code is on GitHub. Use the hosted service, or self-host it as one binary with every feature. In a load test on 2026-10-31, in a container limited to one vCPU and 1 GB of RAM, it ingested 100,000 pageviews at 2,829 a second with none failed and a p99 of 34 ms, and used 157 MB of memory after the ingest.

Frequently asked questions

How do I see which channel brings my Polar buyers?

Connect Polar to Virling with a read-only organization access token and pass the visitor ID at checkout. Checkout links on buy.polar.sh get it from the script automatically; for a checkout session you create on your server, set virling_vid in its metadata. Each payment is then credited to the visits before it, with its channel and campaign.

Do I need to change my Polar checkout links?

No. Keep each buy.polar.sh link as a normal link on a page that runs the Virling script. The script adds reference_id with the visitor ID, unless it is already there, and Polar stores it in the order's metadata, where Virling reads it.

How are Polar renewals attributed?

An order with billing reason subscription_cycle is a renewal. It takes the channel, referrer, campaign and landing page of the customer's first payment, matched by Polar customer ID. Plan changes (subscription_update) keep that channel too.

Which scopes does the Polar token need?

orders:read and refunds:read, plus subscriptions:read so Retention can tell who still pays. No other scopes are needed.
