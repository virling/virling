Paddle revenue attribution for developer tools.

For APIs, CLIs and SDKs sold through Paddle Billing. Virling ties each Paddle transaction to the visit that brought the buyer, such as your docs, GitHub repository or package page, by passing a visitor ID to checkout in customData. You see which channel brings developers who pay, not only stars and downloads. Installs and terminal use are not tracked. Open source under AGPL, hosted or self-hosted.

A developer may find your package, read the docs, try the free tier and pay weeks later. Paddle records who paid and how much, but not the visit that brought them. Virling reads your Paddle Billing transactions with a read-only API key and joins each one to the visitor who checked out.

From docs, GitHub and package pages to checkout

  • Docs. With the same data-site, pages on yourtool.dev, docs.yourtool.dev and app.yourtool.dev count for one site and share the virling_vid cookie, so reading the docs never changes the channel the visit came from. A docs page that starts a visit is its landing page. See do your docs bring paying customers.
  • GitHub. Clicks from github.com land in Referral and show as GitHub in the Source tab. GitHub sends only its origin, so give the README, repository website field and release notes one utm_campaign each. GitHub revenue tracking has the links to copy.
  • Package pages. npmjs.com, pypi.org and crates.io are Referral rows under their own domain. Tag the README and homepage links to tell placements apart; package registry traffic covers each one.
  • Links printed by your CLI. A link opened from a terminal has no referrer. Tag it, such as ?utm_source=cli&utm_medium=referral&utm_campaign=upgrade-hint, or it is Direct. A tagged visit can take the credit from the channel that first brought the developer; switch to first touch to see that one.

By default a payment goes to the latest visit in the last 90 days that was not Direct. Virling for developer tools covers other channels, and the lookback window can be 30, 60, 90 or 365 days.

What is not tracked

Virling does not track installs, terminal use, API calls or anything your SDK does. npm install, pip install and a command in a shell never open your site, so they are not visits. Virling sees visits to pages that run the script, and the Paddle payments that follow.

Set it up

  1. Add the site. Click + Add a site and enter your domain, such as yourtool.dev, and its timezone.
  2. Install the script. Paste the tag before </head> on the site, the docs and the app, with the same data-site. Leave cookieless mode off.
  3. Connect Paddle. In Paddle, open Developer tools, then Authentication, and create an API key with transaction.read and adjustment.read, plus subscription.read for retention. Paste it under payments; live keys start with pdl_live_ and sandbox keys with pdl_sdbx_. Completed transactions from the last 90 days are imported on the first run, then new ones every minute.
  4. Pass the visitor ID. The script does not add it to Paddle checkouts by itself. With Paddle.js, overlay or inline, pass it as customData. window.virling?.vid?.() returns nothing when the script is blocked or not loaded yet.
Paddle.Checkout.open({
  items: [{ priceId: "pri_...", quantity: 1 }],
  customData: { virling_vid: window.virling?.vid?.() },
});

Server-created transactions

If your backend creates the transaction, read the virling_vid cookie from the buyer's request and set it in custom_data. Use your own Paddle key here, not the read-only one you gave Virling.

const res = await fetch("https://api.paddle.com/transactions", {
  method: "POST",
  headers: { authorization: `Bearer ${process.env.PADDLE_API_KEY}`, "content-type": "application/json" },
  body: JSON.stringify({
    items: [{ price_id: "pri_...", quantity: 1 }],
    custom_data: { virling_vid: req.cookies.virling_vid },
  }),
});
// Open checkout in the browser with Paddle.Checkout.open({ transactionId })

A transaction created from a terminal command or an API call has no browser cookie, so there is no visitor ID to pass. Have the CLI open your pricing page in the browser instead and start checkout there. Custom data on a customer, product or price is not read.

Trials and renewals

  • Trials kept apart from revenue. A subscription's first transaction with nothing to pay starts a trial. It is never counted as revenue, a payment or a customer, and the customer's later payment is credited to the visits before the trial started. Virling reads the trial start from a checkout opened with Paddle.js, not from a transaction your server created, so open trial checkouts with items and customData.
  • Renewals that keep the first channel. A transaction whose origin is subscription_recurring, subscription_update or subscription_charge is a renewal. It carries no custom data of its own and keeps the channel of the customer's first payment, matched by Paddle customer ID. Plan changes and one-time charges on a subscription, such as usage overage, count as renewals too.
  • Refunds and chargebacks taken off. Approved refund and chargeback adjustments lower the transaction's revenue, and transactions from the last 60 days are read again every 6 hours, so later refunds show up.
  • Who still pays. With subscription.read, subscription status is read once an hour so Retention can tell who still pays; without it, retention falls back to payment recency.

Check that it works

Connect a sandbox key, visit a page that runs the script in a private window through a tagged link, and pay with one of Paddle's test cards. Wait a minute for the next sync and open the payments list: the payment should show your test source instead of Unattributed. Use a new email address for each test, since a later payment by the same customer keeps the first payment's channel. Sandbox payments stay in your reports after you replace the key with a live one.

Every setting is on the Paddle integration page. The full walkthrough is in how to track Paddle revenue by traffic source, and Next.js Paddle UTM tracking covers the App Router.

What to know

  • Transactions older than the 90-day backfill are not imported, so renewals of subscriptions that started before that are usually Unattributed. Transactions from before the script was on your site count as revenue but are Unattributed.
  • A visit in one browser and a checkout in another, or on another device, cannot be tied together.
  • Payments without a customer ID cannot be linked to a first payment, and payments without a visitor ID still count toward revenue as Unattributed.

Frequently asked questions

How do I see which channel brings my Paddle customers?

Add the Virling script to your site and docs, connect Paddle with a read-only API key, and pass the visitor ID as customData when you open Paddle checkout. Each payment is credited to the visits before it, so the Channels card and its Source and Campaign tabs show whether GitHub, your docs, a package page or a search brought the developers who pay.

Does Virling track installs or CLI use?

No. Virling does not see package installs, terminal commands, API calls or SDK use. It sees visits to pages that run the script and the Paddle transactions that follow.

Can a checkout created on my server be credited?

Yes, when the request comes from the buyer's browser on your domain. Read the virling_vid cookie from that request and set custom_data: { virling_vid } on the transaction you create. A transaction created from a terminal or an API call has no cookie, so it counts toward revenue as Unattributed, unless the customer already has an attributed first payment.

How are Paddle trials and renewals credited?

A subscription's first transaction with nothing to pay, from a checkout opened with Paddle.js, starts a trial and is never counted as revenue. The customer's later payment is credited to the visits before the trial started. Renewals and plan changes keep the channel of the customer's first payment.

Which permissions does the Paddle API key need?

transaction.read and adjustment.read, plus subscription.read so Retention can tell who still pays. No other permissions are needed, and Virling never creates, changes or refunds anything.
