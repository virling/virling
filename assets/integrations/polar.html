Polar revenue attribution: each order joined to the visit behind it.

Virling ties each Polar payment to the visit that came before it, so your analytics show which channel, referrer and page bring paying customers, not just visitors. Open source, one Rust binary, or hosted.

Start free trial See the demo

Virling reads Polar orders, refunds and, when allowed, subscriptions with an organization access token.

Create a token

  1. In Polar, open your organization's settings and create an Organization Access Token. Polar's guide: organization access tokens.
  2. Give it the orders:read and refunds:read scopes, plus subscriptions:read so Retention can tell who still pays. No other scopes are needed.
  3. Paste it into Virling. It starts with polar_oat_.

Production and sandbox tokens both work. Virling tries api.polar.sh first and sandbox-api.polar.sh second. If a scope is missing, connecting fails with a message naming it.

What is imported

  • Orders from the last 90 days on the first run, then new orders every minute. Unpaid orders are checked again every 10 minutes for up to 30 days, and imported once paid.
  • Refunds. New refunds update the order they belong to. A pending refund is read again once it settles.
  • Renewals. An order with billing reason subscription_cycle is marked as a renewal.
  • Subscription status, once an hour, when the token has subscriptions:read. Without it, retention falls back to payment recency.

How a payment finds its visitor

Virling reads virling_vid from, in order: the order's metadata, the order's custom field data, then the customer's metadata. After those it reads a checkout link's reference_id from the order's metadata.

With a checkout session, set it in metadata:

const checkout = await polar.checkouts.create({
  products: ["PRODUCT_ID"],
  success_url: "https://yourdomain.com/thanks",
  metadata: { virling_vid: req.cookies.virling_vid },
});
// Send the customer to checkout.url

For the App Router, see Next.js Polar UTM tracking.

Checkout links

Checkout links on buy.polar.sh need no code. Keep the link as a normal <a href> on a page that runs the script: the script adds reference_id=<visitor ID> to it, unless it is already there, and Polar stores it in the order's metadata, where Virling reads it. A virling_vid custom field on the link still works too.

Test it in the sandbox

  1. Connect a token from the Polar sandbox.
  2. Open a private window and visit a page that runs the script through a tagged link, such as https://yourdomain.com/?utm_source=test&utm_medium=email.
  3. In the same window, go to a sandbox checkout your server creates with virling_vid in metadata, and pay with a test card. The script does not add the visitor ID to sandbox links.
  4. Wait a minute for the next sync, then open the payments list at /app/yourdomain.com/payments. The payment shows the test source and the Email channel of your tagged visit instead of Unattributed.

Use a new email address for each test: a later payment by the same customer is a renewal and keeps the first payment's channel. A site has one Polar connection, and sandbox orders stay in your reports after you replace the token with a production one. If you sell only through buy.polar.sh links, connect the production token, make one small live payment through a link and refund it. If a step fails, see Test your setup.

What you can see

Once orders come in, these cards on the dashboard answer questions a seller asks:

  • Which channels bring orders, not only visits? The Channels card lists visitors, revenue and revenue per visitor for each channel, with a Source tab for the site behind it.
  • Which launch post or newsletter sold the most? The Channels card's Campaign tab shows the same numbers for each campaign you tagged.
  • Which page do buyers see before they pay? The Pages card shows revenue by the last page before paying, and by the first page of the visit.
  • Which channel's orders get refunded? The Channels card also shows Refunded, the share of a row's payments that were refunded in whole or part.
  • How long do customers take to pay? The Time to pay card shows the median time from first visit to first payment for each channel with at least three first payments in the range. Renewals do not count.

What stays Unattributed

These orders still count toward revenue, but no channel is credited, unless the same customer has an earlier order or trial that was credited:

  • Orders from a checkout session created with no virling_vid in its metadata, when the customer's metadata has none either.
  • Orders from a checkout link opened from an email, a QR code or another site, or by a visitor with no visitor ID because the script was blocked or cookieless mode was on.
  • Orders from before the script was on your site, which usually includes the 90-day import.
  • Orders with a visitor ID when no visit of that visitor falls inside the lookback window.
  • Renewals, usually, when the first order is Unattributed or older than the first import.

Polar payments are not matched by email. To find the cause for one payment, see Unattributed revenue.

Frequently asked questions

How do I see which channel a Polar order came from?

Connect Polar to Virling with an organization access token. Virling reads virling_vid from the order metadata, the order's custom field data or the customer metadata and ties the order to the visit before it.

Which scopes does the Polar token need?

orders:read and refunds:read, plus subscriptions:read so Retention can tell who still pays. No other scopes are needed.

How do I attribute Polar checkout links to visits?

Keep each buy.polar.sh link as a normal link on a page that runs the script. The script adds reference_id with the visitor ID, unless it is already there, and Polar stores it in the order's metadata, where Virling reads it.

Which channel do Polar renewals get?

Orders with billing reason subscription_cycle or subscription_update, and any later order by the same customer, keep the channel of that customer's first order. If that order is older than the first import, its renewals are usually Unattributed.

Are Polar refunds taken off the channel?

Yes. A succeeded refund lowers the revenue of the order it belongs to, on that order's date, so the channel credited with the order drops too. A pending refund counts once it succeeds, if it does so within 7 days.

Why is a Polar payment Unattributed?

Usually because neither the order nor its customer carries a visitor ID: the checkout was created without virling_vid in its metadata, or a checkout link was opened from an email or another site.

Does Virling work with the Polar sandbox?

Yes. Paste a sandbox token and Virling reads sandbox orders and refunds. The script does not add the visitor ID to sandbox links, so test with a checkout your server creates with virling_vid in its metadata.

How far back does Polar history go?

The first import reads orders from the last 90 days. Orders from before the script was on your site count as revenue but are Unattributed.
