Creem knows who paid, and Virling knows which post they came from. A scoped API key, one webhook and the visitor ID in checkout metadata join the two; Link checkout to visits explains the idea for every provider.

Creem payment links need a server checkout

For some providers the Virling script adds the visitor ID to a plain checkout link when someone clicks it. It does not do this for Creem: a creem.io/payment link shared as is, on your page or anywhere else, reaches Creem with no visitor ID. Creem also returns checkout metadata only in webhooks, never on transactions, so the ID has to go into the checkout itself.

Give your buy button a small server route that creates the checkout with virling_vid in metadata, read from the visitor's cookie, and sends the buyer to the returned URL:

const res = await fetch("https://api.creem.io/v1/checkouts", {
  method: "POST",
  headers: { "x-api-key": process.env.CREEM_API_KEY, "content-type": "application/json" },
  body: JSON.stringify({
    product_id: "prod_...",
    success_url: "https://yourstore.com/thanks",
    metadata: { virling_vid: req.cookies.virling_vid },
  }),
});
// Send the customer to (await res.json()).checkout_url

Virling looks for virling_vid in the checkout's metadata first, then the subscription's, then the customer's. When the buyer lands back on your thanks page from a creem.io checkout or payment page, that return continues the visit and Creem is never counted as its source.

The API key and its scopes

  • transactions:read is the one Virling cannot work without. A key missing it is refused when you paste it.
  • webhooks:write lets Virling add its one checkout.completed webhook when you connect. Each delivery is checked against the creem-signature header, and the signing secret is stored encrypted. On a server with an https address, a key without this scope is refused, since Creem sends the visitor ID nowhere else.
  • subscriptions:read is optional. With it, subscription status is read once an hour so Retention can tell who still pays; without it, retention falls back to how recently each customer paid.

Create the key in Creem under Developers, then API keys, and paste it under payments in Virling. No other scopes are needed.

Test mode

A key that starts with creem_test_ is tried against test-api.creem.io first, and any other key against api.creem.io first, so live and test keys both connect without a setting. With a test key, Virling reads test transactions and adds its webhook in test mode; point your checkout route at https://test-api.creem.io too. A site has one Creem connection, and test payments stay in your reports after you replace the key with a live one.

Refunds and chargebacks

A refund lowers the revenue of its transaction, on that transaction's date, and a partial refund lowers it by the refunded amount. A chargeback counts as a full refund. Transactions from the last 60 days are read again every 6 hours, so a refund can take that long to show, and one on an older transaction is not picked up.

How far back history goes

The first import reads Creem transactions from the last 90 days, newest first, then new ones every minute. Those older sales count toward revenue, but they came before the webhook, so they carry no visitor ID and are usually Unattributed. Anything older than 90 days is not imported.

If you sell a template library or course as a membership, every payment after a customer's first is a renewal and keeps the first payment's channel. A completed checkout with nothing to pay starts a free trial, and the customer's first paid transaction is credited to it.

Compare posts, newsletters and creators

Why a Creem sale is Unattributed

  • The buyer used a Creem payment link. It carries no visitor ID. Fix: send buyers through your server route instead.
  • The webhook never arrived. It needs Virling on a public https address. A self-hosted server on plain http still imports payments, but they stay Unattributed; after moving to https, set VIRLING_BASE_URL and use Replace key to add the webhook.
  • The sale came before you connected. Imported history has no visitor ID.

Untagged links and cookieless mode are covered in Unattributed revenue.

Frequently asked questions

Do Creem payment links need code to be attributed?

Yes. The Virling script adds the visitor ID to some providers' checkout links, but not to Creem's. Create the checkout on your server with POST /v1/checkouts and set metadata.virling_vid to the visitor's virling_vid cookie. Payments without a visitor ID still count toward revenue as Unattributed.

Which scopes does the Creem API key need?

transactions:read, plus webhooks:write so Virling can add its one checkout.completed webhook, and optionally subscriptions:read so Retention can tell who still pays. No other scopes are needed. Live and test mode keys both work.

How are Creem refunds and chargebacks counted?

A refund lowers the revenue of its transaction, on that transaction's date, and a chargeback counts as a full refund. Transactions from the last 60 days are read again every 6 hours, so a refund can take that long to show.

Does Creem test mode work?

Yes. With a test mode key, Virling reads test transactions and adds its webhook in test mode. A site has one Creem connection, and test payments stay in your reports after you replace the key with a live one.

How far back does Creem history go?

The first import reads transactions from the last 90 days. They count as revenue, but those from before the webhook carry no visitor ID and are usually Unattributed.

Does a buyer coming back from Creem checkout start a new visit?

No. A return from a creem.io checkout or payment page continues the visit, and Creem is never counted as its source, so the sale stays with the post or link that sent the buyer.
