See which channel brings the people who pay for your open source project on Polar.

For open source maintainers who sell licenses, hosted plans or paid support through Polar. Virling shows which channel brought each paying customer: your GitHub README, your docs, Hacker News, a newsletter or a package registry. Virling is open source too, under AGPL, hosted or self-hosted.

Stars, downloads and Polar's order list tell you how popular a project is and who paid. None of them tells you which link a paying customer followed to your site. Virling reads your Polar orders with a read-only organization access token and joins each one to the visits of the person who checked out.

Where developers come from

The channel is read from the first page of a visit. A utm_medium of email, newsletter or a paid value decides first, then the referrer, then utm_source. So for most of these places a tag names the placement and covers clicks with no referrer, and the referrer decides the channel.

Newsletters do not need a referrer: links tagged utm_medium=newsletter or utm_medium=email are the Email channel, with the campaign you set.

Each payment is credited to one visit in the lookback window, 90 days by default. The default model takes the latest visit that was not Direct, so someone who found you on Hacker News and came back by typing your URL is credited to Hacker News. First touch, which credits the visit that introduced them, is one setting away.

Set it up

  1. Add the site and install the script. Add your project's domain and paste the tag before </head> on your site and docs, including the pages that hold your checkout links.
  2. Create a token. In Polar, open your organization's settings and create an Organization Access Token. Polar's guide: organization access tokens.
  3. Give it scopes. orders:read and refunds:read, plus subscriptions:read so Retention can tell who still pays. No other scopes are needed.
  4. Paste it into Virling. It starts with polar_oat_. Production and sandbox tokens both work, and if a scope is missing, connecting fails with a message naming it.
  5. Link checkout to visits. Keep each buy.polar.sh checkout link as a normal <a href> on a page that runs the script: the script adds reference_id=<visitor ID>, unless it is already there, and Polar stores it in the order's metadata. For a checkout session you create on your server, set virling_vid in metadata.
const checkout = await polar.checkouts.create({
  products: ["PRODUCT_ID"],
  success_url: "https://yourproject.dev/thanks",
  metadata: { virling_vid: req.cookies.virling_vid },
});
// Send the customer to checkout.url

Virling reads virling_vid from, in order: the order's metadata, the order's custom field data, then the customer's metadata.

What is imported

  • Orders from the last 90 days on the first run, then new orders every minute. Unpaid orders are checked again every 10 minutes for up to 30 days, and imported once paid.
  • Refunds. New refunds update the order they belong to. A pending refund is read again once it settles.
  • Renewals. An order with billing reason subscription_cycle is marked as a renewal and keeps the channel of the customer's first payment, so a hosted plan or support subscription stays credited to the visit that sold it.
  • Subscription status, once an hour, when the token has subscriptions:read. Without it, retention falls back to payment recency.

Your first week

  1. Day one: connect. Install the script on your site and docs, connect a Polar token and link checkout, as above. To test without real money, connect a token from the Polar sandbox first. A site has one Polar connection, and sandbox orders stay in your reports after you replace the token with a production one.
  2. Day one: place a test order. Open a private window and visit a page that runs the script through a tagged link, such as https://yourproject.dev/?utm_source=test&utm_medium=email. In the same window, go to a sandbox checkout your server creates with virling_vid in metadata, and pay with a test card. The script does not add the visitor ID to sandbox links, so if you sell only through buy.polar.sh links, connect the production token, make one small live payment instead and refund it. Use a new email address for each test.
  3. A minute later: check it. Open the payments list at /app/yourproject.dev/payments. The payment shows the test source and the Email channel instead of Unattributed. If it does not, follow Test your setup.
  4. Days two to seven: tag your links. Change the README, release notes and website field, and the package metadata with your next release.
  5. After the first few sales: open Payments, then Channels. On Payments, check that new sales name a source, and open one to see the visits before it with the credited one marked. On the Channels card, the Source tab splits Referral into GitHub and each registry, and the Campaign tab shows each tagged link. Imported orders are mostly from before the script, so expect them to be Unattributed.

Frequently asked questions

Which channel brings my Polar customers?

Connect Polar to Virling with a read-only organization access token and pass the visitor ID at checkout. Each payment is then credited to one visit before it, with that visit's channel, referrer, campaign and landing page. The default model credits the latest visit in the last 90 days that was not Direct.

How do GitHub and package registry visits show up?

A click from github.com, npmjs.com, pypi.org or crates.io lands in the Referral channel under its own domain, because none of those hosts is on a known list. Tag the link with utm_source and utm_campaign to see which README, release or package page it was.

Do I need to change my Polar checkout links?

No. Keep each buy.polar.sh link as a normal link on a page that runs the Virling script. The script adds reference_id with the visitor ID, unless it is already there, and Polar stores it in the order's metadata, where Virling reads it.

Which scopes does the Polar token need?

orders:read and refunds:read, plus subscriptions:read so Retention can tell who still pays. No other scopes are needed.

Is Virling itself open source?

Yes. Virling is open source under AGPLv3, with the code on GitHub. Use the hosted service, or self-host it with every feature.
